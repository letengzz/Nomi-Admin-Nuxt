# Nomi Admin Nuxt 部署指南

本文覆盖三种部署形态、首次上线步骤、日常更新与回滚、数据备份恢复，以及常见故障排查。

所有命令以 Linux 服务器为准（Ubuntu 22.04 / 24.04 验证）。Windows 只适合本地开发。

---

## 1. 先选部署形态

| 形态 | 用途 | 是否需要 MySQL | 后台登录/接口 | 推荐场景 |
| --- | --- | --- | --- | --- |
| **Docker Compose**（`compose.yaml`） | 生产 | 自带 MySQL 8.4 | 完整可用 | **推荐**，单机上线首选 |
| **裸机 Node + systemd** | 生产 | 需自备 MySQL | 完整可用 | 已有 MySQL/运维体系，或不便用 Docker |
| **GitHub Pages**（`ci-cd.yml`） | 演示站 | 不需要 | 假登录（`app/mock` 内存应答） | 对外演示、评审，**不能当生产** |

关键结论：**Pages 上跑的是静态演示站**。产物里没有 Nitro、没有数据库，`/api/health`、`/api/auth/login` 全部不可用，登录页是浏览器内的假登录，刷新即复原。真实业务必须用前两种。

下文第 3、4、5 节分别对应三种形态；第 6 节起（备份、更新、排查）对生产部署通用。

## 2. 部署前准备

### 2.1 版本要求

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| Node.js | **>= 22.12.0** | `package.json` 的 `engines` 已声明，低于此版本直接拒装 |
| pnpm | **11.20.0** | 由 `packageManager` 字段固定，`corepack enable` 后自动取该版本 |
| Docker | 24+ | 仅 Compose 方案需要 |
| Docker Compose | v2（`docker compose` 子命令） | 不支持 `docker-compose` v1 |
| MySQL | **8.0+**，建议 8.4 | Compose 方案由编排提供，裸机方案自备 |

### 2.2 必须准备的配置项

先在服务器上生成两个密钥，不要复用、不要提交到 Git：

```bash
# TOKEN_SECRET：token 表的 HMAC 密钥，32 字节
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# 数据库密码
openssl rand -base64 24
```

变量总表：

| 变量 | 生产必填 | 作用 | 备注 |
| --- | --- | --- | --- |
| `MYSQL_HOST` | 是 | 数据库地址 | 裸机 `127.0.0.1`；Compose 固定 `mysql` |
| `MYSQL_PORT` | 是 | 数据库端口 | 默认 `3306` |
| `MYSQL_USER` | 是 | 连库账号 | 裸机常用 `root` 或自建账号；Compose 写死 `nomi` |
| `MYSQL_PASSWORD` | 是 | 上面对应账号的密码 | 两套语义，见 2.3 |
| `MYSQL_DATABASE` | 是 | 库名 | 默认 `nomi_admin`，不存在时自动 `CREATE DATABASE` |
| `MYSQL_POOL_SIZE` | 否 | 连接池上限 | 默认 10，中后台够用，调大只会更早被 MySQL 拒连 |
| `TOKEN_SECRET` | **是** | token 签名密钥 | 缺失/变更的后果见下 |
| `INITIAL_ADMIN_PASSWORD` | 建议 | 初始超管口令 | 仅「user 表为空」那一次生效 |
| `SEED_DEMO_ACCOUNTS` | 否 | 是否创建演示账号 | 生产默认不建，置 `1` 才建 |
| `NOMI_UPLOAD_DIR` | 否 | 上传文件落盘目录 | 默认 `<cwd>/data/uploads`；Compose 为 `/app/data/uploads` |
| `NITRO_HOST` / `NITRO_PORT` | 否 | 监听地址/端口 | 容器内 `0.0.0.0:3000`；裸机建议 `127.0.0.1:3000` |
| `NUXT_BUILD_ID` | 否 | 健康检查回显的版本标识 | 见 7.2，用于确认线上跑的是哪次构建 |
| `IP_LOCATION_API` | 否 | 公网 IP 归属地查询 | 可选；不配时「登录地点」显示「公网 IP」，详见 2.5 |
| `MYSQL_ROOT_PASSWORD` | 仅 Compose | 容器内 MySQL 的 root 密码 | 只被 healthcheck 和备份命令使用，应用不读 |

`TOKEN_SECRET` 的两个后果必须知道：

- **未配置**：Compose 里用 `${TOKEN_SECRET:?...}` 强制校验，容器直接起不来；裸机不配则回落到代码里的开发默认值 —— 等于线上签名密钥公开。
- **更换**：等于让所有已签发的登录态立即失效（`token` 表按它做 HMAC 校验），所有用户被强制重新登录。轮换要挑时间窗口。

初始超管口令的规则（`server/utils/auth/initial-password.ts`）：

- 不配置 → 首次建库时随机生成 24 位，写入 `<cwd>/data/initial-admin-password.txt`（权限 600），首次改密后自动删除；开发环境同时打印到控制台，生产只给文件路径（避免明文进日志采集系统）。
- 配置了 → 必须 **≥16 位且覆盖「小写/大写/数字/符号」中至少三类**，否则**启动失败**。宁可不启动，也不让弱口令进库。
- 无论哪种来源，该账号首次登录后必须先改密；改密前除个人中心/退出登录外的接口一律返回业务码 428。

### 2.3 两套 `MYSQL_*` 不要混填

这是最容易踩的坑：

| 场景 | `MYSQL_PASSWORD` 指谁 | `MYSQL_ROOT_PASSWORD` |
| --- | --- | --- |
| 本机开发 / 裸机 Node 直跑 | 这台 MySQL 里 `MYSQL_USER`（通常 root）的密码 | 不读取 |
| Docker Compose | 容器内 `nomi` 账号的密码（compose 写死 `MYSQL_USER: nomi`） | 容器内 MySQL 的 root 密码 |

Compose 下 `nomi` 账号**只在 `mysql_data` 卷首次初始化时创建**。之后改 `MYSQL_PASSWORD` 不会作用于已有卷，应用会直接连不上库。需要进容器 `ALTER USER`，或删卷重建（会丢数据，先备份）。

### 2.4 网络与端口

| 环境 | 对外端口 | 链路 | TLS |
| --- | --- | --- | --- |
| 测试（默认） | 3000 | 宿主机 3000 → nginx 容器 80 → app 容器 3000 | 无 |
| 正式（`compose.prod.yaml`） | 80 / 443 | 宿主机 nginx → `127.0.0.1:3000` → app 容器 | certbot |

- 测试环境 app 不对外映射端口，只在 compose 内网可达；对外入口是容器 nginx 占用的 3000。
- 正式环境 app 只绑 `127.0.0.1:3000`，容器 nginx 不启动；80/443 与 HTTPS 由宿主机 nginx 处理。
- 两套配置不会同时占着 3000，切换时按 3.7 节的 `down` / `up` 顺序操作。

上线前先确认域名 A 记录已指向服务器，否则 certbot 签发会失败。

### 2.5 「登录地点」为什么空白 / 只显示「公网 IP」

在线用户与系统日志的「登录地点」列来自 `ip_location` 字段，写入分两种：

- **内网 / 回环 IP**（`127.x`、`10.x`、`192.168.x`、`172.16-31.x`）：应用本地就能判定，显示「本地回环」「局域网」等，无需任何配置。本地开发看到的就是这类。
- **公网 IP**：需要 `IP_LOCATION_API` 才能查到真实地名。没配这个变量时，早期版本存空串 → 界面显示「—」；现在统一回落显示「公网 IP」，不再留空。要显示「中国 广东 深圳」这类具体地名，按下面配。

配置方法（填一个返回 JSON 的 URL，用 `{ip}` 占位）：

```bash
# .env（Compose 与裸机都读它；Compose 需在 compose.yaml 里透传，已配好）
IP_LOCATION_API=http://ip-api.com/json/{ip}?lang=zh-CN
```

应用会替换 `{ip}` 后 GET，从 `country` / `province` / `regionName` / `region_name` / `region` / `city` / `district` 等字段拼地名（兼容 `{"data":{...}}` 嵌套）。省名按 `province → regionName → region_name → region` 的优先级取：ip-api.com 的 `region` 只是 `IDF` 这类缩写，中文全名在 `regionName`，取错会显示成「法国 IDF 巴黎」。默认 **2500ms 超时**（早期版本写死 600ms，而 ip-api.com 实测要 700ms+，导致配置正确却必然超时降级——这就是「配了还是显示公网 IP」的根因）；网络慢或跨境可在 `.env` 里加 `IP_LOCATION_TIMEOUT=5000` 上调。失败静默降级成「公网 IP」，绝不影响登录或写日志；查到的地名会在进程内缓存（同一 IP 只查一次），失败不缓存，服务恢复后下次登录自动重试。免费公共接口有频率限制，生产建议自建或使用商业服务。

**排查「配了还是显示公网 IP」**：看服务端日志里 `[ip-location]` 前缀的行，它会写明是 HTTP 非 2xx、返回空地名，还是查询异常（含超时/出网失败原因）。再确认改完 `.env` 后重建过容器。

**改完必须重建 app 容器**才生效（compose 只在建容器时读环境变量）：

```bash
docker compose up -d                       # 一般会自动检测 env 变化并重建 app
docker compose up -d --force-recreate app  # 不放心就用这条，强制重建
```

只编辑 `.env` 不重建，界面会一直显示「公网 IP」——这是最容易误判成「配置没用」的一步。

两个常见坑：

1. **没走反向代理**：默认部署下 nginx 占对外 3000 并写入 `X-Forwarded-For`，应用拿得到真实公网 IP。若图省事把 app 端口直接映射出去（或自己写代理时漏了这一行），应用看到的会是 Docker 网桥 IP（`172.x`）或本机地址，被判成「局域网」。本仓库 `deploy/nginx.conf` 已配好，保持默认即可。
2. **改了配置但老记录不变**：`ip_location` 是登录/操作时写入时的快照，改配置不会回刷历史数据。历史空值现在显示「未知地点」；想要新地名，让用户重新登录一次即可。

## 3. 方案 A：Docker Compose（生产推荐）

`compose.yaml` 一条命令起「应用 + MySQL」，库表与种子由应用首启自动写入，不需要手工执行任何 SQL。

### 3.1 准备代码与环境文件

```bash
sudo mkdir -p /srv/nomi-admin && sudo chown "$USER":"$USER" /srv/nomi-admin
git clone <仓库地址> /srv/nomi-admin
cd /srv/nomi-admin
```

创建 `.env`（compose 会读它做**变量替换**，这个文件不会被打进镜像）：

```bash
cat > .env <<'EOF'
MYSQL_ROOT_PASSWORD=替换为root密码
MYSQL_PASSWORD=替换为nomi账号密码
MYSQL_DATABASE=nomi_admin
TOKEN_SECRET=替换为32字节随机串
INITIAL_ADMIN_PASSWORD=替换为16位以上强口令
SEED_DEMO_ACCOUNTS=0
EOF

chmod 600 .env
```

缺 `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` / `TOKEN_SECRET` 任一项，`docker compose up` 会直接报错退出 —— 刻意如此，免得起一个连不上库、token 用开发默认值的容器。

### 3.2 首次启动

```bash
docker compose build app            # 首次构建，需 2GB 以上可用内存
docker compose up -d                # app + mysql
docker compose ps                   # 两个服务都应变成 healthy
```

首启会依次发生：MySQL 初始化数据目录（约 20~40 秒）→ 应用启动 → 建库 → 建表 → 灌种子（含 scrypt 哈希，需要几秒）→ 生成初始超管。

### 3.3 验证

```bash
# 1. 健康检查（返回 status: ok 即进程正常）
curl -fsS http://127.0.0.1:3000/api/health

# 2. 首启日志：应能看到建表、种子、初始账号三组信息
docker compose logs app | grep -E "\[db\]|\[security\]"

# 3. 首页应 302 到 /admin
curl -sI http://127.0.0.1:3000/ | head -3

# 4. 浏览器打开 http://<服务器IP>:3000，应落到登录页
```

日志里出现 `[db] 种子数据已写入：…` 就说明库和种子都成功了。

### 3.4 取初始超管口令

- 配了 `INITIAL_ADMIN_PASSWORD`：直接用该口令登录，日志里不会打印明文。
- 没配：口令在容器内 `/app/data/initial-admin-password.txt`，该目录挂在 `app_data` 卷上，重建容器也不会丢。

```bash
docker compose exec app cat /app/data/initial-admin-password.txt
```

登录后系统会强制改密，改完这个文件自动删除。**改密完成后建议清掉 `.env` 里的 `INITIAL_ADMIN_PASSWORD`**（它只在空库那一次生效，留着只是增加泄露面）。

### 3.5 安全收尾

1. **确认流量经过 nginx，而不是 app 直连**。默认 compose 里 app 不映射端口、nginx 占对外 3000，
   这已经是正确形态。若你手动给 app 加过 `ports: '3000:3000'`，请删掉——
   否则应用只能看到 Docker 网桥 IP，登录地点会被判成「局域网」。
   裸机（Node 直跑）部署时，才需要把应用绑到 `127.0.0.1:3000` 让外层 nginx 接管。

2. **确认演示账号没有进库**：`SEED_DEMO_ACCOUNTS=0`（生产默认），日志里不应出现 `admin` / `user` 之外的演示员工账号。若已误建，用超管在「用户管理」里删除或禁用。

3. **数据库不对公网开放**：Compose 里 `mysql` 没有 `ports`，只能被 `app` 通过内部网络访问，保持这样。

4. **`.env` 权限 600**，且不要进 Git（`.gitignore` 已忽略）。

### 3.6 反向代理与 HTTPS

两种做法，任选其一。

#### 方式一：用内置 Nginx（默认，只出 HTTP）

```bash
docker compose up -d
```

nginx 默认随 compose 一起启动，占用宿主机 3000，访问 `http://<服务器IP>:3000`（地址与以前 app 直连时一样）。
适合前面还有一层云负载均衡做 TLS 终止的场景。`deploy/nginx.conf` 已处理好三件容易漏的事：
`proxy_buffering off`（否则 SSE/流式渲染失效）、`client_max_body_size 20m`（否则上传报 413 且应用日志无记录）、
`X-Forwarded-*`（否则来源 IP 全是容器地址，限流与审计失效）。

> 从旧版本升级时若你之前手动给 app 加过 `ports: '3000:3000'`，务必先删掉再 `up`，
> 否则会和 nginx 的 `3000:80` 抢宿主机 3000 端口，导致 compose 起不来。
> 想临时直连 app 排障，用 `127.0.0.1:3001:3000` 避开对外端口。

#### 方式二：宿主机 Nginx + certbot（正式环境）

正式环境（域名 + HTTPS）走这套，完整步骤见下面的 3.7 节。它用 `compose.prod.yaml`
覆盖端口配置，让 app 只绑 `127.0.0.1:3000`、容器 nginx 不启动，避免双层代理。

### 3.7 正式环境（域名 + HTTPS）

测试环境用 3000 端口 + 内置 nginx（上面的方式一），正式环境用标准 80/443 + 域名 + 证书自动续期。
两套配置互不干扰：

| 环境 | 启动命令 | 对外入口 | TLS |
| --- | --- | --- | --- |
| 测试 | `docker compose up -d` | `<IP>:3000`（容器 nginx） | 无 |
| 正式 | `docker compose -f compose.yaml -f compose.prod.yaml up -d --build` | `https://域名`（宿主机 nginx） | certbot |

#### 1. 准备域名与目录

域名 A 记录指向服务器公网 IP，并放行 80/443（云安全组 + 系统防火墙）：

```bash
sudo ufw allow 22/tcp && sudo ufw allow 80,443/tcp && sudo ufw enable
sudo mkdir -p /var/www/certbot && sudo chmod 755 /var/www/certbot
```

#### 2. 装 Nginx 与 certbot

```bash
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
```

#### 3. 首次签发证书

把 `deploy/nginx.prod.conf` 复制到 `/etc/nginx/conf.d/nomi-admin.conf`，对示例域名
`admin.example.com` 做一次全局替换（配置里是 server_name ×2、证书路径 ×2，注释里那处一并换掉即可）。
**首次签发时先把 443 server 块整段注释掉**
——证书还不存在，nginx 起不来——只留 80 端口那块做 ACME 验证：

```bash
sudo nginx -t && sudo systemctl reload nginx
sudo certbot certonly --webroot -w /var/www/certbot -d 你的域名 \
  --deploy-hook "systemctl reload nginx"
```

签好后把 443 server 块恢复，再 reload：

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> 也可以直接用 `sudo certbot --nginx -d 域名` 让 certbot 全托管配置，但它生成的 443 块
> 不含本仓库配置里的安全响应头（HSTS / nosniff / X-Frame-Options），之后要手动补。
> 用上面的 `certonly` 方式最可控。

#### 4. 切到正式环境的容器编排

```bash
# 测试环境若在跑，先停掉它占用的 3000（容器 nginx）
docker compose down

# 覆盖文件生效：app 只绑 127.0.0.1:3000，容器 nginx 不启动
docker compose -f compose.yaml -f compose.prod.yaml up -d --build
```

#### 5. 验证

```bash
curl -I http://你的域名              # 应 301 到 https
curl -fsS https://你的域名/api/health
```

浏览器打开 `https://你的域名` 应落到登录页；在线用户 / 系统日志的「登录地点」应显示真实公网 IP。

#### 6. 证书自动续期

certbot 安装的 systemd timer 会每天检查续期，用下面命令确认配置无误：

```bash
sudo certbot renew --dry-run
```

`--deploy-hook` 已在签发时登记，续期后会自动 reload nginx，无需手工干预。

#### 7. 回退到测试环境

```bash
docker compose -f compose.yaml -f compose.prod.yaml down
docker compose up -d --build
```

宿主机 nginx 配置可以留着（80/443 不影响 3000 测试），也可以 `sudo systemctl stop nginx` 停掉。

#### 注意

- 别再套一层不传 `X-Forwarded-For` 的负载均衡，否则登录地点会显示那台 LB 的 IP。
- 首次上线若担心 HSTS 锁死，把配置里的 `max-age` 先调成 300 观察一周再改回一年。

### 3.8 开机自启与日志

容器已带 `restart: unless-stopped`，只需保证 Docker 本身开机启动：

```bash
sudo systemctl enable --now docker
```

日志默认由 Docker 的 json-file 驱动无限增长，建议在 `/etc/docker/daemon.json` 加轮转：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "20m", "max-file": "5" }
}
```

改完 `sudo systemctl restart docker`。日常查看：

```bash
docker compose logs -f --tail=200 app
docker stats --no-stream
```

## 4. 方案 B：裸机 Node + systemd

适合已有 MySQL、或不希望引入 Docker 的环境。**必须用 `pnpm build` 的产物，不要用 `pnpm generate`**（静态产物没有服务端接口）。

### 4.1 安装运行时

```bash
# Node 22（系统级安装，不要用 nvm —— systemd 找不到 nvm 的 node）
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs git
sudo corepack enable

node -v    # 需 >= 22.12.0
pnpm -v    # 应为 11.20.0
```

### 4.2 部署代码并构建

```bash
sudo useradd -r -s /usr/sbin/nologin nomi
sudo mkdir -p /srv/nomi-admin
sudo chown nomi:nomi /srv/nomi-admin

sudo -u nomi git clone <仓库地址> /srv/nomi-admin
cd /srv/nomi-admin
sudo -u nomi pnpm install --frozen-lockfile
sudo -u nomi pnpm build
```

构建产物在 `.output/`（自包含：服务端代码 + 静态资源 + 已打包依赖）。运行时**不需要** `node_modules`。

上传目录：

```bash
sudo -u nomi mkdir -p /srv/nomi-admin/data/uploads
```

### 4.3 环境变量文件

放 `/etc/nomi-admin.env`，只给 root 与 `nomi` 读：

```bash
sudo tee /etc/nomi-admin.env >/dev/null <<'EOF'
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=nomi_admin
MYSQL_PASSWORD=替换为实际密码
MYSQL_DATABASE=nomi_admin
MYSQL_POOL_SIZE=10
TOKEN_SECRET=替换为32字节随机串
INITIAL_ADMIN_PASSWORD=替换为16位以上强口令
SEED_DEMO_ACCOUNTS=0

NODE_ENV=production
EOF

sudo chown root:nomi /etc/nomi-admin.env
sudo chmod 640 /etc/nomi-admin.env
```

注意这是 systemd 的 `EnvironmentFile` 格式：**纯 `KEY=VALUE`，值不要加引号**，也不要写注释尾随在同一行。

数据库账号建议单独建，权限只落在业务库上：

```sql
CREATE DATABASE IF NOT EXISTS nomi_admin
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'nomi_admin'@'127.0.0.1' IDENTIFIED BY '上面的密码';
GRANT ALL PRIVILEGES ON nomi_admin.* TO 'nomi_admin'@'127.0.0.1';
FLUSH PRIVILEGES;
```

建库其实可以省掉（应用会自己建），但账号必须先有，且要有 `CREATE` 权限，否则建库那步失败。

## 6. 数据、备份与恢复

### 6.1 需要持久化的三样东西

| 数据 | Compose 位置 | 裸机位置 | 丢失后果 |
| --- | --- | --- | --- |
| 数据库 | 卷 `mysql_data` | MySQL 数据目录 | 账号、菜单、权限、公告全部消失 |
| 上传文件 | 卷 `uploads` → `/app/data/uploads` | `/srv/nomi-admin/data/uploads` | 站点 logo、公告配图 404 |
| 初始口令文件 | 卷 `app_data` → `/app/data` | `/srv/nomi-admin/data/initial-admin-password.txt` | 首启后就不重要了（改密后自动删） |

卷的实际名称带 compose 项目前缀（默认是目录名）：

```bash
docker volume ls | grep -E "mysql_data|uploads|app_data"
# 例如 nomi-admin-nuxt_mysql_data
```

`docker compose down -v` 会连卷一起删 —— 对生产执行前必须确认。

### 6.2 备份脚本

`/srv/nomi-admin/backup.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail
cd /srv/nomi-admin

STAMP=$(date +%F-%H%M)
# compose 项目名 = 目录名（转小写）；卷名 = 项目名_卷名
PROJECT=$(basename "$PWD" | tr '[:upper:]' '[:lower:]')
UPLOAD_VOLUME="${PROJECT}_uploads"
mkdir -p backups

# 数据库：--single-transaction 在 InnoDB 下不锁表，可在线备份
docker compose exec -T mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers --databases "$MYSQL_DATABASE"' \
  | gzip > "backups/db-$STAMP.sql.gz"

# 上传文件
docker run --rm \
  -v "${UPLOAD_VOLUME}:/data:ro" \
  -v "$PWD/backups:/backup" \
  alpine tar czf "/backup/uploads-$STAMP.tar.gz" -C /data .

# 保留 14 天
find backups -type f -name '*.gz' -mtime +14 -delete

echo "备份完成：backups/db-$STAMP.sql.gz / backups/uploads-$STAMP.tar.gz"
```

```bash
chmod +x backup.sh && ./backup.sh
```

每日 3:00 执行：

```bash
( crontab -l 2>/dev/null; echo "0 3 * * * /srv/nomi-admin/backup.sh >> /var/log/nomi-backup.log 2>&1" ) | crontab -
```

裸机方案把数据库那段换成 `mysqldump -u... -p...`，上传目录换成 `tar czf backups/uploads-...tar.gz -C data/uploads .` 即可。

**备份要落到机器之外**（对象存储、另一台机器）。同一台机器上的备份在磁盘故障时一起消失。

### 6.3 恢复

```bash
cd /srv/nomi-admin
UPLOAD_VOLUME="$(basename "$PWD" | tr '[:upper:]' '[:lower:]')_uploads"
docker volume ls | grep "$UPLOAD_VOLUME"   # 先确认卷名对得上

# 数据库
gunzip -c backups/db-2026-11-22-0300.sql.gz \
  | docker compose exec -T mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'

# 上传文件
docker run --rm \
  -v "$UPLOAD_VOLUME:/data" \
  -v "$PWD/backups:/backup" \
  alpine sh -c 'tar xzf /backup/uploads-2026-11-22-0300.tar.gz -C /data'

docker compose restart app
```

恢复后必须清掉浏览器里的旧登录态（`TOKEN_SECRET` 若也变了，所有 token 自动失效），并核对账号能否登录。

### 6.4 演练

上线后一周内至少做一次「恢复到临时目录/临时库」的演练。没验证过的备份等于没有备份。

## 7. 后续如何更新

### 7.1 数据库变更不需要手工执行 SQL

应用每次启动都会按固定顺序做一遍幂等操作（`server/database/init.ts` + `migrations.ts`）：

1. 库不存在 → `CREATE DATABASE`（utf8mb4 / utf8mb4_unicode_ci）
2. 旧表改名（`migrateLegacyTableNames`，仅在「旧表在、新表不在」时动手）
3. `CREATE TABLE IF NOT EXISTS` 建缺失的表
4. 空表灌种子（含语言词条、默认配置）
5. `runMigrations()` 执行增量迁移，用 `schema_migration` 表记账，已执行过的不会重复跑

所以你拉新版本后**不需要**手工跑 SQL，重启应用即可。但有两条硬约束：

- **迁移没有 down 脚本**。一旦新版本跑过迁移（比如删了字段），旧版本代码可能直接不兼容。因此**应用回滚必须配合数据库恢复**，见 7.3。
- **迁移失败会抛错**，库处于「半迁移」状态。半迁移比启动不了更难查，所以升级前必须先备份。

### 7.2 升级前必做

```bash
cd /srv/nomi-admin

# 1. 记录当前版本与镜像，便于回滚
git rev-parse --short HEAD
docker tag nomi-admin-nuxt:local "nomi-admin-nuxt:rollback-$(date +%Y%m%d-%H%M)" 2>/dev/null || true

# 2. 备份（必须）
./backup.sh

# 3. 看这次改动有没有数据库变更/破坏性变更
git fetch origin
git log --oneline HEAD..origin/main
git diff --stat HEAD..origin/main -- server/database/ nuxt.config.ts package.json

# 4. 拉代码（只快进，避免在服务器上产生合并提交）
git pull --ff-only
```

如果 `git diff` 里出现了 `server/database/schema.ts` 或 `migrations.ts`，把它当成「需要备份 + 需要验证数据」的信号，而不是普通前端改动。

### 7.3 Docker Compose 更新流程

```bash
cd /srv/nomi-admin

# 1. 备份 + 记录旧镜像（见 7.2）

# 2. 拉代码
git pull --ff-only

# 3. 依赖或代码有变化时重建镜像（依赖层有缓存，未变则很快）
docker compose build app

# 4. 只重启 app，MySQL 不动
docker compose up -d app

# 5. 观察启动过程：建表/迁移/种子日志，以及健康状态
docker compose logs -f --tail=100 app
docker compose ps
```

**关于停机时间**：单机 Compose 是「先停旧容器、再起新容器」，中断通常 3~10 秒，期间请求会失败。要真正零停机需要多副本 + 负载均衡（blue-green），当前编排没有做这件事，不在本文范围。

**关于 `.env` 改动**：改完 `docker compose up -d` 会重建容器使其生效。但 `MYSQL_PASSWORD` 对已存在的 `mysql_data` 卷无效（账号只在首次初始化时创建），改了会直接连不上，见 8 节。

**健康检查通过才算更新成功**：

```bash
curl -fsS http://127.0.0.1:3000/api/health
```

返回 `{"status":"ok",...}` 即可。健康检查只回答「进程是否活着」，不查数据库 —— 所以还要做 7.8 的冒烟验证。

**回滚**：

```bash
# 1. 把旧镜像重新指回 compose 使用的 tag
docker tag nomi-admin-nuxt:rollback-20261122-0300 nomi-admin-nuxt:local

# 2. 强制重建容器
docker compose up -d --force-recreate app

# 3. 如果新版本已经跑过不可逆的迁移 → 必须同时恢复数据库
gunzip -c backups/db-20261122-0300.sql.gz \
  | docker compose exec -T mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'
docker compose restart app
```

判断要不要恢复数据库：看 `git diff` 是否涉及 `server/database/`。纯前端/样式改动不必恢复；迁移改过结构就必须恢复。

### 7.4 裸机 Node 更新流程

```bash
cd /srv/nomi-admin

# 1. 备份数据库与上传目录
mysqldump -u nomi_admin -p --single-transaction --databases nomi_admin | gzip > backups/db-$(date +%F-%H%M).sql.gz
tar czf backups/uploads-$(date +%F-%H%M).tar.gz -C data/uploads .

# 2. 留一份旧产物，回滚时不必重新构建
rm -rf .output.bak && cp -a .output .output.bak

# 3. 拉代码并构建
sudo -u nomi git pull --ff-only
sudo -u nomi pnpm install --frozen-lockfile
sudo -u nomi pnpm build

# 4. 重启并观察
sudo systemctl restart nomi-admin
sudo journalctl -u nomi-admin -f --since "1 min ago"
curl -fsS http://127.0.0.1:3000/api/health
```

回滚：

```bash
sudo systemctl stop nomi-admin
rm -rf .output && mv .output.bak .output
sudo systemctl start nomi-admin
```

（若新版本已跑过迁移，同样需要先恢复数据库备份。）

### 7.5 只改配置的更新

不需要重新构建：

```bash
# Compose
vim .env && docker compose up -d app

# 裸机
sudo vim /etc/nomi-admin.env
sudo systemctl restart nomi-admin
```

`NITRO_PORT` / `NITRO_HOST` / `TOKEN_SECRET` / `INITIAL_ADMIN_PASSWORD` 都是运行时读取。注意 `INITIAL_ADMIN_PASSWORD` 只在空库那一次生效，库已有数据时改它没有任何作用。

### 7.6 依赖升级

在**本地或 CI** 升级，不要在服务器上直接 `pnpm up`：

```bash
pnpm up --latest
pnpm install
pnpm lint && pnpm lint:style && pnpm typecheck && pnpm test
pnpm build           # 构建通过再提交
git commit -am "chore: 升级依赖"
```

提交后按 7.3 流程发到服务器，并把 `pnpm-lock.yaml` 一起提交 —— 服务器和 CI 都用 `--frozen-lockfile`，lockfile 不一致会直接失败。

`pnpm up --latest` 会跨大版本升级（Nuxt、Element Plus、TypeScript 等），务必先看 release notes 并单独提交一次，出问题好单独回退。

### 7.7 Pages 演示站更新

push 到 `main` 即自动发布，无需其他操作。PR 只跑质量门禁、不发布。手动重发：Actions → `CI / GitHub Pages` → `Run workflow`。

注意 Pages 发布的是 `NUXT_PUBLIC_DEMO=1` 的静态产物，和生产站是两套东西，不要用它验证后端改动。

### 7.8 更新后验证清单

按顺序过一遍，全绿才算更新完成：

1. `curl -fsS http://127.0.0.1:3000/api/health` 返回 `status: ok`
2. `docker compose ps` / `systemctl status` 为 healthy / active
3. 日志里没有 `[db]` 报错、没有 `[security] 未能写入文件` 告警
4. 浏览器打开登录页，能正常拿到验证码/表单渲染（不是空白）
5. 用真实账号登录成功（验证 `TOKEN_SECRET` 一致、token 表可用）
6. 进入任一列表页，数据能加载（验证数据库连接与迁移结果）
7. 上传一张图片，能显示（验证 `uploads` 卷挂载与权限）
8. 手机尺寸下打开后台，布局不塌（后台走 SPA，注意 `ssr: false` 的路由不受服务端影响）
9. `curl -s http://127.0.0.1:3000/api/health | grep build` 与本次 `NUXT_BUILD_ID` 对得上（若配置了该变量）

想确认线上到底跑的哪个提交，把 `NUXT_BUILD_ID` 注入到环境变量里（Compose 的 `app.environment` 或 `/etc/nomi-admin.env`），值用短 SHA：

```bash
NUXT_BUILD_ID=$(git rev-parse --short HEAD)
```

健康检查会回显它的前 12 位。

## 8. 故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `docker compose up` 报<br>`请在 .env 里设置 TOKEN_SECRET` | `.env` 缺必填项 | 补 `TOKEN_SECRET` / `MYSQL_PASSWORD` / `MYSQL_ROOT_PASSWORD`，`chmod 600 .env` |
| 应用起来但一直 healthy 不了 | MySQL 未就绪，或 healthcheck 密码不对 | `docker compose logs mysql`；确认 healthcheck 用的是 `MYSQL_ROOT_PASSWORD` |
| 应用日志 `ER_ACCESS_DENIED_ERROR` | 改了 `MYSQL_PASSWORD` 但卷是旧的 | 卷首次初始化才建账号；进容器 `ALTER USER 'nomi'@'%' IDENTIFIED BY '...'`，或备份后删卷重建 |
| `ECONNREFUSED 127.0.0.1:3306`（容器内） | 用 `127.0.0.1` 连容器外的库 | 容器里必须写服务名 `mysql`，不能写回环地址 |
| 页面能开但一片空白，控制台 `_nuxt/*.js` 404 | `baseURL` 不对（Pages 子路径） | 检查 `NUXT_APP_BASE_URL`；Pages 项目页必须是 `/<repo>/` |
| Pages 上资源全 404 | 缺 `.nojekyll` | workflow 已自动创建；手工发布要自己 `touch .output/public/.nojekyll` |
| 上传图片报 413，应用日志无记录 | Nginx `client_max_body_size` 默认 1m | 调到 20m（或按业务）并 reload |
| 上传报 `EACCES` | 上传目录属主不是运行用户 | Compose 用命名卷（镜像里已 chown 1000）；裸机 `chown -R nomi:nomi data/uploads` |
| 上传成功但图片 404 | `NOMI_UPLOAD_DIR` 指向了未挂载的路径 | Compose 必须是 `/app/data/uploads`；裸机核对绝对路径 |
| 502 Bad Gateway | 应用没在监听，或 upstream 地址错 | `curl 127.0.0.1:3000/api/health`；容器方案 upstream 是 `app:3000`，宿主机方案是 `127.0.0.1:3000` |
| 首次登录提示必须改密（业务码 428） | 初始超管尚未改密，设计如此 | 先改密，其他接口才会放行 |
| 找不到初始口令 | 配了 `INITIAL_ADMIN_PASSWORD` 就不再写文件 | 用 `.env` 里那串；或查 `docker compose logs app \| grep security` 里的路径 |
| 所有用户突然被登出 | `TOKEN_SECRET` 变了 | 属预期行为，通知用户重新登录 |
| 容器被 OOM Kill（退出码 137） | `mem_limit: 512m` 偏小，或构建期内存不足 | 先看 `docker inspect` 的 OOMKilled；构建机给 2GB+；运行期按实际调到 768m~1g |
| `ERR_PNPM_IGNORED_BUILDS` | 新依赖带安装脚本，未在 `pnpm-workspace.yaml` 的 `allowBuilds` 里登记 | 按提示补一行 `包名: true/false`，不要用 `--ignore-scripts` 绕过 |
| `pnpm install --frozen-lockfile` 失败 | lockfile 与 `package.json` 不一致 | 本地 `pnpm install` 后提交 lockfile |
| 深链刷新 404（Pages） | 预渲染只覆盖固定路由 | workflow 已把 `200.html` 复制成 `404.html`；本地发布需手动做 |

排查顺序建议：**先看应用日志 → 再看反向代理日志 → 最后才怀疑代码**。绝大多数「页面打不开」都是代理或端口问题。
