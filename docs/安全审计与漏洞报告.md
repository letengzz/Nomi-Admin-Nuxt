## 二、严重漏洞

### CRIT-01 默认超级管理员弱口令，系统启动即自动创建

> ✅ **修复状态：已修复（2026-11-22）**
> 口令不再写死在源码/文档里：由 `INITIAL_ADMIN_PASSWORD` 指定或启动时随机生成，
> 且种子超管首次登录必须改密。改动清单、升级影响与实测记录见 **附录 E**。
> 下面保留原始发现，作为问题背景与复核依据。

**位置**

- `shared/constants/seed-data.ts:195-199`（种子账号明文口令）
- `server/database/seed.ts:220-224`（首次建表后 `hashPassword` 落库）
- `server/database/init.ts:1-12`（`ensureDatabase()` 在每个管理端接口入口执行，等于「开箱即建」）
- `README.md:279`、`docs/权限系统实现.md`（文档中公开写明「密码均为 123456」）

```ts
// shared/constants/seed-data.ts
export const SEED_ADMINS: readonly AdminSeed[] = [
  { id: 1, username: 'super', nickname: '超级管理员', password: '123456', departmentId: 1, roleIds: [1] },
  { id: 2, username: 'admin', nickname: '管理员',   password: '123456', departmentId: 2, roleIds: [2] },
  { id: 3, username: 'user',  nickname: '普通用户', password: '123456', departmentId: 8, roleIds: [3] },
];
```

**描述**

系统首次启动会自动建库、建表并灌入种子数据，其中包含 3 个固定账号，口令是 6 位纯数字 `123456`，且 **README 与设计文档中明文公开**。种子只在表为空时写入，但「表为空」在生产首次部署时必然成立 —— 也就是说任何一套新上线实例，都带一个口令公开、权限为 `*` 的超管账号。系统没有「首次登录强制改密」的机制，也没有在检测到默认口令时阻断。

`roleIds: [1]` 对应超管角色，`rules = '*'`，按 `server/utils/auth/rbac.ts:153` 的判定，`'*'` 直接穿透所有权限检查。

**复现（已实测）**

```bash
curl -s -X POST http://127.0.0.1:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"userName":"super","password":"123456"}'
```

返回：

```json
{
  "code": 200, "msg": "ok",
  "data": {
    "token": "zqhf7oYX…（已脱敏）",
    "refreshToken": "u-iJXN-…（已脱敏）",
    "expireTime": 1795584043,
    "role": "超级管理员",
    "userName": "super"
  }
}
```

用该 token 请求 `/api/admin/users/list`、`/api/admin/notices/add` 均正常返回（后者已被用于 HIGH-01 的验证）。

**影响**

未授权攻击者拿到超级管理员会话，可读写全部账号、角色、权限节点、系统配置，可导入导出用户数据，可发布公告（进而配合 HIGH-01 打全员），危害为**完全接管**。由于口令写在公开仓库文档里，这属于「已知凭据」而非「弱口令猜测」。

**修复建议**

1. **立即**：种子账号改为「首次启动随机生成口令 + 一次性打印到启动日志」，或改为部署时必须由环境变量 `NOMI_INIT_ADMIN_PASSWORD` 提供，缺省则拒绝启动（与 `compose.yaml` 里 `TOKEN_SECRET: ${TOKEN_SECRET:?...}` 的取舍保持一致）。
2. **立即**：给 `user` 表加 `must_change_password tinyint` 标记，默认口令账号首次登录强制跳改密页；服务端在每个接口校验该标记，只有改密与退出接口放行。
3. **短期**：README / 设计文档删除明文口令，改为「启动日志中查看一次性初始口令」。
4. **短期**：口令复杂度下限提到 12 位并禁止纯数字（与 MED-03 一并处理）。

### CRIT-02 找回密码验证码无投递通道 + 开发环境明文回传，可重置任意账号密码

> ✅ **修复状态：已修复（2026-11-22）**
>
> 验证码不再出现在任何 HTTP 响应里；改为经 SMTP 投递到账号绑定邮箱，未配置邮件服务时直接关闭自助找回（503）。验证码在服务端只存 `HMAC` 摘要，重置接口全线防枚举，新口令走强策略，两个接口都加了按 IP 的窗口限流。
> 改动清单与实测记录见 **附录 F**。

**位置**

- `server/api/auth/password-code.post.ts:36-52`（签发验证码，`import.meta.dev` 时把验证码写进响应）
- `server/utils/reset-codes.ts:1-20`（模块注释明确写着「演示环境没有邮件/短信网关」）
- `server/api/auth/password-reset.post.ts:46`（先判账号存在，再消费验证码）
- `nuxt.config.ts:200`（`devServer: { host: '0.0.0.0' }`）

**描述**

两个问题叠加成一条完整的接管链路：

1. **没有投递通道**：`issueResetCode()` 只在进程内 `Map` 里生成 6 位数字，没有任何邮件/短信发送逻辑。也就是说，任何部署形态下「真实用户」都收不到验证码 —— 功能本身不可用。
2. **开发环境把验证码直接回给调用方**：`devCode: import.meta.dev ? state.code : undefined`。只要实例以 `nuxt dev` 启动（本项目 `devServer.host` 又是 `0.0.0.0`，同网段可直接访问），**未认证的攻击者只要知道账号名，就能拿到该账号的重置验证码并改掉它的密码**。
3. `password-reset` 对「账号不存在」返回 `404 该账号不存在`，正好提供了账号名是否有效的判定（与 MED-02 合流）。

配合 CRIT-01 的 `super` 账号名（文档公开），这条链路在开发/演示环境里等于「直接改掉超管密码」。

**复现（已实测，用一次性测试账号，未触碰 super）**

```bash
# 1) 注册一个测试账号
curl -X POST /api/auth/register -d '{"userName":"sectest_24610","password":"Passw0rd!","agreement":true}'

# 2) 免投递直接拿码（响应里带 devCode）
curl -X POST /api/auth/password-code -d '{"account":"sectest_24610"}'
# → {"code":200,"data":{"expiresIn":300,"cooldown":60,"devCode":"378239"}}

# 3) 用该码重置密码
curl -X POST /api/auth/password-reset \
  -d '{"account":"sectest_24610","code":"378239","newPassword":"Hacked123!"}'
# → {"code":200,"msg":"ok"}

# 4) 新密码登录成功
curl -X POST /api/auth/login -d '{"userName":"sectest_24610","password":"Hacked123!"}'
# → {"code":200,"data":{"token":"t9ZVhbNV…","role":"普通用户"}}
```

（测试账号随后已通过 `/api/admin/users/del` 删除。）

**影响**

任意已知账号（含 `super`）可被改密接管；攻击者不需要任何前置凭据。同时「真实用户收不到验证码」使找回密码在正式环境中功能不可用，形成可用性与安全性的双重缺陷。

**修复建议**

1. **立即**：`devCode` 分支改为只在 `process.env.NODE_ENV !== 'production' && process.env.NOMI_ALLOW_DEV_CODE === '1'` 同时成立时返回，且启动时打印醒目警告；默认关闭。
2. **立即**：接入真实投递（SMTP 或短信网关），投递失败要回滚验证码并返回可诊断错误，而不是假装成功。
3. **短期**：`password-reset` 在账号不存在时返回与「验证码错误」**完全一致**的响应（同为 200 或同为同一业务码），消除枚举面。
4. **短期**：验证码改为「服务端存 `HMAC(code)` + 绑定账号 + 单次使用 + 5 分钟 TTL」并落到 Redis/MySQL，替代进程内 Map（同时解 MED-04）。
5. **短期**：`devServer.host` 改回默认（仅 127.0.0.1），需要真机调试时用命令行 `--host` 临时开启。

## 三、高危漏洞

### HIGH-01 公告富文本净化可绕过 → 存储型 XSS

**位置**

- `server/utils/notice-service.ts:119-136`（`sanitizeNoticeHtml`，黑名单正则）
- `server/utils/notice-service.ts:147`（`normalizeNoticeInput` 入库前调用净化）
- `app/pages/admin/notice/[id].vue:89-90`（`v-html="notice.content"` 直接渲染）

**描述**

`content` 是富文本 HTML，入库前用**黑名单正则**清洗，前端用 `v-html` 渲染。黑名单共有 4 条规则（去 `script/style/iframe/...` 标签、去 `on*=` 事件属性、把 `javascript:` 链接替换掉）。黑名单方式有两个稳定绕过：

1. **`<svg/onload=>`**：事件属性正则要求 `on` 前是**空白字符**（`\son[a-z]+`），而 `<svg/onload=...>` 中 `on` 前是 `/`，HTML 解析器仍会把它当作属性分隔符，浏览器照常执行。
2. **实体编码的 `javascript:`**：正则只匹配字面量 `javascript:`，不解析 HTML 实体；`href="javas&#99;ript:alert(1)"` 在浏览器里解码后就是 `javascript:`，点击即执行。

用项目里的实现逐条跑载荷，结果如下（`=>` 右边是净化后的输出）：

```
"<img src=x onerror=alert(1)>"                  => "<img src=x>"                                  ✅ 被拦
"<svg/onload=alert(document.domain)>"           => "<svg/onload=alert(document.domain)>"          ❌ 绕过
"<a href=\"javas&#99;ript:alert(1)\">x</a>"     => "<a href=\"javas&#99;ript:alert(1)\">x</a>"    ❌ 绕过
"<a href=\"javascript&#58;alert(1)\">x</a>"     => "<a href=\"javascript&#58;alert(1)\">x</a>"    ❌ 绕过
```

**复现（已实测，端到端）**

用 CRIT-01 拿到的超管 token 提交公告：

```bash
curl -X POST /api/admin/notices/add -H "batoken: <super token>" -H "Content-Type: application/json" -d '{
  "title":"SEC-POC-XSS","category":"notice",
  "content":"<p>正文</p><svg/onload=alert(document.domain)><a href=\"javas&#99;ript:alert(1)\">点我</a>",
  "publishTime":0,"isTop":0,"notifyMethod":"internal","notifyScope":"all","scopeIds":[],"status":1
}'
# → {"code":200,"data":{"id":15}}
```

`GET /api/notices/15` 返回的 `content` 与提交内容**逐字节一致**，载荷原样落库。前端 `notice/[id].vue` 用 `v-html` 渲染该字段，任何打开这条公告的用户（`notifyScope: all` 时为全员）都会执行脚本。（验证后该公告已删除。）

**影响**

- 一个只有「公告编辑」权限的中低权限账号，可以让**所有用户（含超管）**在自己的会话里执行任意脚本；
- 令牌存在 localStorage（见 MED-01），脚本可直接读取 `accessToken` / `refreshToken` 并外传，实现**权限提升到超管**；
- 可配合 XSS 伪造操作（改角色、重置他人密码），且审计日志记录的是受害者账号，追溯会指向错误的人。

**修复建议**

1. **立即**：不要用黑名单，改白名单。引入成熟净化库（`sanitize-html` 或 `DOMPurify` + `jsdom`）在服务端做白名单净化，只保留 `p/br/strong/em/ul/ol/li/a/img/table/...` 与 `href/src/style` 等有限属性，并强制 `href` 只允许 `http/https/mailto`。
2. **立即**：`<svg>`、`<math>`、`<template>` 等「可携带事件的非 HTML 命名空间标签」整体拒绝。
3. **短期**：展示层加第二道防线 —— 富文本渲染放到受限 `iframe`（`sandbox` 无 `allow-scripts`），或前端用 `DOMPurify` 再净化一次（纵深防御，不可替代服务端）。
4. **短期**：补 XSS 回归测试。现在的 `test/notice-service.spec.ts:122-142` 只覆盖 `onclick` 与字面量 `javascript:`，没覆盖 `svg/onload` 与实体编码；`test/__sec_probe.spec.ts` 写了载荷却**没有断言**，等于没测（见 LOW-10）。

| SheetJS ReDoS | GHSA-5pgg-2g8v-p4x9 / CVE-2024-22363 | `<0.20.2` | `>=0.20.2` |

它不是「只在构建期用到」的依赖 —— `import.post.ts` 让任何持有 `system/user/add` 权限的账号上传 Excel，服务端就在主进程里用漏洞版本解析。原型污染在 Node 服务端可导致对象原型被改写（例如污染 `Object.prototype` 影响后续 `if (obj.admin)` 这类判断）；ReDoS 可用一个构造过的单元格内容让正则回溯爆炸，单请求打满 CPU。

上传侧有 5MB 大小限制（`MAX_IMPORT_BYTES`），能压缩载荷规模但**不能消除**这两个漏洞。

**修复建议**

1. **立即**：升级到 `xlsx@0.20.3+`（npm 源上 0.19.x 之后官方改走自有 CDN，若 npm 上无新版，改用 `https://cdn.sheetjs.com/xlsx-0.20.x/xlsx-0.20.x.tgz` 作为依赖源，或在 `pnpm-workspace.yaml` 里用 `overrides` 指向 tarball）。
2. **短期**：解析放到 Worker / 子进程并加超时（例如 3s 强杀），避免单请求拖垮主进程。
3. **短期**：解析前校验文件魔数（`PK\x03\x04` for xlsx、`\xD0\xCF\x11\xE0` for xls），不只看扩展名。
4. **中期**：把导入做成「解析 → 落中间表 → 异步任务」，主请求只做排队，天然隔离 DoS。

### HIGH-03 登录缺少 IP 级限流与验证码，账号锁定可反用为拒绝服务

**位置**

- `server/utils/auth/session.ts:36-37`：`LOGIN_RETRY_LIMIT = 5`、`LOGIN_FAILURE_WINDOW = 24*3600`（写死，不读配置）
- `server/utils/auth/session.ts:176-195`：锁定判定与失败计数
- `server/api/auth/login.post.ts` / `login.post.ts:18-38`：请求体只读 `userName/password/departmentId/keepLogin`，**没有 captcha 字段**
- `server/utils/system-config.ts:138`：`captchaEnabled: true`（默认开，但无任何实现）
- `deploy/nginx.conf:1-9`：注释自己承认「少了压缩、缓存与限流三件事」
- `server/middleware/`：空目录，**没有任何全局限流中间件**；`grep -i "rate.?limit|throttle"` 在 `server/` 下零命中

**描述**

登录接口的安全模型只有「单账号失败 5 次锁定」，缺三样东西：

1. **没有按 IP / 按设备限流**。攻击者可以用同一个 IP 对 10 万个账号各试 1 次（口令喷洒），永远不会触发任何锁定，且服务端没有任何 429。
2. **验证码配置项是空壳**。`captchaEnabled: true` 会让登录页（`login-config` 接口）显示「已启用验证码」，但服务端登录流程**完全不校验**。这比不显示更糟：安全评审看到配置以为是开的，实际是关的。
3. **锁定机制可被反用**。锁定维度是「账号」，任何人只要知道 `super` 这个账号名（文档公开），连续发 5 个错密码就能把它锁 24 小时。攻击者可以对全部已知账号批量锁定，形成**登录拒绝服务**；解锁需要管理员改密或等 24 小时。

另外锁定窗口用的是 `last_login_time` 而不是独立的 `last_failure_time`：登录成功也会刷新这个字段（`session.ts:212`），语义上是混用的。

**实测**

```bash
# 连续错误口令，无任何 429 / 验证码挑战
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{http_code} " -X POST /api/auth/login \
    -H "Content-Type: application/json" -d '{"userName":"nobody_zzz","password":"x"}';
done
# → 200 200 200 200 200（业务码统一为 0，HTTP 恒 200）
```

且登录请求体中没有 `captcha` / `captchaId` 任何字段参与校验。

**修复建议**

1. **立即**：在 `server/middleware/` 加全局限流（按 IP + 路由桶，如登录 10 次/分钟、取码 5 次/小时），或用 Nitro 的 `rateLimiter` / Redis 令牌桶；Nginx 层再加一道 `limit_req`。
2. **立即**：要么真正实现验证码（服务端生成 + 一次性消费 + 与 IP 绑定），要么把 `captchaEnabled` 默认改为 `false` 并从前端隐藏，**不要让配置说谎**。
3. **短期**：锁定改为「账号 + IP」双维度，并加锁定上限与自动解锁时间；给锁定操作记 `locked` 日志（已有 behavior 类型，可直接用）。
4. **短期**：把 `LOGIN_RETRY_LIMIT` / 窗口 / `security.lockMinutes` 接到 `loadSystemConfig()`，消除代码与配置的双份真相（见 MED-03）。
5. **短期**：登录失败增加固定/指数退避延迟（如 `sleep(min(2^n, 5s))`），显著降低喷洒速率。

### HIGH-04 全站缺失安全响应头

**位置**

- `nuxt.config.ts`（无 `routeRules.headers`、无 `nitro.plugins` 设置安全头）
- `deploy/nginx.conf`（无 `add_header` 任何安全头）
- `server/middleware/`（空）

**实测**

```bash
curl -s -D - -o /dev/null http://127.0.0.1:3000/login
```

```
HTTP/1.1 200 OK
x-robots-tag: noindex, nofollow
set-cookie: i18n_redirected=zh; Path=/; SameSite=Lax
content-type: text/html;charset=utf-8
x-powered-by: Nuxt
```

`/admin`、`/api/health` 同样没有。缺的头：

| 头 | 缺失后果 |
| --- | --- |
| `Content-Security-Policy` | 无法缓解 XSS（HIGH-01 直接受益）；`unsafe-inline` 内联脚本无约束 |
| `Strict-Transport-Security` | HTTPS 部署后仍可被降级/中间人 |
| `X-Frame-Options` / `frame-ancestors` | 后台可被 iframe 嵌套 → 点击劫持（诱导管理员点「删除角色」） |
| `Referrer-Policy` | 后台 URL（含 id、关键词）随外链泄漏 |
| `Permissions-Policy` | 摄像头/麦克风/定位未被禁用 |
| `X-Content-Type-Options` | 仅 `/api/site-assets/*` 单独设了 `nosniff`，其余响应没有 |

值得注意：本项目**并非完全没有这些头的代码** —— Nuxt 开发模式的错误页会临时带上 `content-security-policy` / `x-frame-options: DENY`（来自 `node_modules` 里的 dev 错误处理器），生产正常响应则完全没有。也就是说「测试环境看着有、线上其实没有」，容易误判。

**修复建议**

1. **立即**：在 `nuxt.config.ts` 的 `routeRules` 里给 `/**` 统一加头（Nitro 支持 `headers`）：

```ts
routeRules: {
  '/**': {
    headers: {
      'X-Frame-Options': 'DENY',
      'X-Content-Type-Options': 'nosniff',
      'Referrer-Policy': 'strict-origin-when-cross-origin',
      'Permissions-Policy': 'camera=(), microphone=(), geolocation=()',
      'Strict-Transport-Security': 'max-age=31536000; includeSubDomains',
    },
  },
}
```

2. **短期**：CSP 从 `Content-Security-Policy-Report-Only` 起步，先观察再收紧；后台（`/admin/**`，已是 SPA）可以更严：`default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`。注意项目在 `<head>` 里内联了 `THEME_BOOTSTRAP_SCRIPT`，收紧 `script-src` 时需改为 nonce 或 hash。
3. **短期**：`nginx.conf` 用 `add_header ... always` 兜一层（`always` 关键字能覆盖 4xx/5xx）。
4. **短期**：去掉 `x-powered-by: Nuxt`（`nitro: { routeRules }` 或 nginx `proxy_hide_header`）。

## 四、中危漏洞

### MED-01 令牌存 localStorage，access 3 天 / refresh 30 天且可无限续期

- 位置：`app/stores/user.ts:111`（`usePersistedState('user', ...)`）、`app/utils/request.ts:83`（`headers.batoken = user.accessToken`）、`server/utils/auth/token.ts:28-30`
- 描述：令牌持久化在 localStorage，任何 XSS（HIGH-01）都可直接读走；access TTL 3 天是「长效 bearer」，泄露窗口很长；refresh 30 天且**每次轮换重新发 30 天**（`rotateByRefreshToken` 调 `issueTokenPair` 用默认 TTL），等于**会话永不过期**（只要持续活跃），没有绝对会话上限。
- 影响：一次 XSS 或一次令牌泄露 = 长期接管，且没有「重新登录」这个自然止损点。
- 建议：
  1. access TTL 降到 15–30 分钟；refresh 保留 7–30 天，但加**绝对上限**（session 出生时间 + 例如 12 小时/7 天不可延长）；
  2. 令牌改用 `HttpOnly; Secure; SameSite=Strict` Cookie 承载，配合 CSRF token（可彻底消除 XSS 直接读 token 的问题）；
  3. 若要保留 localStorage，必须补齐 CSP（HIGH-04）；
  4. 敏感操作（改密、改角色、导出）增加「二次确认」，降低令牌泄露后的可利用面。

### MED-02 账号枚举（三处）

- 位置与差异：
  1. `session.ts:180-186`：账号存在且被锁定时返回「密码错误次数过多，账号已锁定」→ 说明账号**存在**；
  2. `register.post.ts:54`：已注册返回 `409 该账号已被注册`；
  3. `password-reset.post.ts:46`：账号不存在返回 `404 该账号不存在`（**实测**：`{"code":404,"msg":"该账号不存在"}`）。
- 影响：攻击者可批量确认有效账号名，把「口令喷洒」变成「定向爆破」，也为 CRIT-02 提供前置信息。
- 建议：锁定提示改为统一「账号或密码错误（若多次失败请稍后重试）」；注册改为「若账号可用将直接登录 / 已发送通知」这类无差异响应；重置统一返回同一业务码，仅内部日志区分。

### MED-03 安全策略配置与实现脱钩

- 位置：`server/utils/system-config.ts:127-141` 定义了一整套安全策略；实际实现里：
  - `security.passwordMinLength: 8` vs `password.ts:62` 的 `PASSWORD_MIN_LENGTH = 6`、`register.post.ts:23` 的 `PASSWORD_MIN = 6`；
  - `security.requireSpecialChar: true` / `allowPasswordUsername: false` / `passwordHistoryLimit: 3` / `passwordExpireDays: 90` —— **无任何代码读取**；
  - `security.loginFailLimit: 5` / `lockMinutes: 30` —— 被 `session.ts:36-37` 的硬编码 `5` / `24h` 覆盖；
  - `login.captchaEnabled: true` —— 无实现（HIGH-03）；
  - `storage.allowedExtensions` 含 `svg`，而 `site-assets.ts` 的 `IMAGE_MIME` 不含 `svg`（上传被拒），两边口径不一。
- 影响：管理员在「系统设置」里调安全策略**不生效**，形成「以为加固了、其实没有」的假象；这是审计中最常见的真实风险来源。
- 建议：写一个 `loadSecurityPolicy()` 作为唯一入口，所有相关校验（密码、锁定、验证码、上传扩展名）都从它取值；配置项要么接线、要么删除，不留空壳。补一条集成测试：改配置 → 行为随之改变。

### MED-04 验证码进程内存储，无淘汰机制

- 位置：`server/utils/reset-codes.ts:44`（`const codes = new Map()`）
- 问题：
  1. **内存型 DoS**：`issueResetCode` 对任意 `account` 字符串（3–20 位）直接 `set`，只有「再次访问同一账号」时才会被覆盖/删除。攻击者用随机账号名连续请求 `/api/auth/password-code`，Map 只增不减（受 60s 冷却限制的是同一账号，不同账号不受限），可缓慢耗尽内存。`compose.yaml:88` 给的 `mem_limit: 512m` 会先于 OOM 打满，进程被重启。
  2. **多实例失效**：负载均衡后两个实例的 Map 不共享，用户在 A 取码、到 B 提交就是「验证码不存在」。
  3. **重启即丢**：滚动更新期间全部重置流程中断。
  4. **接口未被统一包装**：`password-code.post.ts` 用的是裸 `defineEventHandler`，没有走 `definePublicHandler`，因此缺少 `ensureDatabase()` 与统一 `{code,msg,data}` 错误包，异常时返回结构与其它接口不一致（前端要写第二套解析）。
- 建议：落 Redis（`SETEX code:{account}` + `INCR attempts`）或 MySQL 表；Map 若保留必须加「最大条目 + LRU/TTL 定时清理」；接口统一用 `definePublicHandler` 包装。

### MED-05 上传只校验客户端 MIME 与扩展名

- 位置：`server/api/admin/settings/upload.post.ts:36-45`、`server/api/admin/notices/upload.post.ts:27-36`
- 现状（做得对的部分）：扩展名白名单、2MB 上限、落盘文件名由服务端重新生成（`${kind}-${Date.now()}-${uuid8}.${ext}`）、读取侧 `isSafeImageName` 正则挡住路径穿越、响应 `nosniff`。
- 缺口：`file.type?.startsWith('image/')` 是**客户端可控**的字段；`extname(file.filename)` 也是客户端给的。没有校验文件魔数，因此可以上传「扩展名 `.png`、内容其实是 HTML/SVG/JS」的文件。由于读取时 `Content-Type` 由扩展名决定且带 `nosniff`，当前**不能**直接形成 XSS 执行，但：
  - 会被当作图片嵌入页面 → 图片解析库（浏览器）攻击面；
  - 一旦将来有人把 `Content-Type` 改成 `image/svg+xml`（配置里 `allowedExtensions` 已经有 `svg`），立刻变成存储型 XSS。
- 建议：校验魔数（PNG `89 50 4E 47`、JPEG `FF D8 FF`、GIF `47 49 46 38`、WEBP `RIFF....WEBP`、ICO `00 00 01 00`）；用 `sharp`/`file-type` 二次识别并**以识别结果为准**重写扩展名；明确**不支持 SVG**并把 `storage.allowedExtensions` 里的 `svg` 删掉。

### MED-06 refresh token 轮换缺少重用检测

- 位置：`server/utils/auth/token.ts:234-283`（`rotateByRefreshToken`）
- 现状：轮换本身是对的（旧 refresh 用后即删）。
- 缺口：如果攻击者与正常用户同时持有同一个 refresh token（例如从 localStorage 拷走），攻击者先刷新会导致正常用户被踢；但由于**没有「会话族」概念，也没有重用检测**，系统不会把这次异常当作泄露信号，也不会主动撤销该 `session_id` 下的所有令牌并告警。OAuth 2.1 / OWASP 推荐的做法是：已使用过的 refresh token 再次出现 → 判定为泄露 → 撤销整个会话族。
- 建议：给 `token` 表加 `used_at` / `family_id`；轮换时若发现「旧 refresh 已被使用过」则删除同 `session_id` 全部令牌并写一条 `login_log`（behavior 可复用 `kick` 或新增 `reuse_detected`），前端提示重新登录。

### MED-07 compose 直接把应用端口暴露到宿主机

- 位置：`compose.yaml:53-54`（`ports: ['3000:3000']`）、`compose.yaml:98-99`（nginx 用 `profiles: proxy`，默认不启动）
- 描述：默认 `docker compose up` 只起 app + mysql，app 的 3000 直接绑定到宿主机所有网卡。此时：
  - 没有 TLS（登录口令、令牌明文过网）；
  - 没有 `limit_req`（HIGH-03 的暴力破解无任何拦阻）；
  - 没有 gzip_static / 缓存；
  - 绕过了注释里说的「少了压缩、缓存与限流三件事」的那层。
  Nginx 配置存在但**默认不启用**，容易让人误以为「已经反代了」。
- 建议：默认改为 `ports: ['127.0.0.1:3000:3000']`，并把 `nginx` 从 `profiles` 里提出来作为默认入口；或在 README/注释里明确「生产必须 `--profile proxy` 且只暴露 8080/443」。

### MED-08 受版本控制的 `.env.example` 含疑似凭据的孤立键

- 位置：`.env.example:15` → `MYSQL_IZLIXNQZ=eras_kq****`（完整值见该文件）
- 证据：`git show HEAD:.env.example` 中可见该行，即**已进入公开仓库历史**。
- 描述：这一行的键名不符合项目任何约定（`MYSQL_HOST/PORT/USER/PASSWORD/DATABASE/POOL_SIZE`），值是一串 20 位随机字符，位置紧跟在 `MYSQL_PASSWORD=` 之后，高度疑似「误粘贴的真实凭据」。它不参与任何变量替换，属于纯噪声，但会把一个可能有效的密钥永久留在 Git 历史里。
- 建议：删除该行；确认该值是否为真实口令/密钥，若是则**立即轮换**并考虑用 `git filter-repo` 清理历史；在 CI 加一道 secret 扫描（gitleaks / trufflehog）。

## 附录 F. CRIT-02 修复记录（2026-11-22）

**结论**：`/api/auth/password-code` 的响应体里**永远没有验证码**（没有 `devCode`、没有环境变量开关、没有构建期分支）。验证码只经两处离开服务端：配置好的 SMTP 投递到账号绑定邮箱，或开发环境下打印到服务端控制台。未配置邮件服务的部署**直接关闭**自助找回，而不是退回「把码显示在页面上」。

### F.1 攻击面收敛对照

| 旧行为 | 现在 | 为什么 |
| --- | --- | --- |
| `devCode: import.meta.dev ? state.code : undefined` | 响应体无 `code` 字段 | 一个「仅 dev」的分支，只要实例以 `nuxt dev` 起在 `0.0.0.0`，未认证者即可重置任意账号 |
| 无投递通道，任何人可对自己请求的账号名取码 | 验证码发到 `user.email` | 重置的前提从「知道账号名」变成「能收到该账号的邮件」 |
| 请求体可任选账号，无邮箱概念 | 收件地址取库里的绑定邮箱，不接受请求参数 | 否则接口就是「向任意收件人发任意内容」的垃圾邮件发射器 |
| 账号不存在 → `404 该账号不存在` | 先改为静默成功；**后续产品要求又改回明确提示**（404 / 441 / 440，见下方说明） | 静默成功让用户输入错误账号后对着「已发送」干等；最终按产品要求暴露未绑定类错误，靠 IP 限流兜住枚举风险 |
| 账号存在 + 码错 → 「验证码不正确」；账号不存在 → 「验证码不存在」 | 两者同一句话 | 否则「先申请码、再乱填一个」就能读出账号是否存在 |
| 新口令只要求 ≥6 位 | ≥10 位 + 四类字符取三 + 非常见口令 + 不含账号名 | 找回密码曾是绕过强口令策略的后门 |
| 只按账号 60 秒冷却 | 账号冷却（静默）+ 按 IP 窗口限流（429） | 「换账号名各发一次」挡不住，会把邮箱打成轰炸机 |
| 进程内明文验证码 | 只存 `HMAC-SHA256(账号+码, 进程随机密钥)`，`timingSafeEqual` 比较 | 内存被读走 / 日志被打出来都换不出验证码；密钥重启即失效 |
| 发信失败无法感知（因为根本没发信） | 投递失败即作废该码并记日志 | 不能留一个「用户没收到、但确实能用」的码在表里 |

> **后续产品调整（同日）**：取码接口对三类账号错误改为明确提示 —— 登录名不存在 `404 accountNotFound`、邮箱未绑定用户 `441 emailNotFound`、账号未绑定邮箱 `440 emailNotBound`。防枚举在这里让位于「别让用户对着假的成功提示等一封永远不会来的信」；账号已停用与冷却期内仍回静默成功，按 IP 的 5 次/10 分钟限流保留。

### F.3 部署与运维

- **要开自助找回**：系统设置 → 邮件配置，填 `host / port / encryption / fromAddress / username / password` 并勾选启用。四要素缺任何一个都按「未配置」处理。
- **不开也能用**：借口的回执是 `503 当前未配置邮件服务，无法自助找回密码，请联系管理员重置` —— 这是**有意的**失败，不是 bug。管理员仍可在「用户管理 → 重置密码」处理，重置出的口令会强制下次登录改密。
- **开发环境**：没配 SMTP 时验证码打印在启动服务的终端里（`[password-reset] <账号> 的验证码：……（仅开发环境输出）`）。它永远不出网络。
- **多实例**：验证码表与限流计数都在进程内，`A` 实例发的码 `B` 实例验不过。**必须**换成 Redis（key = `reset:code:<账号>`，TTL 300，`INCR` 计次）；`reset-codes.ts` 顶部注释给了对应命令。
- **限流依赖可信代理**：`x-forwarded-for` 只有在 nginx 后面才可信。裸奔公网时它可被伪造，此时限流只是「提高成本」，不是硬约束。

### F.5 残留风险（本期未做）

- **验证码仍是 6 位数字**：配合 5 次/码 + 10 次/IP/10 分钟的限流，单账号被在线爆破的期望尝试量远低于 10⁻³ 量级，但把位数提到 8 位成本极低，可作为下一步。
- **`mobile` 字段未接入短信通道**：只实现了邮件。要支持「手机找回」需要短信网关，代码结构与 `mail.ts` 对称，但本次没有可用网关可测。
- **投递失败对用户不可见**：接口一律回「已发送」，SMTP 挂掉时用户只会觉得「没收到」。这是为了消除枚举与计时侧信道主动做的取舍，运维需要盯 `[password-reset] 验证码投递失败` 这条日志（建议接告警）。
- **`devServer.host: '0.0.0.0'`**（LOW-05）仍未改：它与本次修复叠加后不再能泄露验证码，但开发模式暴露源码与堆栈的问题照旧，另行处理。

## 附录 G. CRIT-02 修复后的回归缺陷：账号只认用户名，填邮箱静默不投递（2026-11-22）

**现象**：SMTP 配置正确、接口回 `200 已发送`，但邮箱里始终没有信。

**根因**：两个问题叠在一起，各自都「看起来没问题」：

1. `password-code` / `password-reset` 都用 `findAdminByUsername(account)` 查账号，只匹配 `user.username`；
2. 为了防枚举，账号不存在时**必须**返回与成功完全相同的响应。

于是「填邮箱当账号」这条最常见的用户行为，落到代码里就是「查不到 → 按防枚举回成功 → 什么都不发」，
界面上没有任何异常。防枚举把一次**输入错误**变成了**静默失败**。

**修复**：

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| 新增 `findAdminByAccount()` | `server/utils/auth/session.ts` | 匹配 `username` 或 `LOWER(email)`，用户名优先；两处接口同时改用它 |
| 账号格式校验 | `password-code.post.ts`、`app/utils/forget-password.ts` | 登录名或邮箱二选一；上限从 20 放宽到 100（对齐 `user.email varchar(100)`），新增文案 `rule.accountFormat` |
| 可观测性 | `password-code.post.ts` | 未投递时记录原因（账号不存在 / 已停用 / 未绑定邮箱 / 冷却期内），投递成功记录脱敏收件人 |
| 邮件配置自检 | `server/api/admin/settings/test-email.post.ts`（新增）、系统设置页 | 用**已保存**的配置发一封测试信；只接受收件人，SMTP 参数一律读库（避免变成任意发信代理）；5 分钟 5 封 |
| 文案 | `i18n/locales/{zh,en}.json` | 副标题与占位符改为「用户名或邮箱」；补 `email.testTo/testSend/testHint/testOk` |

### H.2 几个刻意的取舍

- **布局用 table + 内联样式**：邮件客户端没有 flex/grid，Outlook 走 Word 引擎，Gmail 会剥 `<style>`。
- **限宽挂在 `div` 上而不是 `table`**：`table` 同时写 `width:100%` 与 `max-width` 时，定宽算法会按 `max-content` 排版，手机上横向溢出（实测 390px 断点踩到了）。
- **主题里不放验证码**：它会在锁屏通知、收件箱列表里以明文出现。
- **邮件里不放任何链接**：找回密码不需要点击跳转，少一个「是不是钓鱼」的疑虑。
- **相对路径 logo 直接不输出**：邮件里拿不到站点的相对路径，宁可不显示也不给空图。
- **暗色模式**：`prefers-color-scheme` 下画布/卡片/验证码各有反色，验证码数字从 `#0f172a` 提到 `#6ee7b7`，否则深底深字等于看不见。
