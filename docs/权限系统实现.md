# 权限系统实现说明（Nuxt 4 + Nitro + MySQL）

> 设计依据：`docs/权限系统设计.md`（BuildAdmin v2.3.9 的逐行解析）。
> 本文只讲**本项目怎么落地**：哪些设计被原样保留、哪些换成了 Nuxt 的等价物、哪些刻意没做。

---

## 1. 一句话总览

菜单、页面、按钮、接口权限共用一棵树（`permission_rule`），**角色**（`role`）用 `rules` 字段引用节点 id；
每个管理端接口都经过 `defineAdminHandler(节点名, handler)` 鉴权；前端只拿「有权的那部分」
菜单与按钮名做显示，**不做任何安全判断**。

账号只有一张 `user` 表，**没有「类型」字段**：能不能进后台、进来看到什么，全看它挂的角色。
「普通用户」本身就是一个只含仪表盘 + 个人中心的角色。部门（`department`）只用于归档与筛选，
不参与任何鉴权判断 —— 这条边界是刻意的，见 §5.1。

```
浏览器                          Nitro                            MySQL
──────                          ─────                            ─────
login ──────────────► /api/auth/login ──► user + user_role
                      签发 access/refresh ─► token（只存 HMAC 摘要）
进入 /admin ─────────► /api/admin/init ──► role.rules → permission_rule
  菜单 / authNode ◄──── 树 + path→动作表
按钮 v-auth/auth() ──► 只控制显示
任意写接口 ──────────► defineAdminHandler
                        ① ensureDatabase（建库建表，幂等）
                        ② token → 账号（303/409）
                        ③ check(节点名)（401）
                        ④ 业务 → operation_log
```

## 3. 数据库：没库建库、没表建表

启动顺序（`server/database/init.ts`）：

1. 用**不带 database** 的连接执行 `SELECT SCHEMA_NAME ...`，不存在则
   `CREATE DATABASE IF NOT EXISTS`（`utf8mb4_unicode_ci`）；
2. 建连接池后**先做表改名**（`migrateLegacyTableNames`）：`admin*` → `user / role / user_role / permission_rule / operation_log`。
   必须抢在建表之前，否则会先建出空的新表、再改名就撞名；
3. 逐条执行 `SCHEMA_STATEMENTS`（全是 `CREATE TABLE IF NOT EXISTS`）；
4. 对空表灌种子（2 种语言、10 个部门、55 个菜单与权限节点、3 个角色、43 条系统配置、
   超级管理员与 2 个演示账号 + 8 个成员）；
5. 跑未执行的一次性迁移（`server/database/migrations.ts`，见下）；
6. 删除 `expire_time < now - 2 天` 的 token（**故意保留 2 天**：过期记录要能被读到，才能返回 409 让前端续期）。

触发点有两处，缺一不可：

- `server/plugins/database.ts`：Nitro 启动时执行，失败只打日志、不阻止应用启动
  （MySQL 比应用晚启动是常态，容器会一直重启反而看不到原因）；
- `ensureDatabase()` 在每个接口入口再试一次：失败会清掉缓存的 promise，下一次请求重新尝试。

幂等边界：**表已存在就不动；种子只在表为空时写**。这是「自动初始化」，不是「自动重置」。
系统配置同理：默认值只在 `system_config` 为空时整份落库，管理员把某个区块「恢复默认」清空后，
重启不会把默认行重新写回来 —— 读取时本来就会回落到 `DEFAULT_CONFIG`。

### 一次性迁移

`CREATE TABLE IF NOT EXISTS` 表达不了「给已有表加字段」「把节点换个父级」「删掉一列」，
所以另有一层具名迁移（`server/database/migrations.ts`），执行记录写进
`schema_migration` 表，**每个迁移只跑一次**：

| 迁移 | 做了什么 |
|---|---|
| `migrateLegacyTableNames`（建表前） | 旧表改名：`admin`→`user`、`admin_group`→`role`、`admin_group_access`→`user_role`、`admin_rule`→`permission_rule`、`admin_log`→`operation_log`；`uid`/`admin_id` 列改 `user_id`，`group_id` 列改 `role_id`，索引同步改名 |
| `add-user-type` | 历史的账号类型字段（`user_type`），已被 `drop-user-type` 回收 |
| `move-user-menu` | 账号菜单从「业务管理」搬到 `system` 下，改名 `system/user*`、`path=/admin/system/users` |
| `add-user-action-rules` | 补 `system/user/status`、`system/user/resetPwd` 两个按钮节点 |
| `grant-user-actions` | 只给「原本就能编辑用户」的角色补这两个节点，不给只读角色提权 |
| `seed-demo-users` | 一个成员都没有时灌演示成员（删光后不会复活） |
| `drop-admin-menu` | 删除 `system/admin*` 节点，并从所有角色的 `rules` 里回收这些 id |
| `2026-11-15-drop-user-type` | 删除 `user.user_type` 列：账号不再分类型，权限只看角色 |
| `2026-11-15-add-user-department` | `user` 加 `department_id` + 索引；建 `department` 表并灌 10 个部门 |
| `2026-11-15-rename-roles` | 「角色组」统一叫「角色」：`user_group`→`role`、`user_group_access`→`user_role`，`perm` 类节点名同步改 `system/role*` |
| `2026-11-15-add-department-menu` | 新增 `system/department` 菜单与 4 个按钮节点，挂到系统管理下 |
| `2026-11-15-open-operation-log` | 日志不再按人裁剪（详见 §5.3） |
| `2026-11-15-assign-default-role` | 没有角色的存量账号挂上「普通用户」，避免登录进来空白 |
| `2026-11-15-tidy-menu-weights` | 系统管理下的菜单顺序对齐：用户 → 部门 → 角色 → 节点 → 日志 → 设置 |
| `2026-11-15-add-role-code` | `role` 加 `code`（角色编码）；按名字给三个种子角色补 `super` / `admin` / `member` |
| `2026-11-15-add-language-menu` | 新增 `system/language` 菜单与 4 个按钮节点，给「能看用户列表」的角色补授权 |
| `2026-11-15-import-language-entries` | 把 `i18n/locales/*.json` 的 526 个词条、1052 条译文导入数据库（`INSERT IGNORE`，不覆盖人工修改） |

表改名天然幂等（源表在、目标表不在才动手），所以不进记账表；其余每个只跑一次。

顺序不能颠倒：全新库必须先写入 id 写死的种子账号，迁移里的自增数据才不会抢占 id。
迁移失败会直接让启动失败 —— 半迁移的库比启动不了更难查。
**改表名类的迁移不要依赖 dev 热更新**：热更新会先建新表导致新旧表并存，改完重启一次服务。

新增字段 / 搬节点时，请照着写一条新迁移，不要改历史迁移的 `name`。

### 表结构

| 表 | 关键字段 | 说明 |
|---|---|---|
| `user` | `username` 唯一、`department_id`、`password`（scrypt）、`status` = `enable/disable`、`login_failure`、`gender` | 单一账号表，**无类型字段**；登录锁定：连续 5 次失败且 24 小时内 → 锁定 |
| `department` | `pid`、`name`、`leader`、`phone`、`weigh`、`status` | 部门树；只用于归档/筛选/登录页选择，不参与鉴权 |
| `role` | `pid`、`name`、`code`、`rules`（`'*'` 或逗号串 id） | 权限载体；`'*'` = 超管哨兵；`code` 是代码引用的稳定标识（2-50 位小写字母/数字/`_`/`-`，非空时唯一） |
| `user_role` | `user_id`、`role_id`（唯一键） | 多对多，权限取并集 |
| `permission_rule` | `pid`、`type`（`menu_dir/menu/button`）、`name` 唯一、`path` | 菜单与权限同源 |
| `operation_log` | `user_id`、`url`、`title`、`data`、`ip` | 只记写操作，密码/token 字段被替换为 `******` |
| `token` | `token`（HMAC 摘要）、`type`、`user_id`、`expire_time` | access=`admin`，refresh=`admin_refresh` |
| `language` | `code` 唯一、`name`、`native_name`、`weigh`、`status` | 语言定义；`code` 与 `nuxt.config.ts` 的 `i18n.locales.code` 对齐，`zh` 是默认语言（不可停用/删除） |
| `language_entry` | `key` 唯一（点分路径）、`module`、`remark` | 词条；`module` 取 key 的第一段，用于筛选 |
| `language_value` | `entry_id` + `lang_code` 唯一、`value` text | 译文按行存：新增语言不需要 ALTER TABLE，完成度由非空行数算出 |
| `system_config` | `section` + `config_key` 唯一、`config_value` text | 按「区块 + 键」存配置；首次启动把 `DEFAULT_CONFIG` 整份落库，**没写过的键回落到默认值**，恢复默认 = 删该区块的行 |
| `schema_migration` | `name` 主键、`applied_time` | 一次性迁移记账本 |

> 表名与功能对齐：账号表 `user`（不再叫 `admin`，因为它同时存所有成员）、权限载体叫 `role`
> （页面就叫「角色管理」）、日志表叫 `operation_log`。改名全部由迁移完成，代码里已无旧名。

## 4. 鉴权链路

### 4.1 接口侧

```ts
// server/api/admin/roles/add.post.ts
export default defineAdminHandler('system/role/add', async (event, context) => {
  // context.admin / context.roles / context.ruleIds / context.isSuper
  return ok({ id });
});
```

`defineAdminHandler` 依次做：

| 步骤 | 失败返回 |
|---|---|
| `ensureDatabase()` | `code=0`，msg 指出是「MySQL 没起」还是「账号密码错」 |
| `resolveAdmin(event)`：读 `batoken` / `ba-token` / `Authorization: Bearer` | 无 token / 无效 / 被禁用 → `303`；过期 → `409` |
| `check(context, node)`；超管直接通过 | `401` |
| 执行业务 | 抛 `ApiError` → `code=0`；未知异常 → `code=0`（生产不回内部细节） |
| 非 GET 请求写 `operation_log` | 写日志失败只告警，不影响响应 |

业务码（`server/utils/http.ts`）：`200` 成功 / `0` 失败 / `303` 未登录 / `409` 过期 / `401` 无权限。
**HTTP 恒为 200**，前端只看 `body.code`。

### 4.2 双 token 与 409 续期

| 项 | 值 | 位置 |
|---|---|---|
| access TTL | 3 天 | `ACCESS_TOKEN_TTL` |
| refresh TTL | 30 天 | `REFRESH_TOKEN_TTL` |
| 存储 | `HMAC-SHA256(明文, TOKEN_SECRET)` | `digestToken()` |
| 续期 | `POST /api/admin/refresh-token`，**用完即轮换** | `rotateByRefreshToken()` |

客户端（`app/utils/request.ts`）收到 409 时：并发请求共用同一个续期 promise → 换到新 token →
**重放原请求一次**（`retried` 标记防死循环）→ 续期失败则清登录态回登录页。

比文档更严格的一处：refresh token 的 `type` 是 `admin_refresh`，不能当 access token 用。

## 5. 权限标识与命名约定

- `permission_rule.name`：接口验权与前端按钮权限的唯一标识，大小写不敏感，全库唯一；
- `permission_rule.path`：前端路由；`menu_dir` 用 `#group-*` 占位；
- 命名的实际用法（种子数据）：

| 页面 | path | 菜单节点 | 按钮节点 |
|---|---|---|---|
| 用户管理 | `/admin/system/users` | `system/user` | `system/user/add`、`system/user/status`、`system/user/resetPwd` … |
| 部门管理 | `/admin/system/departments` | `system/department` | `system/department/add` … |
| 角色管理 | `/admin/system/roles` | `system/role` | `system/role/add` … |
| 菜单管理 | `/admin/system/rules` | `system/rule` | `system/rule/sortable` … |
| 操作日志 | `/admin/system/logs` | `system/log` | `system/log/index` |
| 语言管理 | `/admin/system/languages` | `system/language` | `system/language/index`、`add`、`edit`、`del` |

文档要求 `name === path`，本项目**不需要**：`/api/admin/init` 直接输出
`authNode: { '/admin/system/roles': ['index','add','edit','del'] }`，
由服务端把「节点名 → 动作名」的映射算好。这条隐式约定被换成了显式契约。

### 5.1 角色是唯一的权限来源，部门只是归档

早期版本用 `user_type` 区分「管理员 / 普通用户」，两个类型走两套逻辑。现在删掉了这个字段：

| | 以前 | 现在 |
|---|---|---|
| 能否登录后台 | `user_type='admin'` 才能 | 有账号就能登录 |
| 进来看到什么 | 类型决定基础范围 | 角色决定（「普通用户」角色 = 只有仪表盘 + 个人中心） |
| 部门 | 无 | `department_id`，用于列表筛选、部门树、登录页选择 |

这样做的理由：类型和角色会打架（一个 `user_type='user'` 的账号挂了管理员角色，到底听谁的？）。
把「普通用户」降级成一个角色之后，登录进来是**空后台**而不是「你有账号但不许登录」——
后者对使用者更难解释，对实现也只是一道额外的闸。

部门**不决定功能权限**（菜单、按钮、接口仍只由角色决定），但决定**数据范围**：
非超级管理员只能看见本部门及所有子部门的内容，超管看全库。范围由服务端从
`context.admin.department_id` 推导，前端传的筛选参数只能收窄、不能扩大（详见 §7.1）。

### 5.2 账号管理（`server/utils/auth/user-service.ts`）

每个写操作先回答四个问题：

1. 目标存在吗？
2. 我看得见他吗 —— `assertUsersInScope`：非超管只能操作本部门及子部门的账号；
3. 我动得了他吗 —— `canOperateAccount`：对方角色的规则集合必须 ⊆ 我的规则；超管只有超管能动；
4. 会不会锁死系统 —— 不能删/停用自己，不能删除/降级/停用最后一个超管。

两个曾经踩过的坑，处理方式写死在代码里：

- **踢 token 只踢真正被改到的账号**：`deleteUsers` / `setUserStatus` 先按 id 查一遍账号类型与状态，
  再对筛出来的 id 清 token。直接按传入 id 清，前端传一个超管 id 就能把他踢下线；
- **角色不能为空**：新建与编辑都必须至少一个角色，否则账号登录进来是空白后台，
  看起来像「系统坏了」而不是「没授权」。

账号接口（全部要求对应节点）：

| 接口 | 节点 | 说明 |
|---|---|---|
| `GET /api/admin/users/list` | `system/user/index` | 分页 + 关键词（账号/昵称/邮箱/手机）+ 部门（含子部门）/ 角色 / 排除角色 / 排除自己 / 状态 / 性别筛选；**服务端先按部门范围裁剪**；返回 `total`（当前筛选）与 `allTotal`（可见范围内无筛选的总数） |
| `POST /api/admin/users/add` | `system/user/add` | 账号、密码、昵称、部门、角色、联系方式、性别 |
| `POST /api/admin/users/edit` | `system/user/edit` | 账号名不可改；密码留空不改 |
| `POST /api/admin/users/status` | `system/user/status` | 批量启用/停用，停用即踢 token |
| `POST /api/admin/users/reset-password` | `system/user/resetPwd` | 覆盖密码并踢 token |
| `POST /api/admin/users/del` | `system/user/del` | 支持 `ids` 批量；不能删自己/最后一个超管 |
| `GET /api/admin/languages/list` | `system/language/index` | 语言列表（含译文完成度）、模块列表、词条总数 |
| `GET /api/admin/languages/entries` | `system/language/index` | 词条分页 + 按 key / 任意译文搜索 + 模块筛选 |
| `POST /api/admin/languages/save` · `entry` | `system/language/edit` | 新增/编辑语言、词条与各语言译文；写操作统一挂 `edit` 节点 |
| `POST /api/admin/languages/del` · `entry-del` | `system/language/del` | 删语言（连译文）、删词条；默认语言禁止删除 |
| `GET /api/i18n/messages` | 免登录 | 只返回启用语言的非空译文，嵌套成可直接合并的消息对象 |

### 5.3 操作日志按部门范围可见

设计文档让非超管只看自己的日志，本项目改成**看本部门及子部门所有人的日志**（超管看全部）。

理由：日志的用途是团队级追溯（谁在什么时候改了谁的数据），只看自己等于把审计变成
个人操作记录，排障时毫无用处。入口权限由 `system/log/index` 卡住，数据边界由
`userScopeSubquery()` 用 `user_id IN (SELECT id FROM user WHERE …)` 落到 SQL 上 ——
日志表刻意不存 `department_id`，组织关系会变，审计记录不该跟着改口径。
按 `userId` 查某个账号的详情日志时，范围外的 id 也只会得到空结果。

### 5.4 部门管理

`department` 是一棵普通树（`pid` 指向父部门），服务端负责：

- **环检测**：`normalizeDepartmentInput` 拒绝把部门挂到自己的子孙下；
- **删除前置检查**：`pid = 0` 的**顶级部门不可删除**。根节点撑着整棵组织树，删掉会让所有
  子部门的 `pid` 指向不存在的上级，用户管理左侧树和登录页下拉都会把它们当成新的根。
  纯函数 `assertRootDepartmentDeletable(pid)` 在 `assertDepartmentDeletable` 第一行拦截，
  `departments/del` 把查到的整行（含 `pid`）传进去而不是只传 `id`，避免漏判；
  之后再查「有子部门 / 有成员」，错误文案直接给出原因。
  前端顶级行隐藏删除按钮（与超管角色的口径一致），「顶级部门」标签带
  `title="顶级部门不能删除"`，`remove()` 里还有一层不发请求的兜底；
- **成员计数**：列表带 `userCount`，用户管理左侧树与部门列表共用同一份数据；
- **停用语义**：停用后不能给新账号选这个部门，已有成员不受影响；
- **顶级部门状态锁**：`pid = 0` 的根节点一律启用，**状态不可更改**。停用它会让登录页的
  部门下拉（`listEnabledDepartments`）和用户管理左侧树把整棵组织树摘掉，子部门即便仍启用
  也不可达 —— 这比某个子部门停用严重得多。
  判定放在纯函数 `lockRootDepartmentStatus(requested, pid, existingPid?)`：同时看「提交后的
  `pid`」与「原来的 `pid`」，堵住「新建顶级就停用」「把子部门提升成顶级时顺手停用」
  「把顶级改挂别处时顺手停用」三种绕法；明确提交 `status=0` 时抛 `顶级部门不能停用`，
  其余情况锁成 `1`。`departments/add` 与 `departments/edit` 都用它的返回值写库
  （不再直接写 `input.status`），所以绕过前端直接调接口也改不动。
  前端同口径：列表行开关对 `row.pid === 0` 置灰、编辑弹窗按
  「提交后的上级是顶级 / 编辑前本来是顶级」置灰，提交时再强制 `status=1`；
  子部门照常启停用，普通编辑（改名、负责人、排序）不受影响。

部门接口：`GET /api/admin/departments/list`、`add`、`edit`、`del`，节点 `system/department/*`。
`list` 按当前登录人的部门范围返回扁平表（`userCount` 也只统计范围内的人），
前端把父级不在结果里的节点当根渲染，自然得到「以自己部门为根」的树；
`add` / `edit` / `del` 都先过 `assertDepartmentScopeAllows`：非超管不能建新的顶级部门、
不能编辑/删除范围外部门、不能把部门改挂到范围外。
登录页另有一个**免登录**的 `GET /api/auth/departments`，只返回 `id / pid / name`，
用于「选择部门」下拉自动填演示账号 —— 它不暴露负责人、电话等字段。

### 5.5 语言管理：把内置文案搬进数据库

`/admin/system/languages` 是主从版面：左侧语言（代码、完成度、启停用、编辑/删除），
右侧词条表（**词条键、模块、类型**、每种语言一列、编辑/删除），支持按 key / 任意译文
搜索、按模块与类型筛选、分页与新增词条。

**词条分两类**（`language_entry.type`）：

| 类型 | 来源 | 能改译文 | 能删 |
|---|---|---|---|
| 系统 `system` | 内置 `zh/en.json` 经种子导入 | ✅ | ❌ |
| 自定义 `custom` | 后台「新增词条」 | ✅ | ✅ |

系统词条是页面文案的兜底，删掉之后界面会自动回退到内置文案、列表里却少一条记录 ——
「删了却还在用」的状态没有意义，所以服务端在 `deleteEntry` 里直接拒绝，前端把删除按钮
置灰并给出提示。类型筛选下拉的分组条数由 `GET /api/admin/languages/list` 的
`entryCounts` 一并返回，切筛选不用再发一次统计查询。

**译文为什么是列表**：语言可以随时新增，所以词条弹窗里「译文」是一份可增删的行
（语言下拉 + 内容），而不是按 zh/en 写死的固定输入框。打开时先把启用语言铺好、停用但
已有译文的也带上（不藏数据），「添加语言」按剩余语言追加一行，选过的语言不会在别的行
重复出现。

**数据从哪来**：`scripts/sync-language-seed.mjs` 把 `i18n/locales/zh.json` 与 `en.json`
扁平化成 `server/database/language-seed.ts`（当前 542 个词条）。迁移
`2026-11-15-import-language-entries` 用 `INSERT IGNORE` 写入 `language_entry` 与
`language_value`，所以：
- 全新库首次启动就有全部现有文案；
- 已有库重启后只补新增的 key，**管理员改过的译文不会被覆盖**；
- 以后改了 JSON，跑 `pnpm lang:sync` 重新生成种子文件即可。

类型列由 `2026-11-15-add-language-entry-type` 补上：先按种子表把 key 标成 `system`，
其余一律 `custom`；`2026-11-15-sync-language-seed-entries` 负责把后来新增的文案补成词条
（种子表增长时不必手工干预）。两者都以种子表为唯一事实来源，重复执行不会漂。

为什么是编译期生成的 TS 常量而不是运行时读 JSON：生产构建的 `.output` 里不一定还有
`i18n` 目录，运行时读文件不可靠。

**改了怎么生效**：`GET /api/i18n/messages`（免登录，登录页也要用多语言）只返回
「启用语言 + 非空译文」，`app/plugins/i18n-runtime.ts` 在 `onNuxtReady` 后用
`mergeLocaleMessage` 深度合并进 vue-i18n。语言管理页保存时派发
`nomi:i18n-updated`，插件重新拉一次，文案立即生效，不必刷新整页。
静态 `zh/en.json` 始终是兜底：库里删掉/清空某个 key，页面回退到内置文案，
不会出现裸露的 `auth.user.title`。

**约束**：默认语言 `zh`（与 `nuxt.config.ts` 的 `defaultLocale` 一致）不能停用或删除；
编辑语言时 `code` 不可改（译文表按它引用）；新增语言只写语言定义，
要能在界面切换还得在 `nuxt.config.ts` 的 `i18n.locales` 里注册（页面上有提示）。

## 6. 前端权限

```ts
const { auth, can, isSuper } = usePermission();

auth('add')                    // 当前页面是否有 add 动作
auth('del', '/admin/system/rules')
can('system/role/add')         // 完整节点名
```

```vue
<ElButton v-if="auth('add')">新增</ElButton>
<ElButton v-auth="'del'">删除</ElButton>
```

三层协作：

1. **菜单**：`/api/admin/init` 下发的树直接进 `menu` store，侧边栏、面包屑、标签页跟着变；
2. **页面**：`auth.global.ts` 里「静态菜单表中存在、但不在有权路径里」→ 回我的首页
   （只是体验，不是安全边界）；
3. **按钮**：`authNode` 是服务端按授权裁剪过的，没权限的按钮连名字都拿不到。

登出：先 `POST /api/admin/logout` 删 token 记录，再清 permission / user / menu 三个 store。

### 6.1 角色管理：左列表 / 右详情

`/admin/system/roles` 是主从版面，不再是「一张大表 + 弹窗里塞授权树」：

- 左栏**上方**是「搜索角色 / 编码」（名称与编码都匹配，大小写不敏感）+「新建角色」，
  **下方**是角色列表（显示编码、成员数、权限节点数），点一行即切换右侧；
- 右栏上方是选中角色的名称、编码、成员数与启停用/编辑/删除，下方两个页签：
  - **功能权限**：`permission_rule` 全树 + 复选框，勾选后点「保存权限」；
    超管角色是 `'*'` 哨兵，这里只提示「拥有全部权限」，不给改；
    它也不能被停用或删除 —— 停用会让所有超管同瞬间失去权限，连改回来的接口都进不去。
    `roles/edit` 会拒绝 `status=0` 并在写库时强制 `status=1`，`roles/del` 直接拒绝；
    前端列表头部开关、编辑弹窗里的状态开关都对超管角色置灰，提交时再强制一次 `status=1`；
  - **角色用户**：`GET /api/admin/users/list?roleId=…&keyword=…` 的账号表 + 搜索 + 分页，
    顶部「分配用户」/「取消分配」两个批量按钮。
    过滤用 `id IN (SELECT user_id FROM user_role …)` 而不是 JOIN，避免一个账号挂多个角色时
    在 COUNT 里被算两次；候选列表反向用 `excludeRoleId` + `excludeSelf`（当前登录账号不允许
    被自己批量加减角色，列出来只会让人白选）。
    写操作走 `POST /api/admin/roles/users`（`{id, action:'add'|'remove', userIds}`，
    挂在 `system/role/edit` 节点下）：只改 `user_role` 的一行，不动账号资料；
    改完踢掉受影响账号的 token，让前端权限 store 重新加载。

**超管角色的成员下限**：`rules='*'` 的角色至少保留 1 个成员。只剩 1 人时，
「角色用户」页签的「取消分配」按钮置灰并显示说明，`confirmUnassign` 里再兜一层；
服务端 `assertSuperRoleCanRemove(isSuperRole, memberCount)` 是硬校验
（`changeRoleUsers` 在 remove 前用 `countRoleMembers` 查实时人数），
之后还有原有的「不能移除最后一个超级管理员」按账号维度的兜底。
判超管角色只看 `rules` 哨兵，不再叠加 `status`（该角色已不可停用）。

新建/编辑弹窗只管基本信息（名称、编码、上级、状态），**权限统一在右侧树里保存**；
所以编辑资料时会把已有 `rules` 原样带回，避免「改个名字顺手清空授权」。
编码在 `normalizeRoleCode` 里统一小写、格式校验，在 `assertRoleCodeAvailable` 里查重
（编辑时排除自己）；空编码允许多个角色占位，不参与唯一性判断。

### 6.2 列表页的滚动约定

系统管理下的页面**整页不滚动**，数据在表体内滚动：

- 页面 `definePageMeta({ layout: 'page-fill' })`，`.page-content` 铺满剩余高度；
- `useFillTable()` 用 `useElementSize` 量容器高度，算出表体像素高度交给 `ElTable` 的 `height`
  （Element Plus 只有拿到像素高度才会开表体滚动）；窗口高度 ≤ 800px 时返回 `undefined`，
  退化成自然高度，避免小屏上表体只剩两行。

### 6.3 用户管理页的版面

左侧是部门树（顶部「搜索部门名称」，`filter-node-method` 本地过滤），右侧是列表：

- 列表**不显示 ID**，第一列是「序号」（`(page - 1) * pageSize + index + 1`）；
- **序号、昵称、操作三列固定**（`fixed="left"` / `fixed="right"`），其余列横向滚动；
- 状态列统一用 `ElSwitch`：`inline-prompt` 显示「启用 / 停用」，
  停用色用 CSS 变量 `--el-switch-off-color: var(--el-color-danger)` 设置。
  **不要用 `inactive-color` 属性**：Element Plus 2.14 已移除该属性，写了会静默失效
  （停用显示成灰色）；
- 操作列只平铺「详情 / 修改 / 重置密码」三个高频动作，其余「分配角色 / 分配部门 / 删除」
  收进 `ElDropdown` 的**三个圆点**菜单（删除带分隔线、自己那一行不显示删除）；
  操作列宽从 284 收到 220，避免按钮换行；
- 「分配部门」与「分配角色」一样走 `POST /api/admin/users/edit`，但只改
  `departmentId` / `roles`，其余字段原样回传，避免顺手清空资料；
- 工具栏筛选是「关键词 + 状态 + 性别 + 搜索 / 重置」，`gender` 只认
  `unknown / male / female`（服务端 `GENDERS` 白名单，非法值按「不限」处理），
  重置会同时清空关键词、状态、性别、部门与部门搜索词。
  搜索/重置两个按钮包在 `.toolbar-actions` 里：Element Plus 给相邻按钮默认加了
  `margin-left: 12px`，会和 flex 的 `gap` 叠成 22px，工具栏内统一清掉，只留 6px；
- **左侧树的数字是组织统计，不是筛选结果**：
  - 根节点 = `listUsers` 返回的 `allTotal`（`SELECT COUNT(*) FROM user WHERE department_id IN (可见部门)`），
    固定显示**当前登录人可见范围内**的账号数，切部门 / 搜索 / 选状态时都不变化；
    非超管文案改成「本部门及下级部门」并附一行范围提示，超管仍是「全部部门」；
  - 部门节点 = 自己与所有子部门的成员数之和（`buildDeptTree` 里递归累加接口给的
    `userCount`），和「点部门按含子部门筛选」的口径一致；
  - 当前筛选命中多少条由列表分页的 `total` 表达，两者各司其职。
  `listUsers` 用 `Promise.all` 并行跑「筛选 COUNT / 可见范围 COUNT / 当前页」三个查询，
  多一个 COUNT 不额外增加往返；
- 最近登录写全年月日时分秒；详情抽屉里时间与 IP 分两行。

## 7. 数据权限（行级）

### 7.1 部门数据范围（已接线）

**规则**：超管（`rules='*'`）看全库；其他账号只看「自己所属部门 + 所有子部门」；
没有分配部门的账号只看自己（避免「无部门」变成看全部的后门）。
范围只由服务端从 `AdminContext.admin.department_id` 推导，`/api/admin/init` 下发的
`departmentId` 仅供 UI 提示与表单默认值，**不是安全边界**。

`server/utils/auth/department-scope.ts` 是全项目唯一真源：

| 函数 | 作用 |
|---|---|
| `collectDepartmentIds` | 内存广度优先取部门子树，带 `seen` 防脏数据成环 |
| `buildDepartmentScope` / `resolveDepartmentScope` | 纯函数推导 / 连库解析成 `{ departmentIds, selfId }`；超管为 `null` |
| `userScopeCondition` | `user` 表条件：`department_id IN (?) OR id = ?`（自己永远可见） |
| `departmentScopeCondition` | 只按部门的条件，用于统计数字与树节点人数对齐 |
| `userScopeSubquery` | 只有 `user_id` 的表用 `IN (SELECT id FROM user WHERE …)` 裁剪 |
| `assertDepartmentScopeAllows` | 部门写操作护栏（纯函数，可单测） |

**读接口**：`users/list`（列表、`total` 与 `allTotal`）、`departments/list`（部门与直属人数）、
`roles/list`（成员数）、`logs/list`（操作人范围）、角色用户列表与「分配用户」候选列表
（复用 `users/list`，自动生效）。前端传 `departmentId` 只能「在范围内再收窄」：
范围外的部门直接得到空列表，不会退化成看全部。

**写接口**：`assertUsersInScope` 挂在 `assertBatchOperable` / `loadTarget` 上，覆盖
编辑、删除、启停用、重置密码、角色成员分配；`resolveDepartment` 禁止非超管新建
「无部门」账号或把人调到范围外（唯一例外：本来就没部门的人改自己资料时保留 0，
否则连昵称都改不了）；部门 `add/edit/del` 用 `assertDepartmentScopeAllows` 挡住越界。删除角色时的「还有成员」检查仍走**全库**计数，避免误删还有范围外成员的角色。

**前端同步**：用户管理左树根节点非超管显示「本部门及下级部门」并附范围提示；
部门管理新建时默认挂到自己部门下（非超管不允许新建顶级部门）。

### 7.2 备用能力：权限集合白名单（未接线）

```ts
const ids = await getDataLimitAdminIds(context, 'allAuthAndOthers');
const scoped = dataLimitClause('user_id', ids);
if (scoped) {
  sql += ` AND ${scoped.clause}`;
  params.push(...scoped.params);
}
```

| 模式 | 含义 |
|---|---|
| `false` | 不限制 |
| `'personal'` | 只看自己 |
| `'allAuth'` | 权限 ⊆ 我的所有角色里的账号 |
| `'allAuthAndOthers'` | 权限**严格更少**的角色（真正的下级） |
| `'parent'` | 我的下级角色里的账号 |
| 数字 | 指定角色里的账号 |

`[]` = 不追加 where（超管或未开启）。层级由**权限集合包含关系**推导，
不看 `role.pid` —— 原因见设计文档 1.7：pid 可被改，权限不能凭空分配。

## 8. 防提权（服务端硬校验）

| 场景 | 校验位置 | 规则 |
|---|---|---|
| 给角色授权 | `sanitizeAssignRules` | 非超管只能分配自己拥有的节点 |
| 编辑/删除角色 | `assertRoleOperable` + `roles/edit` | 角色规则必须 ⊆ 我的规则；`'*'` 角色只有超管能动，且不可停用、不可删除、不可把 `'*'` 改成 id 串 |
| 新建/编辑账号并指定角色 | `resolveRoles` | 只能挂到自己能操作的角色；至少一个角色 |
| 角色批量加人 / 移除成员 | `changeRoleUsers` | 角色与目标账号都要可操作、不含自己；超管角色至少保留 1 个成员；不能把最后一个超管移出超管角色 |
| 编辑/删除/停用账号 | `canOperateAccount` | 对方权限不能高于我；不能删/停用自己；不能动最后一个超管 |
| 新建子节点 | `normalizeRuleInput` | 非超管只能在有权节点下建子节点，不能建顶级节点 |
| 删除节点 | `deleteRule` | 有子节点先拒绝；删除后从所有角色的 `rules` 里剔除该 id |

## 10. 没做的部分（与设计文档的差异）

| 文档里的能力 | 本项目 | 原因 |
|---|---|---|
| 会员端独立账号体系（前端注册/登录/会员权限） | 未实现 | 会员端登录未上线；`loadAdminContext` 的写法可以直接复制成会员侧上下文 |
| `check()` 的 `url` 模式（节点名带 `?k=v`） | 未实现 | 参数级条件用业务代码表达更直观；节点名里不允许 `?` |
| WEB 终端、安装器、CRUD 生成器 | 未实现 | 属于 BuildAdmin 特有入口，与本项目技术栈无关 |
| 规则/菜单缓存 | 未做 | 每次请求查 2 次（角色 + 规则），中后台规模下不值得引入缓存失效逻辑 |
| 数据库迁移框架 | 已引入轻量版 | `schema_migration` + 具名迁移，只能前进，没有回滚（`down`） |
| 敏感字段审计（`security_sensitive_data`） | 操作日志覆盖 | `operation_log` 已记录每次授权变更的请求体（`rules` 数组） |

## 11. 新增一个受控页面 / 接口

1. **加节点**：`/admin/system/rules` 新建菜单（`path=/admin/xxx`，`name=system/xxx`），
   再给它加按钮节点（`name=system/xxx/add` 等）。也可以在 `server/database/seed.ts`
   里加（只对全新安装生效）。
2. **加接口**：`server/api/admin/xxx/add.post.ts`，`defineAdminHandler('system/xxx/add', ...)`。
3. **加页面**：`app/pages/admin/xxx.vue`，模板里用 `auth('add')` 控按钮；
   想让它出现在侧边栏，必须建节点并在角色里勾选。
4. **授权**：`/admin/system/roles` 编辑对应角色，勾选新节点并保存。
5. **验证**：用无该节点的账号登录，接口返回 `code=401`，页面按钮不显示，手输 URL 会被守卫弹回首页。
