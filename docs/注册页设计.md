### 1.3 一句话数据流

```text
用户访问 /#/auth/register
  → beforeEach 守卫判定它是静态路由（匿名放行）
  → 渲染 register/index.vue
  → 复用 LoginLeftView / AuthTopBar / login/style.css 搭出外壳
  → 用户在 ElForm 里输入 → 失焦触发 async-validator 校验
  → 点「注册」→ formRef.validate() 全量校验
  → 通过 → loading=true → setTimeout(1000) 模拟请求
  → ElMessage.success('注册成功') → toLogin() 再 setTimeout(1000)
  → router.push({ name: 'Login' }) → 回到登录页
```

**注意最后三步**：整个过程**没有任何网络请求**，也没有写入任何 store；注册成功不会自动登录、不会保存 token、不会记录用户信息。这是理解本文第 17 章所有问题的钥匙。

## 2. 设计思路（为什么这样设计）

这一章回答的不是「代码写了什么」，而是「**为什么作者选择这样写**」。理解了这些取舍，第 4～9 章的每一行都会变得顺理成章。

### 2.1 核心取舍：三页共用一套「授权页外壳」

登录、注册、忘记密码是三个独立的路由，但它们在视觉上是**同一张页面的三次换芯**。作者没有把三页各自写一遍布局，而是抽出了三条共用资产：

| 共用资产 | 抽出方式 | 三页各自只写什么 |
| --- | --- | --- |
| 左侧 65vw 品牌区 | 抽成组件 `LoginLeftView` | 什么都不写（`<LoginLeftView />` 一行） |
| 右上工具条 | 抽成组件 `AuthTopBar` | 什么都不写（`<AuthTopBar />` 一行） |
| 右侧表单盒样式 | 抽成 `login/style.css`，各页 `@import` | 只写 `.form` 里的**表单内容** |

于是 `register/index.vue` 的 `<style>` 只有 3 行（L238–L240），而整页却拥有完整的 440×650 表单盒、标题排版、滑入动画。这个取舍的收益与代价：

| 收益 | 代价 / 风险 |
| --- | --- |
| 三页视觉天然一致，改一处三页同步 | CSS 放在 `login/` 目录下，注册页要写 `@import '../login/style.css'`，形成**跨目录反向依赖**：改登录页样式会静默影响注册页 |
| 注册页本体只有 240 行，心智负担低 | 表单盒高度 `650px` 是**为登录页（字段最多：账号下拉 + 2 输入 + 滑块 + 记住密码 + 按钮）**定的，注册页字段更少却也用这个高度，底部留白明显更多 |
| 新增认证页（如「双因素验证」）成本极低 | 共用组件无法按页面差异化 —— `LoginLeftView` 有 `hideContent?: boolean` prop 却**三页都没传**（第 8.11 节） |
| `scoped` + `@import` 让样式不污染全局 | `@reference` / `@apply` 依赖 Tailwind 4 的编译期处理，IDE 对 `@apply` 的智能提示较弱 |

> **设计判断**：这是一个典型的「**薄页面 + 厚共用资产**」结构。对于一套中后台模板来说完全正确 —— 认证页本来就不该有复杂业务，视觉一致性比灵活性更重要。第 19.9 节会给出「如果你想让注册页用不同插图/不同宽度」的改造方案。

### 2.2 为什么注册页没有滑块验证、没有演示账号、没有「记住密码」

把它和登录页并排看，差异非常刺眼：

| 登录页有 | 注册页没有 | 作者可能的意图 |
| --- | --- | --- |
| `ArtDragVerify` 滑块人机验证 | ❌ | 注册页是**演示态**（不发请求），没有服务端需要保护；滑块是纯前端校验，加了也只是装饰 |
| 角色下拉 + 三组演示账号自动填充 | ❌ | 演示账号是「让访客一键体验不同权限」的模板特性，注册场景不需要 |
| 「记住密码」复选框 | ❌ | 注册流程还没有可记住的凭证 |
| 「忘记密码」链接 | ❌ | 注册用户还没有密码可忘 |
| `ElNotification` 成功通知（带系统名） | 只有 `ElMessage.success` | 注册成功反馈更轻，且随后立刻跳走 |
| 真实 `fetchLogin` 请求 + token 写入 | ❌ 只有 `setTimeout` | 模板定位：留出 `TODO` 让使用者接自己的后端 |

**但这里有一个真实的产品一致性问题**：登录页把「防机器人」做得那么显眼，注册页却完全没有，一旦接了真实注册接口，注册接口会成为**唯一没有人机校验的写入口**。第 19.4 节给出把滑块搬过来的做法；第 17.2 节说明为什么纯前端滑块并不能真的防机器人。

### 2.3 为什么表单盒是固定 `440px × 650px` 且绝对居中

`login/style.css` L5 写了：

```css
@apply absolute inset-0 w-[440px] h-[650px] py-[5px] m-auto overflow-hidden ...
```

四个属性共同完成「在右侧 `flex-1` 区域内，水平垂直都居中」：

| 属性 | 作用 | 为什么必须 |
| --- | --- | --- |
| `absolute` | 脱离文档流 | 让盒子不参与父级 flex 的高度计算，才能用 `inset-0` 撑满定位上下文 |
| `inset-0` | `top/right/bottom/left = 0` | 给绝对定位元素四个方向都设为 0，等于把它「拉」到与定位父级一样大 |
| `w-[440px] h-[650px]` | 同时指定宽高 | 有了固定宽高，`inset-0` 产生的「拉伸」被 `margin:auto` 接管为居中 |
| `m-auto` | 四边自动外边距 | **绝对定位 + 四方向 0 + 固定尺寸 + auto margin** 是 CSS 里经典的「无需 transform 的完美居中」 |
| `relative`（在父 `div.flex-1` 上） | 建立定位上下文 | 否则 `absolute` 会一路找到 `body`，盒子会相对整屏居中而不是右侧 35vw 居中 |

对比常见的 `top:50%; left:50%; transform:translate(-50%,-50%)`：作者这套写法**不占用 transform**，因此滑入动画 `slideInRight` 里的 `transform: translateX(30px) → translateX(0)` 可以直接叠加，不会和居中用的 transform 打架。这是很容易被忽略但很讲究的一点。

**高度预算表**（这是理解 `650px` 为什么够用的关键，也是第 17 章几个溢出问题的依据）：

| 区块 | 估算高度 | 来源 |
| --- | --- | --- |
| `.form` 上下 padding | 40 + 40 = 80px | `style.css` L11 `py-[40px]` |
| `.auth-right-wrap` 上下 padding | 5 + 5 = 10px | `style.css` L5 `py-[5px]` |
| 标题 `h3.title` | ≈ 43px | `text-4xl` = 36px，默认行高 1.2 |
| 副标题 `p.sub-title` | 10 + ≈ 20 = 30px | `mt-[10px]` + `text-sm` 14px |
| 表单上边距 | 30px | `mt-7.5` = 7.5 × 4px = 30px |
| 3 个输入框 `ElFormItem` | 3 × (40 + 18) = 174px | `.custom-height` 40px + Element Plus 默认 `margin-bottom: 18px` |
| 协议 `ElFormItem` | ≈ 36 + 18 = 54px | ElCheckbox 默认高度 + margin-bottom |
| 提交按钮区 | 15 + 40 = 55px | 内联 `margin-top:15px` + `custom-height` |
| 底部引导行 | 20 + ≈ 20 = 40px | `mt-5` = 20px + `text-sm` |
| **合计** | **≈ 516px** | |
| **剩余余量** | **≈ 134px** | 用于容纳校验错误提示 |

最坏情况下 4 个字段同时报错，每条错误提示约 18～22px，总计 ≈ 80px，**仍在 134px 余量内**。所以 `overflow-hidden`（L5）在注册页上目前不会裁掉内容 —— 但一旦你按第 19 章加了「邮箱 + 验证码 + 密码强度条」，就会立刻超出并被静默裁切。这个坑在第 17.9 节单独列出。

### 2.4 表单字段设计与校验矩阵

注册页只有 4 个字段，但校验逻辑是三页里最复杂的（登录页只有 2 条 required 规则）：

| 字段 | 类型 | 规则 1 | 规则 2 | trigger | 联动 |
| --- | --- | --- | --- | --- | --- |
| `username` | `string` | `required` + 提示文案 | `min:3, max:20` + 长度提示 | `blur` | 无 |
| `password` | `string` | 自定义 `validatePassword`（非空） | `min:6` + 长度提示 | `blur` | **失焦时主动重校验 `confirmPassword`** |
| `confirmPassword` | `string` | 自定义 `validateConfirmPassword`（非空 + 与 password 相等） | — | `blur` | 依赖 `formData.password` |
| `agreement` | `boolean` | 自定义 `validateAgreement`（必须为 true） | — | `change` | 无 |

设计上的三个巧思：

1. **密码一致性用「跨字段 validator」而不是 `watch`**：`validateConfirmPassword` 直接读 `formData.password`（L156），不引入额外状态，也不需要 `computed`。
2. **改密码时主动重校验确认密码**：`validatePassword` 里 `formRef.value?.validateField('confirmPassword')`（L136）解决了「先填确认密码，再改主密码，确认密码那条红字不会自动消失/出现」的经典问题。
3. **协议用 `trigger: 'change'`**：勾选框没有「失焦」概念，用 `change` 才能在用户勾/取消时实时反馈；同时 `validate()` 全量校验会无视 trigger 执行它，所以提交时也能拦住。

**一个不对称**：改「确认密码」不会反过来重校验「密码」（其实也不需要，因为密码规则不依赖确认密码）；但改「密码」时如果确认密码**还没填**（`formData.confirmPassword` 为空），`validateField` 不会执行 —— 这是有意的，避免用户刚输完密码就被弹出「请再次输入密码」。

### 2.5 为什么 `rules` 写成 `computed` 而不是普通对象

```ts
const rules = computed<FormRules<RegisterForm>>(() => ({ ... t('...') ... }))
```

因为所有错误文案都是 `t('register.rule.xxx')`。如果写成普通对象，`t()` 只在组件 setup 时求值一次，**切换语言后已生成的错误文案仍是旧语言**。`computed` 会在 `locale` 变化时重新求值，把新文案交给 `ElForm`。

但作者还额外加了 `:key="formKey"` + `watch(locale, () => formKey.value++)`（L19 / L114–L116）。原因在第 16 篇第 2 章已分析：`ElFormItem` 内部会把「已展示的错误字符串」缓存为渲染态，`computed` 换的是规则对象，不一定能刷新**已经标红的那行字**。暴力重建整个表单子树是最省心的解法。

对注册页而言，这个代价**比登录页小得多**：登录页重建会连带重置滑块 DOM 导致「视觉未通过 / 状态已通过」的不一致；注册页没有滑块，重建只是丢掉已显示的红字，而 `formData` 是组件级 `reactive`（不在 `ElForm` 子树内），`v-model` 会原样回填，**用户填的内容不会丢**。这是注册页反而更适合 `:key` 方案的地方。第 17.5 节会讨论重建带来的焦点丢失问题。

### 2.6 颜色：为什么要走五层 CSS 变量

注册页里出现了三种「写颜色」的方式：

```vue
<!-- L56：内联 CSS 变量 -->
<RouterLink style="color: var(--theme-color); text-decoration: none" ...>

<!-- L77：Tailwind 工具类 -->
<RouterLink class="text-theme" ...>

<!-- L75：Tailwind 语义化灰 -->
<div class="mt-5 text-sm text-g-600">
```

它们最终都来自同一条链：

```text
第 1 层  setElementThemeColor('#5D87FF')
         → 写入 document.documentElement.style 的 --el-color-primary
第 2 层  el-ui.scss L5    --main-color: var(--el-color-primary)
第 3 层  tailwind.css L8  --theme-color: var(--main-color)
第 4 层  tailwind.css L92 @theme { --color-theme: var(--theme-color) }
第 5 层  Tailwind 生成 .text-theme { color: var(--color-theme) }
         以及 .text-g-600 { color: var(--color-g-600) }
结果     换一次主色 → 全站（含注册页的链接、按钮、左侧插画）同步变色，零 JS 遍历
```

暗色模式则是另一条链：`tailwind.css` L51–L84 的 `.dark` 选择器把 `--art-gray-*` 整套换掉，于是 `text-g-600` 在亮色是 `#7987a1`、暗色是 `#8f8fa3`，**注册页不需要写任何 `dark:` 变体**。这是注册页底部引导行用 `text-g-600`（而登录页用了 Tailwind 原生 `text-gray-600`）显得更「懂事」的原因 —— 详见第 16 章对照表。

⚠️ 但 L56 的内联 `var(--theme-color)` 与 L77 的 `text-theme` 是**两种写法做同一件事**，属于不一致；第 17.11 节建议统一。

### 2.7 动画：一条缓动曲线贯穿全页

| 位置 | 动画 | 时长 | 缓动 |
| --- | --- | --- | --- |
| `style.css` L7 | 右侧表单盒 `slideInRight`（从右 30px + 透明 → 归位） | 0.6s | `cubic-bezier(0.25,0.46,0.45,0.94)` |
| `LoginLeftView.vue` L125 | 左侧插画 `slideInLeft`（从左 30px → 归位） | 0.6s | 同一条曲线 |
| `LoginLeftView.vue` L133 | 左侧文案 `slideInLeft` | 0.6s | 同一条曲线 |
| `LoginLeftView.vue` L154 | 所有几何装饰 | 0.8s | 同一条曲线 |
| `LoginLeftView.vue` L481 | 装饰线条 `lineGrow`（延迟 1.2s） | 0.8s | 同一条曲线 |

**设计意图**：左右两侧同时、同速、反向滑入，形成「从中间向两边展开」的对称入场感；几何装饰稍慢（0.8s）并带 0～1.2s 的错峰延迟，制造层次。`cubic-bezier(0.25,0.46,0.45,0.94)` 是一条「快起慢停」的减速曲线，收尾非常柔和。

注册页每次从登录页跳转过来都会重放这套动画（因为组件被销毁重建），这让「登录 ↔ 注册」的切换有明确的转场反馈，弥补了 `App.vue` 的顶层 `RouterView` 没有包 `<Transition>` 的不足。

⚠️ 两个已存在的小瑕疵：`LoginLeftView.vue` L34 / L39 写了 `animation-delay: 0.5`（**缺单位**），浏览器会当作非法值忽略，所以背景泡泡和太阳/月亮实际是 0 延迟入场；第 17.14 节给出修正。

### 2.8 断点：1600 / 1180 / 768 / 640 各自管什么

| 断点 | 位置 | 在注册页上的效果 |
| --- | --- | --- |
| `≤1600px` | `LoginLeftView.vue` L487 | 左栏从 65vw 缩到 60vw，右侧多出 5vw；左侧文案上移（bottom 80→40px） |
| `≤1180px` | `LoginLeftView.vue` L495 | **左侧整块消失**（`width:auto; height:auto; padding:0`，插画/文案/装饰/logo 全 `display:none`），右栏变成 100% 宽；同时 `AuthTopBar` 改为左右分布并显示一个「小 logo + 系统名」 |
| `≤1180px` | `AuthTopBar.vue` L4 | 顶栏 `justify-content` 从 `flex-end` 改成 `space-between`，左侧品牌出现 |
| `≤768px`（`max-md`） | `style.css` L8 / L15 | 表单盒**取消滑入动画**（`animate-none`）；标题从 36px 降到 30px（`text-3xl`） |
| `≤640px`（`max-sm`） | `style.css` L6 / L15 | 表单盒宽度改为 100%、左右各留 28px（`px-7`）；标题加 `pt-10`（40px 上边距）；顶栏色点面板隐藏（`AuthTopBar.vue` L12 `max-sm:!hidden`） |

**为什么 `≤1180px` 要让左栏彻底消失**：表单盒写死 440px，而右栏宽度 = 视口宽度 − 左栏宽度。两个断点叠加后：

| 视口宽度 | 左栏 | 右栏可用宽度 | 是否放得下 440px |
| --- | --- | --- | --- |
| 1600px | 60vw = 960px | 640px | ✅ 余 200px |
| 1180px | 60vw = 708px | 472px | ✅ 余 32px |
| 1100px | 60vw = 660px | 440px | ⚠️ 刚好贴边 |
| 1000px | 60vw = 600px | 400px | ❌ 放不下 |

也就是说，**440px 硬宽度 ÷ 40%（1600 断点后的右栏比例）= 1100px** 是几何上的临界点。作者把断点定在 1180px，比临界点提前 80px、留出 32px 余量，同时给 `max-sm:px-7` 的窄屏内边距留出空间。所以这个断点不是审美选择，而是由表单盒宽度倒推出来的安全边界（也解释了为什么 `AuthTopBar` 恰好在同一个 1180px 从右对齐改成左右分布）。

### 2.10 注册页当前的定位：一个「可运行的占位符」

必须说清楚，否则容易误判代码质量：

```vue
<!-- L205–L214：真实实现被完整注释保留 -->
// TODO: 替换为真实 API 调用
// const params = { username: formData.username, password: formData.password }
// const res = await AuthService.register(params)
// if (res.code === ApiStatus.success) { ... }
```

这说明作者的意图是：**把 UI、校验、跳转、国际化全部做完整，只把「网络请求」这一层留空**，让使用者按自己的后端替换 10 行代码即可。这解释了：

- 为什么没有 `AuthService`（全项目搜索只有这一处注释提到，类根本不存在）；
- 为什么 `src/api/auth.ts` 只有 `fetchLogin` / `fetchGetUserInfo` 两个函数；
- 为什么 `Api.Auth` 命名空间里只有 `LoginParams` / `LoginResponse` / `UserInfo`，没有 `RegisterParams`；
- 为什么成功后不写 token、不设登录态 —— 因为「注册后是否自动登录」是业务决策，模板不替你决定；
- 为什么 `REDIRECT_DELAY = 1000` 被同时用作「模拟请求耗时」和「跳转前停留」。

⚠️ 注释里的 `res.code === ApiStatus.success` 与项目实际 HTTP 封装**不匹配**：`request.post` 的响应拦截器已经把 `data` 解包并返回业务数据，不会保留 `code` 字段（详见第 6 篇）。直接取消注释会编译/运行失败。第 18 章的 patch 会按项目真实约定重写这段。

### 3.5 样式作用域链：为什么 3 行 `<style>` 能撑起整页

```text
① main.ts L6   import '@styles/core/tailwind.css'
   → 全局注入 :root 变量、@theme、@layer utilities（flex-c / c-p / tad-300…）
② main.ts L7   import '@styles/index.scss'
   → reset / app / el-ui（--main-color）/ dark / router-transition / theme-*
③ register/index.vue L238  <style scoped>
④ L239        @import '../login/style.css'
   → 把 39 行 CSS **文本级展开**进当前 SFC 的样式块
   → Vue SFC 编译器给展开后的每条选择器追加 [data-v-xxxx]
   → 因此 .auth-right-wrap / .form / .title / .custom-height 都只作用于本组件模板
⑤ login/style.css L1  @reference '@styles/core/tailwind.css'
   → Tailwind 4 专用指令：只把变量/工具类**提供给 @apply 解析**，不输出任何 CSS
   → 避免「三页各 @import 一次 tailwind.css 导致样式重复三份」
⑥ login/style.css L5-8  @apply absolute inset-0 ... 
   → 编译期把工具类展开成真实声明（position:absolute; top:0; …）
⑦ login/style.css L28  @keyframes slideInRight
   → Vue SFC 的 scoped 转换会给 @keyframes 名称加唯一后缀以避免跨组件冲突，
     并同步改写引用它的 animation / animation-name 声明（由 postcss 插件处理）
```

**为什么 `@reference` 而不是 `@import`**：Tailwind 4 里 `@import 'tailwindcss'` 会真的输出整套 preflight + utilities；`@reference` 只建立「符号表」，让 `@apply` 能查到 `absolute`、`max-sm:px-7` 这些类，但产物里不含它们。三份授权页各自 `@import` 同一份 `style.css`，却不会把 Tailwind 基础样式重复注入三次 —— 这是 Tailwind 4 迁移后很关键的正确写法。

**一个容易踩的坑**：因为 `@import` 发生在 `<style scoped>` 内部，展开后的 `.el-input`、`:deep(...)` 之类选择器也会被加上 `data-v`；如果将来有人把 `style.css` 改成全局引入（去掉 scoped 或移到 `main.ts`），这些样式会**立刻泄漏到主布局的所有表单**。第 19.9 节讨论改造时会再提到这点。


### 6.2 `@import` 与 `scoped` 的相互作用（容易误解）

```text
编译前（register/index.vue）
  <style scoped>
    @import '../login/style.css';   ← 39 行含 .auth-right-wrap / .form / .title ...
  </style>

编译后（概念示意）
  <style>
    .auth-right-wrap[data-v-a1b2c3] { position:absolute; inset:0; width:440px; ... }
    .auth-right-wrap[data-v-a1b2c3] .form[data-v-a1b2c3] { height:100%; padding-block:40px }
    .title[data-v-a1b2c3] { ... }
    @keyframes slideInRight-a1b2c3 { ... }   ← 关键帧名被重命名，animation 引用同步改
  </style>
```

三个结论：

1. **三页 `@import` 同一文件不会产生全局冲突**：各自编译出不同 `data-v` 哈希。
2. **`@apply` 在 scoped 块里同样生效**：Tailwind 在 PostCSS 阶段把工具类展开成声明，Vue 的 scoped 插件再给选择器加属性，两者顺序由 Vite 插件链保证。
3. **不要在共用 CSS 里写 `:deep(...)` 或全局元素选择器**：加了之后会穿透到子组件，而三页的子组件结构不同，很容易误伤。当前 `style.css` 里没有这类写法，是安全的。

### 7.2 L5–L8：表单盒的 11 个工具类（逐条展开）

L5–L8 其实是一条跨 4 行的 `@apply` 语句（分号在 L8 末尾）。逐个拆：

| 类 | 编译后的 CSS | 在注册页的作用 |
| --- | --- | --- |
| `absolute` | `position: absolute` | 脱离文档流，不占父级高度 |
| `inset-0` | `top:0; right:0; bottom:0; left:0` | 把绝对定位元素的四个边都拉到定位父级（L6 `relative flex-1`）边界 |
| `w-[440px]` | `width: 440px` | 固定宽度；任意值语法（Tailwind 4 支持） |
| `h-[650px]` | `height: 650px` | 固定高度；配合 `m-auto` 才能垂直居中 |
| `py-[5px]` | `padding-top:5px; padding-bottom:5px` | 给滑入动画留一点点呼吸空间，避免阴影/描边贴边 |
| `m-auto` | `margin: auto` | **四边 auto + 四边 inset 0 + 固定宽高 = 水平垂直同时居中**（见 2.3） |
| `overflow-hidden` | `overflow: hidden` | 裁掉超出 650px 的内容。⚠️ 这是第 17.9 节「加字段后底部被静默裁掉」的根源 |
| `max-sm:px-7` | `@media (width < 640px) { padding-left:28px; padding-right:28px }` | 窄屏左右留白 28px |
| `max-sm:w-full` | `@media (width < 640px) { width:100% }` | 窄屏表单盒不再固定 440px，改为撑满（配合上一条形成内边距） |
| `animate-[slideInRight_0.6s_cubic-bezier(...)_forwards]` | `animation: slideInRight 0.6s cubic-bezier(0.25,0.46,0.45,0.94) forwards` | 任意值动画；`forwards` 让结束后停在 `to` 状态（否则会闪回 `opacity:0`） |
| `max-md:animate-none` | `@media (width < 768px) { animation: none }` | 窄屏取消入场动画（避免小屏位移感过强 / 减少低端设备重绘） |

**关于 `cubic-bezier(0.25,0.46,0.45,0.94)`**：控制点 P1=(0.25,0.46)、P2=(0.45,0.94)，是一条「起步较快、后半段极缓」的减速曲线，接近 `ease-out` 但收尾更柔。整份授权页（左右滑入、几何装饰、装饰线条）都用同一条，见 2.7。

**关于下划线**：`cubic-bezier(0.25,0.46,0.45,0.94)` 里的逗号在 Tailwind 任意值里会被解析成参数分隔，所以作者把整段动画简写用 `_` 连接空格、`()` 内保留逗号，这是 Tailwind 4 arbitrary value 的标准写法。写成 `animate-[slideInRight_0.6s_...]` 时不能有多余空格。

### 8.10 三页共用的动画会重复播放吗

会。每次 `router.push` 在 `/auth/login ↔ /auth/register ↔ /auth/forget-password` 之间切换时，`LoginLeftView` 都会被销毁并重建（它是各页面模板的子组件，不是跨路由复用的布局组件），因此：

- 左侧插画、文案、所有几何装饰**每次切页都会重放一遍 0.6～1.2s 的入场动画**；
- 右侧表单盒的 `slideInRight` 也同步重放；
- 视觉上形成「整页重新入场」的转场，弥补了 `App.vue` 顶层 `RouterView` 没有 `<Transition>` 的空缺；
- 代价是从登录点「注册」时，左边明明没变却要重新飞一遍，略显重复。

第 19.9 节会给出「把左侧组件提到路由外层以复用实例」的思路，但要权衡动画与实现复杂度。

### 9.4 三个按钮对注册页的实际影响（重点）

| 操作 | 链路 | 对正在填写的注册表单的影响 |
| --- | --- | --- |
| **切换语言** | `changeLanguage` → `locale.value = lang` → 注册页 `watch(locale)` → `formKey++` → `ElForm` 子树重建 | ✅ 4 个输入值保留（父级 `reactive`）；❌ 已显示的红字、校验状态、当前焦点丢失；✅ 规则文案随 `computed` 更新；页面标题由 `setLanguage` → `setPageTitle` 刷新为英文/中文 |
| **切换主色** | `changeThemeColor` → `setElementTheme` 写 CSS 变量 → `reload()` 翻转 `refresh` | 授权页**不在主布局内**，`refresh` 没有任何消费者，所以**表单完全不受影响**，只是全站颜色瞬时变化。⚠️ 但 `systemThemeColor` 被 Pinia persist 存盘，且主布局下次挂载时会因 `refresh` 变化重建 —— 用户点「注册」进入登录页时不会重建（同属授权页），只有之后真正登录进主布局才会用到这个标志 |
| **切换明暗（右上月亮 / 左侧太阳）** | `themeAnimation(e)` → `startViewTransition` → `switchThemeStyles` 切 `.dark` → `useCommon().refresh()` | `useCommon().refresh()` 是**整页 `location.reload()`**（不是 `settingStore.reload()`）。⚠️ **注册表单 4 个字段全部清空**（`formData` 是内存态，没有持久化），用户填到一半点月亮就白填了。这是注册页最容易被忽略的数据丢失点（第 17.15 节） |

> **命名陷阱**：项目里有两个「refresh」——
> - `settingStore.refresh` / `reload()`：翻转布尔标志，给主布局 RouterView 当 `:key` 用，**不刷新浏览器**；
> - `useCommon().refresh()`：`window.location.reload()`，**真的刷新页面**。
>
> 前者是 `AuthTopBar.changeThemeColor` 用的，后者是 `themeAnimation` 用的。两者只差一个词，但后果完全不同。第 9.4 表格是理解注册页「切主题会不会丢数据」的关键。

### 9.5 为什么授权页就能切主题和语言

这是一个刻意的产品设计：登录/注册是用户**第一次**看到系统，让他在这里就能选好语言和明暗，进主界面后无需再改。实现上依赖三件事：

1. `AuthTopBar` 直接用 `useSettingStore` / `useUserStore`，而这两个 store 在 `main.ts` 的 `initStore(app)` 阶段就已安装，**不依赖登录态**；
2. 语言偏好由 Pinia persist 落到 `localStorage`，`locales/index.ts` 的 `getDefaultLanguage()` 在下次启动时会读回；
3. 主题由 `initializeTheme()`（`App.vue` 的 `onBeforeMount`）在应用挂载前恢复。

代价是：授权页的顶部工具条要自己实现一遍「功能开关」（`useHeaderBar` 的 `language` / `themeToggle` 配置），而主色面板（L12–L33）则是**完全独立的一份实现**，跟主布局设置面板里的主色选择并不共用组件 —— 属于功能重复。

## 10. 校验机制深潜：ElForm 内部到底做了什么

前面第 5 章逐行解释了注册页自己写的校验代码。这一章把视角下沉到 Element Plus，回答「`await formRef.validate()` 这一行背后究竟发生了什么」，这样才能解释第 17 章那些看似奇怪的边界行为。

### 10.1 四个对象之间的关系

```text
formData (reactive)          ← 数据源，注册页 L118
   │  :model
   ▼
ElForm (formRef)             ← 表单实例，注册页 L15 / L108
   │  持有 fields: ElFormItem[]，提供 validate / validateField / resetFields / clearValidate
   │  :rules
   ▼
rules (computed)             ← 规则字典，注册页 L176
   │  prop 索引
   ▼
ElFormItem × 4               ← 每个字段一个，注册页 L21/L29/L40/L52
   │  内部：validateState ('error' | 'success' | '')、validateMessage、validateDisabled
   │  getFilteredRule(trigger) → 交给 async-validator
   ▼
async-validator              ← 真正执行 min/max/required/validator 的第三方库
```

### 10.2 `validate()` 的执行序列

```text
1. register() 调用 formRef.validate()（L202）
2. ElForm.validate() 遍历所有已注册的 ElFormItem
3. 对每个 item 调用 validate(trigger)，此时 trigger 为 undefined
      → getFilteredRule(undefined) 返回**全部规则**（不按 trigger 过滤）
4. 构造 async-validator 的 descriptor：
      { username: [...], password: [...], confirmPassword: [...], agreement: [...] }
5. 用 formData 作为 source，执行 validator.validate(source)
6. 逐字段串行/并行校验（async-validator 默认并行），收集 fields 错误
7. 每个 ElFormItem 设置：
      validateState = 'error' | 'success'
      validateMessage = 第一条失败规则的 message 或 validator 抛出的 Error.message
8. Vue 响应式更新 → 渲染 .el-form-item__error 红字 + .is-error 红框
9. 若有任何失败 → reject({ errors, fields })   ← 注册页 L222 catch 接到这个对象
   若全部通过   → resolve(true)                ← 注册页 L203 继续执行
```

**关键点**：`validate()` 失败走 **reject** 而不是返回 `false`。Element Plus 文档里更推荐的写法是传回调：

```ts
formRef.value.validate((valid, fields) => { ... })   // 回调形式不会 reject
```

注册页用的是 Promise 形式，所以正常的「用户少勾了协议」也会打一条 `console.error`。第 18 章 patch 会改掉。

### 10.3 `validateField('confirmPassword')` 的行为（L136）

| 项 | 行为 |
| --- | --- |
| 作用范围 | 只跑 `confirmPassword` 这一项的规则，不动其他三个字段 |
| trigger | 不传 → 全部规则 |
| 返回值 | `Promise<boolean>`，**失败时 reject** |
| 注册页的处理 | `formRef.value?.validateField(...)` —— 没有 `.catch()`、没有 `await`、没有回调 |
| 后果 | 当「密码改成 B 而确认密码还是 A」时，这次调用会 reject → 浏览器控制台出现 `Uncaught (in promise)` 警告（部分构建配置下会被 `error-handle.ts` 全局捕获并记录）。**功能不受影响**（红字照常显示），但日志噪音是真实的 |

**修复办法**（三选一，第 18 章采用第 3 种）：

```ts
// ① 传回调
formRef.value?.validateField('confirmPassword', () => {})

// ② 显式吞掉 rejection
formRef.value?.validateField('confirmPassword').catch(() => {})

// ③ 只清状态，让用户/提交时再校验（更保守）
formRef.value?.clearValidate('confirmPassword')
```

### 10.4 `trigger` 的两种触发路径

| 路径 | 入口 | 规则筛选 |
| --- | --- | --- |
| 字段级（用户失焦 / 勾选变化） | `ElFormItem` 监听内部 input 的 `blur` / `change`，调 `formItem.validate('blur')` | `getFilteredRule('blur')` 只保留 `trigger:'blur'` 的规则；`trigger:'change'` 的 agreement 规则在 change 时才跑 |
| 表单级（点提交） | `formRef.validate()` | **不过滤**，4 个字段 7 条规则全跑 |

所以「用户从没碰过协议框、直接点注册」时，`agreement` 依然会被校验 —— 这是 `validate()` 的功劳，不是 `trigger:'change'` 的功劳。

### 10.5 自定义 validator 与内置规则的混用

| 字段 | 规则数组 | async-validator 的实际执行 |
| --- | --- | --- |
| `username` | `required` + `min/max` | 空 → 第 1 条失败并停止；非空但长度越界 → 第 2 条失败 |
| `password` | `required+validator` + `min` | 空 → `required` 先失败（validator 甚至可能不执行，取决于版本）；`123` → validator 通过、`min` 失败；`abcdef` → 全通过并触发 L136 联动 |
| `confirmPassword` | `required+validator`（同一条） | `required: true` 与 validator 写在**同一个规则对象**里，async-validator 会同时处理；validator 内部又判空 → 空值时可能得到两条错误但只显示第一条 |
| `agreement` | 仅 `validator` | 直接判 `!value`，最可靠 |

**`required` 对 `false` 的坑**：async-validator 的 `required` 规则对布尔 `false` 的判定在不同版本/配置下不一致，有的把 `false` 视为「有效值」而放行。注册页 L191 **故意不加 `required`**，只用 `validateAgreement` 判 `!value`，是正确的规避。

### 10.6 错误提示的 DOM 与高度影响

```html
<div class="el-form-item is-error">
  <div class="el-form-item__content">
    <div class="el-input custom-height"> ... </div>
    <div class="el-form-item__error">两次输入密码不一致!</div>  <!-- position:absolute; top:100% -->
  </div>
</div>
```

`.el-form-item__error` 是**绝对定位**在 content 下方，因此严格来说它**不占文档流高度**，而是覆盖在下一个元素的上方。这也是为什么 2.3 节的高度预算里我把「4 条错误 ≈ 80px」算作「余量」而不是「撑高」—— 实际上 Element Plus 会为错误态的 form-item 增加 `margin-bottom`（默认 18px → 22px 左右），形成轻微撑高。两种效应叠加，注册页 134px 余量仍然够用；但一旦加了字段（第 19 章），`overflow-hidden` 就会开始裁切底部引导行。

### 10.7 `:key="formKey"` 与 `ElForm` 内部状态

| 状态 | 存放位置 | key 变化后 |
| --- | --- | --- |
| `formData` 四字段 | 注册页 setup（父作用域） | 保留 |
| `loading` / `formKey` | 注册页 setup | 保留 |
| `fields[]`（已注册的表单项） | `ElForm` 实例内部 | **重建**（旧实例卸载、新实例重新收集） |
| `validateState` / `validateMessage` | `ElFormItem` 实例内部 | **清空** |
| DOM 焦点 / 光标 | 浏览器 | **丢失** |
| `formRef` | 注册页 ref | 重新指向新实例 |

这也解释了为什么 L199 的 `if (!formRef.value) return` 是必要的：如果用户在 `:key` 刚变化、新实例还没挂载的那个 tick 里点了注册，`formRef.value` 可能还是 `undefined`。

### 10.8 与登录页校验实现的对照

| 维度 | 登录页 | 注册页 |
| --- | --- | --- |
| `rules` 泛型 | `FormRules`（无泛型） | `FormRules<RegisterForm>`（key 受约束） |
| 规则数 | 2 | 7 |
| 自定义 validator | 0 | 3 |
| `validate()` 用法 | `const valid = await validate(); if (!valid) return` | `await validate()`（无返回值判断） |
| 校验失败的处理 | 落进 `catch`，记 `[Login] Unexpected error` | 落进 `catch`，记「表单验证失败」 |
| 额外人机校验 | `isPassing` 滑块状态（在 `validate()` 之后判断） | 无 |
| `finally` | 有：`loading=false` + `resetDragVerify()` | 无 |

注册页的 `await validate()` 不接返回值是对的（因为失败会 reject 而非返回 false），反倒是登录页 L208–L209 的 `if (!valid) return` 是**死代码**（永远走不到 `false` 分支）。这是注册页写得比登录页更准确的一处。

### 11.3 语言切换的完整链路

```text
① 用户点右上语言按钮 → ElDropdown 选中 English
② AuthTopBar.changeLanguage('en')            (L94-98)
   ├─ if (locale.value === 'en') return       (L95)
   ├─ locale.value = 'en'                     (L96) ← 全局 composer 的 locale ref
   └─ userStore.setLanguage('en')             (L97)
        ├─ setPageTitle(router.currentRoute.value)   → 150ms 后把 document.title 改成 "Register - Art Design Pro"
        └─ language.value = 'en'              → Pinia persist 写入 localStorage
③ locale 变化触发注册页 watch(locale)        (L114-116)
   └─ formKey.value++ → ElForm 子树重建      (L19)
④ 同一时刻 rules computed 重新求值            (L176)
   └─ 所有 message / validator 内的 t() 返回英文
⑤ 模板里所有 $t() 重渲染                    (L11/L12/...)
⑥ 结果：整页文案变英文，已填数据保留，红字与焦点丢失
```

**为什么 `setLanguage` 里要调 `setPageTitle`**：`beforeEach` 只在**导航发生时**设置标题，语言切换不产生导航，所以需要手动刷新一次，否则标签页标题会停留在旧语言。`setPageTitle` 内部有 150ms 延时（`utils/router.ts` L36–L38），是为了避开导航中路由对象尚未稳定的时刻。

### 11.4 语言偏好的持久化与恢复

| 阶段 | 代码 | 行为 |
| --- | --- | --- |
| 应用启动 | `locales/index.ts` L60–L92 `getDefaultLanguage()` | 先读版本化存储 `sys-v{version}-user` 里的 `language`；读不到再读系统存储；都没有则默认 `ZH` |
| 创建实例 | L97–L108 `createI18n({ locale: getDefaultLanguage(), legacy:false, globalInjection:true, fallbackLocale: ZH, messages })` | `fallbackLocale` 保证缺 key 时回落中文，不会显示裸 key |
| 用户切换 | `AuthTopBar` L97 → `userStore.setLanguage` | Pinia persist 写盘 |
| 下次启动 | 回到第一行 | 读回上次选择 |

⚠️ 有一个**初始化顺序上的不对称**：`getDefaultLanguage()` 读的是 Pinia persist 的 `user` 存储键（通过 `StorageKeyManager.getStorageKey('user')`），而 `main.ts` 里 `initStore(app)` 在 `app.use(language)` **之前**执行 —— 顺序正确，能读到。但 `locales/index.ts` 是模块顶层导入时就执行 `getDefaultLanguage()` 的（L98 在模块求值期），那时 `initStore` 可能还没跑；不过它直接读 `localStorage`，不依赖 Pinia 实例，所以仍然可用。

### 11.5 Element Plus 内置文案的语言

`App.vue` 里：

```vue
<ElConfigProvider size="default" :locale="locales[language]" :z-index="3000" ...>
```

`language` 来自 `storeToRefs(userStore)`，所以切语言时 `ElConfigProvider` 也会把 Element Plus 内部文案（如 `show-password` 图标的 aria-label、日期选择器的「确定」等）一并切换。注册页虽然没有日期选择器，但**密码框的眼睛图标提示文字**会跟着变。

⚠️ 但注意：`AuthTopBar.changeLanguage` 同时改了 `locale.value`（i18n）和 `userStore.setLanguage`（Pinia），两者是**两个独立状态**，只是恰好都被更新了。如果别处只改其中一个，就会出现「业务文案是英文、组件内置文案是中文」的错位。

### 14.1 `v-ripple`（模板 L69）

`src/directives/business/ripple.ts`，116 行。注册链路：

`mounted` 钩子（L50–L111）做的事：

| --- | --- | --- |

| 改样式 | L55–L56 | `el.style.position='relative'; el.style.overflow='hidden'` —— 对 `ElButton` 的 `<button>` 根元素生效 |

⚠️ 三个与注册页相关的观察：

1. **没有 `unmounted` 钩子移除监听**：按钮随组件卸载时 DOM 一起销毁，监听自然被 GC，不会泄漏；但指令写法不完整。
2. **`mousedown` 而非 `click`**：`loading=true` 后按钮被禁用，第二次点击不会触发波纹（浏览器不给 disabled 元素派发 mousedown）—— 与 L68 的加载态是配合的。
3. **`overflow:hidden` 是内联写入**：如果将来给按钮加了 `ElBadge` 之类的溢出内容，会被裁掉。

### 14.2 `ArtLogo`（L5 / AuthTopBar L7）

| --- | --- |

### 14.3 `ThemeSvg`（LoginLeftView L10）

它是「让插画跟着主题变色」的关键，逻辑值得完整看一遍：

```text
props: src / size(默认 500) / themeColor
  ↓
sizeStyle = computed → { width, height }（注册页传 '100%'）
  ↓
COLOR_MAPPINGS = {
  '#C7DEFF' → var(--el-color-primary-light-6),
  '#071F4D' → var(--el-color-primary-dark-2),
  '#00E4E5' → var(--el-color-primary-light-1),
  '#006EFF' → var(--el-color-primary),
  '#fff' / '#ffffff' → var(--default-box-color),
  '#DEEBFC' → var(--el-color-primary-light-7)
}
  ↓
watchEffect → loadSvgContent()
  → fetch(props.src) 取 SVG 文本
  → applyThemeToSvg(): 用正则把 fill="..." / stroke="..." 里的固定色替换成 CSS 变量
  → svgContent.value = 处理后的字符串
  ↓
模板 <div class="svg-container" v-html="svgContent">
```

| 观察 | 说明 |
| --- | --- |
| 为什么插画能换色 | 因为替换成的是**字符串形式的 CSS 变量**，浏览器在渲染 SVG 时实时解析，主色一变插画就变 |
| `v-html` 的安全性 | `src` 是本地静态资源（`@imgs/svg/login_icon.svg`），不是用户输入，风险可控 |
| 每次切主题会重新 fetch 吗 | `watchEffect` 只依赖 `props.src`（`themeColor` 虽声明了但函数体内没读它），所以**不会**；换色靠 CSS 变量实时生效，无需重载 |
| `themeColor` prop | 声明了但在组件里完全没被使用 —— 又一个未完成的配置项 |
| 资源大小 | `login_icon.svg` 4.2 KB，`viewBox="0 0 400 300"` |

## 17. 边界行为、坑与改进建议

> 以下 22 条全部来自逐行通读，**每条都给出可复现的触发路径**。严重度：🔴 影响功能/数据、🟠 影响体验、🟡 可维护性/一致性。

### 17.1 🔴 没有真实注册接口 + 两层定时器 + 无生命周期清理

- **触发**：点「注册」并通过校验。
- **现象**：不发任何请求；1000ms 后提示成功并**恢复按钮可点**，再 1000ms 才跳走；若中途离开页面，定时器仍会执行 `ElMessage` 与 `router.push`（链路 7）。
- **根因**：L205–L214 真实实现被注释；L217 与 L232 两个 `setTimeout` 串联；组件没有 `onBeforeUnmount`。
- **影响**：演示态无注册能力；接真实接口前存在重复提交窗口；跨页面出现"幽灵提示"和重复导航。
- **改法**：见第 18 章完整 patch —— 改成 `await fetchRegister(...)`、用 `let redirectTimer` 保存 id、`onBeforeUnmount` 清理、`finally` 统一收尾、提交期间用 `loading` 全程锁住按钮。

### 17.2 🟠 `validate()` 校验失败被当成异常记录

- **触发**：任何一项没填/没勾协议就点注册。
- **现象**：控制台打印 `表单验证失败: {errors, fields}`，文案把正常交互说成错误。
- **根因**：L202 `await validate()` 在失败时 **reject**，L222 `catch` 不分类型统一 `console.error`。
- **影响**：接真实 API 后，"网络 500" 和 "用户没勾协议" 会共用一条日志，排查困难。
- **改法**：用回调形式 `validate((valid) => ...)`，或 `const valid = await validate().catch(() => false); if (!valid) return`，把校验失败与请求异常分开处理。

### 17.3 🔴 `/privacy-policy` 是不存在的路由

- **触发**：点击协议行里的《隐私政策》。
- **现象**：未登录时被 `logOut()` + `next(Login)` 踢回登录页（还伴随两次导航竞争），已登录时落到 404；**已填表单全部丢失**。
- **根因**：L57 硬编码 `to="/privacy-policy"`，而 `staticRoutes` 与所有动态路由模块里都没有该路径；`isStaticRoute()` 又显式排除了 404 catch-all（L231）。
- **影响**：合规功能完全不可用，且是最容易触发的数据丢失点。
- **改法**：见 12.4 三个方案，推荐 C（弹窗）或 A（补静态路由 + 命名跳转）。

### 17.4 🟠 回车提交只在「确认密码」框生效

- **触发**：在账号或密码框按 Enter。
- **现象**：无反应（表单没有 `<button type="submit">`，也不会自动提交）。
- **根因**：L47 `@keyup.enter` 只绑在第三个 `ElInput`；登录页是绑在整个 `ElForm` 上（L18）。
- **改法**：把 `@keyup.enter="register"` 移到 `ElForm` 开标签，或给 `ElButton` 加 `native-type="submit"` + 表单 `@submit.prevent="register"`。

### 17.5 🟠 切语言会丢焦点与校验态

- **触发**：填到一半切 English。
- **现象**：输入内容还在，但光标没了、已显示的红字消失。
- **根因**：L19 `:key="formKey"` + L114–L116 整体重建子树。
- **权衡**：`rules` 已是 `computed`，其实只换规则文案不需要重建；重建是为了清掉 `ElFormItem` 缓存的错误字符串。
- **改法**：改成 `watch(locale, () => { formRef.value?.clearValidate(); })`，配合 `computed` 规则即可刷新文案，且保留焦点；若确实需要重建，至少记录并恢复 `document.activeElement`。

### 17.6 🟡 必填错误文案复用了 placeholder

- **触发**：账号/密码留空失焦。
- **现象**：报错「请输入账号」「请输入密码」——和占位文字一模一样。
- **根因**：L131 用 `t('register.placeholder.password')`、L178 用 `t('register.placeholder.username')`；`register.rule` 段没有对应的 `xxxRequired` key。
- **改法**：在 zh/en 里补 `register.rule.usernameRequired` / `passwordRequired`，改成「账号不能为空」这类明确报错语气。

### 17.7 🟠 `validateField()` 的 rejection 无人处理

- **触发**：链路 4（改主密码导致确认密码不一致）。
- **现象**：控制台出现 `Uncaught (in promise)` 或被全局错误处理捕获的噪音；红字照常显示。
- **根因**：L136 `formRef.value?.validateField('confirmPassword')` 没有 `.catch()`、没有回调。
- **改法**：`validateField('confirmPassword').catch(() => {})`，或改用 `clearValidate('confirmPassword')`。

### 17.8 🟠 密码字段用了 `v-model.trim`

- **触发**：用户设置以空格开头/结尾的密码。
- **现象**：实际存的是被裁掉空格的版本；两个密码框都 trim 所以一致性校验通过，用户毫无察觉。
- **根因**：L32 / L43 的 `.trim` 修饰符。
- **改法**：密码与确认密码去掉 `.trim`（账号可保留），或显式提示「密码首尾空格将被忽略」。同时把 `autocomplete="off"` 改成 `autocomplete="new-password"`。

### 17.9 🟠 固定 650px + `overflow-hidden`，加字段会静默裁切

- **触发**：按第 19 章加邮箱/验证码/密码强度条，或给 `ElFormItem` 加 `label`。
- **现象**：底部「已有账号？去登录」被裁掉，且没有任何报错。
- **根因**：`style.css` L5 `h-[650px]` + `overflow-hidden`；2.3 算出的余量只有约 134px。
- **叠加问题**：L18 `label-position="top"` 目前无效（没有 label），但一旦加 label，`el-ui.scss` L30–L33 会把每个 label 高度锁成 36px，4 个字段立刻多出 144px，直接超出。
- **改法**：给表单盒改 `min-height: 650px; height: auto`，`overflow: visible`；或加字段时同步调高 `h-[...]`。若不需要 label，删掉 L18 的 `label-position` 以免误导。

### 17.10 🟠 链接嵌在 `ElCheckbox` 的 label 内

- **触发**：点击《隐私政策》。
- **现象**：确定会导航离开并丢失表单；不同浏览器/辅助技术下还可能连带切换勾选状态（HTML 规范对 label 内交互内容通常不转发 activation，但行为不完全统一）。
- **根因**：L55–L59 的 `RouterLink` 位于 L53 `<ElCheckbox>` 的默认插槽（渲染为 `<label>` 内容）内。
- **改法**：把链接移到 `ElCheckbox` 外面，用 flex 并排；或至少加 `@click.stop` 并 `target="_blank"` 打开新标签，避免离开当前页。

### 17.11 🟡 同一件事两种写法、同一类跳转两种风格

| 位置 | 现状 | 建议统一为 |
| --- | --- | --- |
| L56 隐私政策链接颜色 | 内联 `style="color: var(--theme-color); text-decoration:none"` | `class="text-theme no-underline"` |
| L77 去登录链接颜色 | `class="text-theme"` | 同上 |
| L57 隐私政策跳转 | 硬编码 `to="/privacy-policy"` | `:to="{ name: 'PrivacyPolicy' }"` 或外链 |

| L14 表单上边距 | `class="mt-7.5"` | 保持不变 |

### 17.12 🟡 `RoutesAlias` 缺少 `Register` / `ForgetPassword`

- **现象**：登录页有 `RoutesAlias.Login` 常量，注册页与忘记密码页只能靠 `isStaticRoute` 白名单；代码里想引用注册路径时只能写字符串或路由名。
- **改法**：在 `routesAlias.ts` 补 `Register = '/auth/register'`、`ForgetPassword = '/auth/forget-password'`，并把 `beforeEach.ts` L210 与 `userStore.logOut()` L171 改用常量。

### 17.13 🟠 成功提示硬编码中文，且没有对应 i18n key

- **触发**：链路 6 的 t=1000ms。
- **现象**：界面切成 English 后仍弹「注册成功」。
- **根因**：L219 `ElMessage.success('注册成功')`；zh/en 的 `register` 段没有 `success` / `failed` key。
- **改法**：补 `register.success` / `register.failed` / `register.networkError`，改成 `ElMessage.success(t('register.success'))`。

### 17.14 🟡 两处 `animation-delay: 0.5` 缺单位

- **位置**：`LoginLeftView.vue` L34（背景泡泡）、L39（太阳/月亮）。
- **现象**：CSS 把 `0.5` 当非法时间值忽略，两个元素实际是 0 延迟入场，与其他装饰的错峰设计不符。
- **改法**：改成 `animation-delay: 0.5s`。

### 17.15 🔴 切明暗主题会整页 reload，清空注册表单

- **触发**：填表单过程中点右上月亮或左侧太阳。
- **现象**：页面刷新，4 个字段全部回到初始值。
- **根因**：`themeAnimation` → `useCommon().refresh()` 是 `location.reload()`（第 13.4 节），`formData` 没有持久化。
- **改法**（三选一）：① 授权页不调用 `refresh()`，只切 `.dark`（CSS 变量实时生效，本就不需要刷新）；② 切主题前把 `formData` 存进 `sessionStorage`，`onMounted` 时恢复；③ 用 `<KeepAlive>` 或把表单状态提到 store。
- **推荐 ①**：授权页没有任何需要刷新才能生效的状态，这行 reload 是主布局遗留需求带过来的副作用。

### 17.16 🟡 `hideContent` prop 与左侧文案未做页面差异化

- **现象**：prop 声明了不用（L79–L81），左侧文案硬编码 `login.leftView.*`（L14–L15），注册页没有自己的品牌语。
- **改法**：要么实现 `v-if="!hideContent"`，要么删 prop；把文案抽成 `auth.leftView.*` 或加 `title`/`subTitle` props。

### 17.18 🟡 `userStore.logOut()` 里的 `/login` 硬编码

- **位置**：`user.ts` L171 `currentRoute.path !== '/login'`。
- **现象**：实际登录页路径是 `/auth/login`（`RoutesAlias.Login`），所以这个判断永远为 `true`，退出时总会带一个 `redirect` 参数；而且 `logOut()` 内部自己 `router.push`，与守卫 L216 的 `next({name:'Login'})` 形成**双重导航**（12.4 链路④）。
- **改法**：改成 `currentRoute.path !== RoutesAlias.Login`；守卫里只调 `userStore.logOut()` 或只 `next()`，不要两者都做跳转。

### 17.19 🟠 注释里的真实实现与项目 HTTP 封装不匹配

- **现象**：L210 `AuthService.register(params)`（`AuthService` 不存在）、L211 `res.code === ApiStatus.success`（响应拦截器已解包、`ApiStatus` 未 import）。
- **影响**：使用者照注释取消注释会直接编译失败，或者误以为项目是「Service 类 + code 判断」风格。
- **改法**：把注释替换成项目真实风格（第 18 章）：

```ts
const res = await fetchRegister({ userName: formData.username, password: formData.password })
// request 已经解包并统一处理错误码，成功即 resolve
```

### 17.20 🟠 账号/密码策略偏弱且无输入约束

| 缺项 | 影响 |
| --- | --- |
| 无 `maxlength="20"` | 20 字上限只能靠失焦校验，不能边输边限 |
| 无 `autocomplete="new-password"` | 密码管理器可能把已有密码填进注册框 |

| 无人机验证 | 接真实接口后注册会成为唯一无防护的写入口 |

### 17.21 🟠 成功后没有自动登录、没有清理敏感数据、协议同意未留痕

- **现象**：注册成功后只是跳登录页，用户要重新输一遍账号密码；`formData.password` 在内存里停留到组件卸载；`agreement` 只做前端校验，不随请求提交。
- **影响**：体验断点；合规上无法证明用户同意过哪个版本的政策。
- **改法**：接真实接口时按业务决定「注册后自动登录」还是「跳登录并预填账号」；提交后立即 `formData.password = ''` / `confirmPassword = ''`；把 `agreement: true` + 政策版本号 + 时间戳一起提交。

### 18.1 完整替换版 `src/views/auth/register/index.vue`

```vue
<!-- 注册页面 -->
<template>
  <div class="flex w-full h-screen">
    <LoginLeftView />

    <div class="relative flex-1">
      <AuthTopBar />

      <div class="auth-right-wrap">
        <div class="form">
          <h3 class="title">{{ $t('register.title') }}</h3>
          <p class="sub-title">{{ $t('register.subTitle') }}</p>

          <ElForm
            class="mt-7.5"
            ref="formRef"
            :model="formData"
            :rules="rules"
            :key="formKey"
            @keyup.enter="register"
          >
            <ElFormItem prop="username">
              <ElInput
                class="custom-height"
                v-model.trim="formData.username"
                :maxlength="USERNAME_MAX_LENGTH"
                :placeholder="$t('register.placeholder.username')"
                autocomplete="username"
              />
            </ElFormItem>

            <ElFormItem prop="password">
              <ElInput
                class="custom-height"
                v-model="formData.password"
                :placeholder="$t('register.placeholder.password')"
                type="password"
                autocomplete="new-password"
                show-password
              />
            </ElFormItem>

            <ElFormItem prop="confirmPassword">
              <ElInput
                class="custom-height"
                v-model="formData.confirmPassword"
                :placeholder="$t('register.placeholder.confirmPassword')"
                type="password"
                autocomplete="new-password"
                show-password
              />
            </ElFormItem>

            <!-- 链接移出 ElCheckbox 的 label，避免点击冲突与误导航 -->
            <ElFormItem prop="agreement">
              <div class="flex-c gap-1 flex-wrap">
                <ElCheckbox v-model="formData.agreement">
                  {{ $t('register.agreeText') }}
                </ElCheckbox>
                <button
                  type="button"
                  class="text-theme text-sm no-underline bg-transparent border-none c-p p-0"
                  @click.stop.prevent="policyVisible = true"
                >
                  {{ $t('register.privacyPolicy') }}
                </button>
              </div>
            </ElFormItem>

            <div class="mt-3.75">
              <ElButton
                class="w-full custom-height"
                type="primary"
                @click="register"
                :loading="loading"
                v-ripple
              >
                {{ $t('register.submitBtnText') }}
              </ElButton>
            </div>

            <div class="mt-5 text-sm text-g-600">
              <span>{{ $t('register.hasAccount') }}</span>
              <RouterLink class="text-theme" :to="{ name: 'Login' }">
                {{ $t('register.toLogin') }}
              </RouterLink>
            </div>
          </ElForm>
        </div>
      </div>

      <!-- 政策用弹窗展示，不离开注册页，表单不丢 -->
      <ElDialog v-model="policyVisible" :title="$t('register.privacyPolicy')" width="560px">
        <div class="text-sm text-g-700 leading-6">
          {{ $t('register.policyBody') }}
        </div>
        <template #footer>
          <ElButton type="primary" @click="acceptPolicy">{{ $t('common.confirm') }}</ElButton>
        </template>
      </ElDialog>
    </div>

<script setup lang="ts">
  import { useI18n } from 'vue-i18n'
  import type { FormInstance, FormRules } from 'element-plus'
  import { fetchRegister } from '@/api/auth'

  defineOptions({ name: 'Register' })

  interface RegisterForm {
    username: string
    password: string
    confirmPassword: string
    agreement: boolean
  }

  const USERNAME_MIN_LENGTH = 3
  const USERNAME_MAX_LENGTH = 20
  const PASSWORD_MIN_LENGTH = 6
  const REDIRECT_DELAY = 1000

  const { t, locale } = useI18n()
  const router = useRouter()
  const formRef = ref<FormInstance>()

  const loading = ref(false)
  const formKey = ref(0)
  const policyVisible = ref(false)

  // 所有异步任务都登记在这里，组件卸载时统一清理（修 17.1 / 15.7）
  let redirectTimer: ReturnType<typeof setTimeout> | undefined
  let messageTimer: ReturnType<typeof setTimeout> | undefined

  onBeforeUnmount(() => {
    if (redirectTimer) clearTimeout(redirectTimer)
    if (messageTimer) clearTimeout(messageTimer)
  })

  // 只清校验态 + 靠 computed 刷新文案，不再重建整棵表单（修 17.5）
  watch(locale, () => {
    formRef.value?.clearValidate()
  })

  const formData = reactive<RegisterForm>({
    username: '',
    password: '',
    confirmPassword: '',
    agreement: false
  })

  const validatePassword = (_rule: any, value: string, callback: (error?: Error) => void) => {
    if (!value) {
      callback(new Error(t('register.rule.passwordRequired')))   // 修 17.6
      return
    }
    if (formData.confirmPassword) {
      // 吞掉 reject，避免 Uncaught (in promise)（修 17.7）
      formRef.value?.validateField('confirmPassword').catch(() => {})
    }
    callback()
  }

  const validateConfirmPassword = (
    _rule: any,
    value: string,
    callback: (error?: Error) => void
  ) => {
    if (!value) {
      callback(new Error(t('register.rule.confirmPasswordRequired')))
      return
    }
    if (value !== formData.password) {
      callback(new Error(t('register.rule.passwordMismatch')))
      return
    }
    callback()
  }

  const validateAgreement = (_rule: any, value: boolean, callback: (error?: Error) => void) => {
    if (!value) {
      callback(new Error(t('register.rule.agreementRequired')))
      return
    }
    callback()
  }

  const rules = computed<FormRules<RegisterForm>>(() => ({
    username: [
      { required: true, message: t('register.rule.usernameRequired'), trigger: 'blur' },
      {
        min: USERNAME_MIN_LENGTH,
        max: USERNAME_MAX_LENGTH,
        message: t('register.rule.usernameLength', {
          min: USERNAME_MIN_LENGTH,
          max: USERNAME_MAX_LENGTH
        }),
        trigger: 'blur'
      }
    ],
    password: [
      { required: true, validator: validatePassword, trigger: 'blur' },
      {
        min: PASSWORD_MIN_LENGTH,
        message: t('register.rule.passwordLength', { min: PASSWORD_MIN_LENGTH }),
        trigger: 'blur'
      }
    ],
    confirmPassword: [{ validator: validateConfirmPassword, trigger: 'blur' }], // 去掉冗余 required
    agreement: [{ validator: validateAgreement, trigger: 'change' }]
  }))

  const register = async () => {
    // 提交期间整体加锁：加载态 + 跳转等待期都不允许再次提交（修 17.1）
    if (!formRef.value || loading.value || redirectTimer) return

    // 校验失败是正常交互，不进 catch、不打错误日志（修 17.2）
    const valid = await formRef.value.validate().catch(() => false)
    if (!valid) return

    loading.value = true
    try {
      // [真实] 按项目 HTTP 封装风格调用；响应拦截器已解包并统一处理错误码
      await fetchRegister({
        userName: formData.username,
        password: formData.password,
        agreement: formData.agreement,
        policyVersion: '1.0',
        agreedAt: new Date().toISOString()
      })

      // [DEMO] 不接后端时，把上面整段注释掉、改回下面这一行：
      // await new Promise((resolve) => setTimeout(resolve, REDIRECT_DELAY))

      // 立刻清掉内存里的明文密码（修 17.21）
      formData.password = ''
      formData.confirmPassword = ''

      ElMessage.success(t('register.success'))   // 修 17.13
      redirectTimer = setTimeout(() => {
        redirectTimer = undefined
        loading.value = false
        router.push({ name: 'Login', query: { username: formData.username } })
      }, REDIRECT_DELAY)
    } catch (error) {
      loading.value = false
      // 真正的异常才记日志，文案与校验失败区分开
      console.error('[Register] 注册请求失败:', error)
      ElMessage.error(t('register.failed'))
    }
  }

  const acceptPolicy = () => {
    formData.agreement = true
    policyVisible.value = false
    formRef.value?.validateField('agreement').catch(() => {})
  }
</script>
```

### 19.1 接真实注册 API（最小改动路径）

如果不想整体替换，只想在原文件上接后端，改 `register()` 的 L205–L221 即可：

```ts

try {
  const res = await fetchRegister({
    userName: formData.username,
    password: formData.password

  ElMessage.success(t('register.success'))
  formData.password = ''
  formData.confirmPassword = ''
```

**三种后续策略**：

| 策略 | 做法 | 适用 |
| --- | --- | --- |

### 19.7 协议同意留痕

```ts
const DRAFT_KEY = 'auth:register:draft'

  const raw = sessionStorage.getItem(DRAFT_KEY)

})

watch(formData, (v) => {

  sessionStorage.setItem(DRAFT_KEY, JSON.stringify({
```

### 22.2 一句话总结

注册页是一张**「薄页面 + 厚共用资产」**的演示态表单：4 个字段、7 条校验规则、3 个自定义 validator、1 条跨字段联动，撑起了完整的前端交互；而它的外壳（65:35 双栏、440×650 绝对居中表单盒、左右对称滑入动画、五层 CSS 变量链、主题/语言切换）全部来自登录页，自己只写了 3 行 `<style>`。

**它最值得学习的三点**：

1. 用「共用组件 + `@import` 共用 CSS」把三张认证页的视觉一致性固化下来，新增一个认证页几乎零成本；
2. 用 `computed` 规则 + 自定义 validator + `validateField` 联动，把「两次密码一致」这种跨字段逻辑表达得干净利落；
3. 所有颜色都走 CSS 变量链，注册页自己不写一句 `dark:`，却完整支持明暗与 7 种主色。

**它最需要警惕的三点**：

1. **它是演示态** —— 没有 `AuthService`、没有注册接口、成功只是 `setTimeout`；照注释取消注释会踩到「Service 类不存在 + `res.code` 与 HTTP 封装不匹配」两个坑；
2. **`/privacy-policy` 是死链** —— 点一下就被守卫踢回登录页，已填表单全丢；
3. **两层未清理的 `setTimeout` + 主题切换的整页 reload** —— 一个制造幽灵提示与重复提交窗口，一个直接清空用户输入。

第 18 章那份完整替换版把这些问题一次性收拢：真实 `fetchRegister`、单定时器 + 生命周期清理、校验失败不再当异常、协议用弹窗、密码不 trim、提示走 i18n、成功后清敏感字段。把它和 18.2–18.9 一起应用，注册页就从「能看的占位符」变成「能接后端、能过合规、能扛边界」的正式页面。
