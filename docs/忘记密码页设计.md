# 20 · 忘记密码页设计与实现逐行详解

> **文档定位**：这是 Art Design Pro 文档体系的第 20 篇专题深潜，对象是 `src/views/auth/forget-password/index.vue` —— 一个**只有 62 行**的页面。它比登录页（284 行）短 4.6 倍，比注册页（240 行）短 3.9 倍，但它是三张认证页里**问题最密集**的一张：提交逻辑是一个空函数，没有表单容器、没有校验、没有接口、没有成功态。
>
> **所以本文写两件事**：
> 1. **这 62 行到底是什么**——每一行、每个 class、每个绑定、每条样式、每个支撑模块的链路，全部拆开，不留黑盒；
> 2. **一个真正能用的忘记密码应该是什么**——从状态机、接口契约、令牌安全、防枚举、限流、多步表单，到可直接替换的完整代码。
>
> 一句话：**前半篇解释"现在为什么是空的"，后半篇给出"应该怎么填满"。**

> **⚠️ 一个必须先说清的前提**

### 1.4 一句话数据流（以及它断在哪）

```text
用户访问 /#/auth/forget-password
  → beforeEach 守卫判定它是静态路由（匿名放行）
  → 渲染 forget-password/index.vue
  → 复用 LoginLeftView / AuthTopBar / login/style.css 搭出外壳
  → 用户输入 → v-model.trim 写进 username ref（没有任何校验）
  → 点「提交」→ 调用 register() → async 空函数 → 立即 resolve
  ✗ 断点：无请求、无 loading、无提示、无状态变化、无副作用
  → 点「返回」→ router.push({ name: 'Login' }) → 回到登录页
```

**这个断点是理解本文的钥匙**：整页**唯一有真实副作用**的交互，是「返回」按钮和三个工具按钮（语言/主色/明暗）。「提交」是装饰。

## 2. 设计思路（为什么这样设计，以及为什么没做完）

这一章回答的不是"代码写了什么"，而是"**作者为什么这么写**"，以及更重要的——"**这个页面距离可用还差什么**"。

### 2.1 核心取舍：三页共用一套「认证页外壳」

登录、注册、忘记密码是三个独立路由，但视觉上是**同一张页面的三次换芯**。作者没有把布局写三遍，而是抽出三条共用资产：

| 共用资产 | 抽出方式 | 三页各自只写什么 |
| --- | --- | --- |
| 左侧 65vw 品牌区 | 组件 `LoginLeftView` | 一行 `<LoginLeftView />` |
| 右上工具条 | 组件 `AuthTopBar` | 一行 `<AuthTopBar />` |
| 右栏表单盒样式 | `login/style.css` + 各页 `@import` | 只写 `.form` 里的表单内容 |

于是本页 `<style>` 只有 3 行，却拥有完整的 440×650 表单盒、标题排版、滑入动画。

| 收益 | 代价 / 风险 |
| --- | --- |
| 三页视觉天然一致，改一处三页同步 | CSS 躺在 `login/` 下，忘记密码页要 `@import '../login/style.css'`，形成**反向依赖** |
| 页面本体只有 62 行，心智负担极低 | 650px 高度是为登录页定的，本页字段最少、留白最多（316px） |
| 新增认证页（如"重置成功页"）成本极低 | 共用组件无法按页差异化：`LoginLeftView` 有 `hideContent?: boolean` prop，**三页都没传**（8.11 节） |
| `scoped` + `@import` 让样式不外泄 | `@reference`/`@apply` 依赖 Tailwind 4 编译期处理，IDE 对 `@apply` 提示较弱 |

> **设计判断**：这是典型的「**薄页面 + 厚共用资产**」结构。对中后台模板完全正确——认证页不该有复杂业务，视觉一致性优于灵活性。问题不在结构，而在**这一页的业务层被整块留空了**。

### 2.2 为什么它只有「一个输入框 + 提交 + 返回」

把三条认证页的字段量并排，就能看出这张页面的定位：

| 页面 | 字段/控件 | 交互复杂度 |
| --- | --- | --- |
| 登录 | 账号下拉 + 账号 + 密码 + 滑块 + 记住密码 | 高（4 类输入 + 1 个人机校验 + 1 个记忆项） |
| 注册 | 账号 + 密码 + 确认密码 + 协议勾选 | 中（3 输入 + 1 勾选 + 3 条自定义校验） |
| **忘记密码** | **1 个输入框** | **极低（1 输入 + 2 按钮）** |

这个设计对应的是最简单的一种找回模型：

```text
「输入账号/邮箱 → 系统给你发一封带重置链接的邮件 → 你去邮箱点链接改密码」
```

在这个模型里，**前端只需要一个输入框**：收集账号 → POST → 显示"邮件已发送"。改密码发生在**邮件里的链接**上，属于另一个页面（本仓库没有这一页，见 2.7 节方案 A）。

所以"只有一个输入框"不是偷懒，而是**流程被切到了后端与邮件侧**。反过来说：**如果你的后端不是发链接，而是发 6 位验证码，这个页面必须扩成 2～3 步**（第 18 章就是这么改的）。

### 2.3 三个称呼打架：邮箱？账号？还是手机号？

这是本页最值得记录的一处**设计不一致**。同一屏里同时出现：

| 位置 | 行号 | 文案来源 | 实际说法 |
| --- | --- | --- | --- |
| 标题 | L10 | `forgetPassword.title` | 忘记密码？ |
| 副标题 | L11 | `forgetPassword.subTitle` | 输入您的**电子邮件**来重置您的密码 |
| 输入框占位符 | L16 | `forgetPassword.placeholder` | 请输入您的**电子邮件** |
| 隐藏标签 | L13 | **硬编码中文** | **账号** |
| 登录页的账号输入框 | login L36 | `login.placeholder.username` | 请输入**账号** |
| 实际登录接口字段 | login L222–L225 | `fetchLogin({ userName, password })` | **userName** |

四条证据拼起来，真实情况是：

```text
i18n 文案（模板作者写的）      → email（从某个英文模板继承下来的措辞）
可见标签（本页 L13）           → 账号（中文硬编码，且被 v-if 藏起来了）
真实后端契约（api/auth.ts）     → userName（用户名，不是邮箱、不是手机号）
```

**后果**：如果按文案实现，前端收集的是"邮箱"，但后端 `LoginParams` 只有 `userName`；如果按后端实现，界面在撒谎（让用户填邮箱，实际要用户名）。这不是样式问题，是**契约问题**——第 18 章给的两个方案（"账号模式"与"邮箱模式"）本质上就是在消解这处冲突。

> **一条可复用的经验**：当 i18n 文案、可见标签、接口字段三者不一致时，**以接口字段为准**，然后把文案改到与之一致。反过来（以文案为准去改接口）几乎总是错的，因为接口已经承载了线上数据。

### 2.4 为什么没有 `<ElForm>`——三个复制痕迹

对比注册页的结构，本页少了一整层：

```text
注册页：div.form → ElForm(:model :rules ref) → ElFormItem ×4 → ElInput ×3
本页：  div.form → div.mt-5          → ElInput ×1   ← 直接裸放，没有 FormItem
```

三处细节证明它是**从别处裁剪出来的**，而不是"故意不用表单"：

| 痕迹 | 证据 | 说明 |
| --- | --- | --- |
| ① 空标签残留 | L13 `<span class="input-label" v-if="showInputLabel">账号</span>`，而 `showInputLabel` 恒为 `false`（L48） | 说明原本是"标签 + 输入框"的布局，后来把标签关掉了，但没删代码 |
| ② 用了三元表达式式的类名 | L13 的 `.input-label` 在全仓库**没有任何定义**（`grep -rn "input-label" src/` 只命中这一行） | 一个从未被样式化的 class，纯残留 |
| ③ 处理函数名叫 `register` | L25 `@click="register"`、L53 `const register = async () => {}` | 这是注册页的函数名。忘记密码页的提交函数叫 `register`，是从注册页复制后**忘了改名** |

`ElForm` 的缺失带来一串连锁后果（第 17 章逐条列）：

- 没有 `rules` → 空输入也能点提交；
- 没有 `ElFormItem` → 没有错误提示位、没有 `aria` 关联、没有 `margin-bottom` 的节奏；
- 没有 `formRef.validate()` → `loading` 无人置 `true`，`:loading` 成了死属性；
- 没有 `@keyup.enter`（登录页在 `ElForm` 上挂了，注册页在确认密码上挂了）→ **回车不会提交**；
- 没有 `:key="formKey"` + `watch(locale)` → 语言切换时若已有校验错误，提示语不会跟着变（本页因为无校验，反而"没错可犯"）。

### 2.5 `register()` 是空函数——三种解读

```ts
const register = async () => {}
```

这一行值得单独讨论，因为它决定了整页的性质：

| 解读 | 支持证据 | 反驳证据 |
| --- | --- | --- |
| **A. 故意留白**，等使用者接自己的后端 | 注册页把真实调用注释掉写成 `// TODO: 替换为真实 API 调用`；本页连 TODO 都没有，更像"占位" | 若故意留白，至少应有 `ElMessage` 提示或 TODO 注释，否则使用者点了没反应会以为页面坏了 |
| **B. 没做完**（半成品） | 函数名是 `register`（复制未改）；`username`/`loading` 收集了不用；死标签残留 | — |
| **C. 刻意做"纯视觉 demo"**，认证三页只负责好看 | 项目定位是中后台模板，重点在主布局/表格/权限 | 登录页是**真的**调 `fetchLogin` 并写 token 的，说明认证链路并非纯装饰 |

**本文的判断**：介于 A 与 B 之间——**结构是 A（模板留白），执行是 B（连留白该有的提示都没写）**。第 18 章按"要能用"的标准补齐，第 19.1 节则给出"只想最小改动"的三行版本（加 `ElMessage` + `trim` + `loading`）。

### 2.6 650px 的高度预算：为什么底部空 316px

`login/style.css` L5 把表单盒钉死为 `440×650`，而本页内容只有约 244px：

| 区块 | 高度 | 来源 |
| --- | --- | --- |
| `.auth-right-wrap` 上下 padding | 5 + 5 = 10px | `style.css` L5 `py-[5px]` |
| `.form` 上下 padding | 40 + 40 = 80px | `style.css` L11 `py-[40px]` |
| `h3.title` | ≈ 43px | `text-4xl` 36px × 1.2 行高 |
| `p.sub-title` | 10 + ≈ 21 = 31px | `mt-[10px]` + `text-sm` 14px × 1.5 |

| 提交按钮容器 | 15 + 40 = 55px | 内联 `margin-top: 15px` |
| 返回按钮容器 | 15 + 40 = 55px | 内联 `margin-top: 15px` |
| **合计** | **≈ 244px** | |
| 容器内容区 | 650 − 10 − 80 = **560px** | |
| **空白** | **≈ 316px** | 全部落在两个按钮下方 |

三个直接后果：

1. **视觉重心偏上**：内容贴顶，底部一大片空，窄屏（≤640px）时更明显（`max-sm:pt-10` 还会再往下推 40px）。

3. **`overflow-hidden`**（`style.css` L5）意味着**超出部分被裁掉且不可滚动**：一旦加两个字段就超 560px，用户会看不到"提交"按钮，且无法滚动到它。这是第 17.8 节列为"高"的原因。

### 2.7 真实的忘记密码有几种做法：四种方案对比

模板把流程切到了"邮件侧"，但**邮件侧怎么做**有四种主流方案。理解它们，才知道第 18 章为什么那样改：

| # | 方案 | 用户体验 | 前端页面 | 后端复杂度 | 安全性 | 适合场景 |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | **邮件链接（一次性 token）** | 输入邮箱 → 去邮箱点链接 → 在新页面设新密码 | 本页 + 一个 `reset-password` 落地页 | 中（发信 + token 签发/校验） | **高**（token 可限时、限次、绑 IP/UA） | 用户有真实邮箱，B 端/C 端通用 |
| **B** | **邮箱验证码（OTP）** | 输入邮箱 → 收 6 位码 → 同页输码 + 新密码 | 本页扩成 2 步（第 18 章采用） | 中（发信 + 存码 + 校验 + 限流） | 中高（需防爆破、限次） | 无独立落地页、想留在当前页 |
| **C** | **短信 OTP** | 输入手机号 → 收短信 → 输码 + 新密码 | 本页扩成 2 步 + 倒计时 | 中高（短信通道成本、签名报备） | 中高（SIM 劫持风险） | 国内 C 端、手机号是主身份 |
| **D** | **人工/管理员重置** | 联系客服 → 人工核身 → 后台重置 | 本页只需"提示联系管理员" | 低 | 取决于人工流程 | 内部系统、账号少 |

本仓库现状 = **A 的入口 + 空实现**：文案说"输入邮件我们会给你发重置方式"，但没有落地页、没有接口、没有发信。

**四方案共同的安全底线**（第 18.6 节会在代码里体现）：

| 风险 | 对策 |
| --- | --- |
| 用户枚举（拿别人的邮箱试探账号是否存在） | 无论账号是否存在，**统一返回**"如果该账号存在，我们已发送" |
| 邮件轰炸 / 接口刷量 | 同一账号 60s 冷却 + 单 IP/单账号日限额 + 图形/滑块验证（可选） |
| 验证码爆破 | 6 位数字 + **5 次错误即失效** + 10 分钟 TTL |
| Token 泄漏 | 一次性、短 TTL（≤15min）、**入库只存哈希**、绑定 userId、用后即焚 |
| 重置后会话残留 | 重置成功 → 服务端**吊销该用户全部 refreshToken/session** |
| 重放 / CSRF | Token 与 userId 绑定；落地页校验 `token` 且校验来源；关键接口带 CSRF 头 |
| 日志泄漏 | 不在 URL/日志中记录明文 token 与验证码 |

### 3.3 为什么这 62 行几乎没有 `import`

本页脚本只有 15 行，**一行 import 都没有**，却用了 `useRouter`、`ref`、`ElInput`、`ElButton`、`$t`。四者来自四条不同通路：

| 使用的东西 | 来源 | 机制 | 证据 |
| --- | --- | --- | --- |
| `ref` | `vue` | `AutoImport({ imports: ['vue', ...] })` | `vite.config.ts` 的 AutoImport 插件 |
| `useRouter` | `vue-router` | 同上（`'vue-router'` 在 imports 列表里） | 同上 |
| `ElInput` / `ElButton` | `element-plus` | `Components({ resolvers: [ElementPlusResolver()] })` 在模板编译时自动 import | `vite.config.ts` |
| `$t` | `vue-i18n` 全局注入 | `createI18n({ legacy: false, globalInjection: true })` | `src/locales/index.ts` |
| `v-ripple` | 自定义指令 | `setupRippleDirective(app)` 在 `main.ts` 里全局注册 | `src/directives/business/ripple.ts` L114 |

**四个必须记住的边界**：

1. **自动导入只覆盖 `imports` 列表里的包**。`useI18n`（组合式 API）**不在**列表里——所以注册页必须显式 `import { useI18n } from 'vue-i18n'`（register L89），而本页因为只用模板里的 `$t`，所以不需要。
2. **`$t` 只在模板可用**。`<script>` 里若要翻译，必须 `const { t } = useI18n()`（登录页 L123）或 `import { $t } from '@/locales'`（`utils/router.ts` 用的是后者）。
3. **组件自动导入只对模板生效**。若在 `<script>` 里写 `ElMessage.success()`，`ElMessage` 属于 **API**，由 `AutoImport` 的 `ElementPlusResolver()` 负责引入（登录页 L116 却仍显式 import 了 `ElNotification`，属于冗余但无害）。
4. **指令不会自动导入**，靠 `app.directive()` 全局注册（`main.ts` → `setupRippleDirective`）。

### 3.5 样式的七步作用域链

为什么"3 行样式"能管住整页？因为有三层叠加：

```text
① forget-password/index.vue L60  <style scoped>
   → 编译器给本 SFC 生成唯一 id，如 data-v-7a3c9f21
② L61  @import '../login/style.css'
   → PostCSS 把 39 行 CSS 文本级内联进当前样式块
③ 内联后的每条选择器被追加属性选择器
   .auth-right-wrap  →  .auth-right-wrap[data-v-7a3c9f21]
   .title            →  .title[data-v-7a3c9f21]
④ Tailwind 的 @apply 在 scoped 之前完成展开（@reference 只提供"词表"，不产出 CSS）

⑦ 子组件（LoginLeftView / AuthTopBar / ElInput）的**根元素**也会带父级 data-v，
   所以 .custom-height 能命中 ElInput 的根 div；但子组件内部元素不带，故不受影响
```

**这解释了 6.3 节那个"40px 输入框看起来只有 36px"的疑问**：`.custom-height[data-v-7a3c9f21]` 命中的是 `ElInput` 的**根 `div`**（它有父级 scope id），而内部的 `.el-input__wrapper` 不带这个属性，于是仍按全局 `--el-component-size`（36px）渲染。

### 4.1 根容器为什么用 `h-screen` 而不是 `h-full`

| 写法 | 依赖 | 结果 |
| --- | --- | --- |
| `h-screen` | 视口单位 `100vh` | 与父级高度无关，**永远等于视口高**；`main.ts` 挂载点即 `#app`，无高度约束时也安全 |
| `h-full` | 父级有确定高度 | 父级（`#app`）若无 `height`，`height:100%` 会失效 → 退化成内容高度 |

选 `h-screen` 是**为了不依赖挂载点样式**，属于稳健写法。代价：移动端浏览器地址栏收起/展开时 `100vh` 会"跳动"（可用 `100dvh` 优化，第 19.7 节）。

### 4.2 `relative` + `absolute` 的父子约定

L5 的 `relative` 与 L8 的 `absolute` 是一对**必须成对出现**的约定：

```text
父 .relative.flex-1
   ├─ 宽度 = 100vw − 65vw = 35vw
   ├─ 高度 = 100vh（被父级 flex 拉伸）
   └─ 子 .absolute inset-0 m-auto w-[440px] h-[650px]
        → 四边为 0 + 固定宽高 + margin:auto = 完美居中（7.2 节详述）
```

三个"删掉就坏"的实验：

| 删掉 | 现象 |
| --- | --- |
| 父级的 `relative` | 表单盒相对 `body` 居中 → 落在整屏正中，压在左侧插画上 |
| `.auth-right-wrap` 的 `m-auto` | `inset-0` + 固定宽高 → 元素贴左上角（`top:0;left:0` 生效，`right/bottom` 被宽高覆盖） |
| `w-[440px] h-[650px]` 之一 | `inset-0` 会把元素在该方向拉伸，"居中"退化为"填满并裁切" |

### 4.5 L14–L18：`ElInput` 的 3 个 props 与 8 个"缺席的 props"

**已给的 3 个**：

| prop | 值 | 作用 |
| --- | --- | --- |
| `class` | `custom-height` | 40px 高（落在外层根 div） |
| `placeholder` | `$t('forgetPassword.placeholder')` | 空值提示，随语言变化 |
| `v-model`（`.trim`） | `username` | 双向绑定；`.trim` 无效（见下） |

**缺席但本页需要的**：

| 缺席的 prop | 应该的值 | 缺失后果 |
| --- | --- | --- |
| `type` | `'email'`（若走邮箱）或 `'text'` | 移动端键盘不会切到邮箱布局；浏览器不做邮箱格式软校验 |
| `clearable` | `true` | 用户必须手动删掉输错的内容 |
| `maxlength` | `100` | 可粘贴超长字符串（后端需兜底） |
| `autocomplete` | `'username'` / `'email'` | 密码管理器无法识别这是一个可自动填充的字段 |
| `name` | `'account'` | 表单自动填充与部分浏览器行为受影响 |
| `autofocus` | `true` | 进页后需手动点输入框才出光标（键盘用户多一次 Tab） |
| `@keyup.enter` | `register` | **回车不提交**，与登录页（`ElForm` 上挂了 `@keyup.enter`）行为不一致 |
| `aria-label` | `$t('forgetPassword.accountLabel')` | 占位符消失后（输入内容时）读屏无标签可读 |

**关于 `.trim` 的准确结论**：

```text
Vue 编译 v-model.trim（组件上）：
  <ElInput v-model.trim="username" />
→
  h(ElInput, {
    modelValue: username,
    'onUpdate:modelValue': $event => username = $event,
    modelModifiers: { trim: true }        ← 关键：交给组件自己处理
  })
```

原生 `<input>` 的 `.trim` 由**编译器内联**处理（`$event.target.value.trim()`），但**组件上的修饰符必须由组件自己实现**。`ElInput` 的 props 里没有 `modelModifiers`，也不读取 `$attrs.modelModifiers`，所以**trim 不生效**。验证方法：输入 `"  abc  "`，点提交前打印 `username.value`，会看到空格还在。

> **正确姿势**：提交时 `const account = username.value.trim()`；或在 `@blur` 里手写 `username.value = username.value.trim()`。第 18 章的 patch 用的是前者。

### 4.6 L21–L31：提交按钮的五个属性，两个是死的

| 属性 | 是否生效 | 说明 |
| --- | --- | --- |
| `class="w-full custom-height"` | ✅ | 宽 100%、高 40px（`!important` 覆盖 36px） |

**`v-ripple` 与 `loading` 的冲突细节**：Element Plus 在 `loading` 为真时会给按钮加 `is-loading` 并把内容替换成转圈图标，但**不会移除已绑定的事件监听**；`v-ripple` 的 `mousedown` 监听挂在根 `button` 上，因此加载中点击**仍会有水波纹**。若将来真的启用 `loading`，建议在 `loading` 时用 `pointer-events: none` 或 `:disabled="loading"` 双保险——否则用户会看到"转圈 + 波纹"同时出现，误以为按钮还能点。

### 4.7 L33–L37：返回按钮与"历史堆栈回环"

| 属性 | 值 | 说明 |
| --- | --- | --- |
| `class` | `w-full custom-height` | 与提交按钮等宽等高 |
| `plain` | — | 白底 + 边框 + 主色文字；`type` 未指定 → `el-button` 默认样式 + `is-plain` |
| `@click="toLogin"` | — | L55：`router.push({ name: 'Login' })` |

**`push` 而非 `replace` 的后果**：

```text
登录页  --click 忘记密码-->  忘记密码页  --click 返回-->  登录页
   history: [Login, Forget, Login]     ← 三步都进了历史栈

此时用户按浏览器「后退」→ 回到"忘记密码页"
再按后退 → 回到"登录页"（第一次那条）
```

如果用户连续点"返回/忘记密码"多次，历史栈会不断堆叠，体验上像"退不出去"。**建议改成**：

```ts
const toLogin = () => router.replace({ name: 'Login' })
```

第 18 章的 patch 已改为 `replace`。

### 6.2 `@import` 与 `scoped` 的相互作用（最容易误解的一点）

```text
编译前（forget-password/index.vue）
  <style scoped>
    @import '../login/style.css';   ← 含 .auth-right-wrap / .form / .title / .custom-height
  </style>

编译后（概念示意）
  .auth-right-wrap[data-v-fp01] { position:absolute; inset:0; width:440px; height:650px; … }
  .auth-right-wrap[data-v-fp01] .form[data-v-fp01] { height:100%; padding-block:40px }
  .title[data-v-fp01] { font-size:2.25rem; font-weight:600; color:var(--art-gray-900) }
  .custom-height[data-v-fp01] { height:40px !important }
  @keyframes slideInRight-fp01 { … }
```

**两个常被问到的点**：

1. **会不会污染全局？** 不会。三页各自编译出不同的 `data-v` 哈希，虽引入同一份 CSS，但选择器互不命中。
2. **`@keyframes` 会不会冲突？** 不会。scoped 编译会给关键帧**重命名**并同步改写 `animation` 引用，所以三页同时存在 `slideInRight` 也不打架。

> **一个反向风险**：如果有人把 `login/style.css` 改成在 `main.ts` 里全局引入，那么 `.auth-right-wrap`、`.title`、`.custom-height` 会**立刻泄漏到所有页面**——尤其 `.custom-height` 会被主布局大量表单误命中。第 17.12 节列为中危。

### 6.3 40px 输入框为什么看起来只有 36px

这是读源码才能发现的"1px 级"细节：

```text
.el-input.custom-height[data-v-fp01]   → height: 40px !important   （我们的类，命中根 div）
  └─ .el-input__wrapper                → 无 data-v-fp01，仍按全局规则
       min-height: var(--el-component-size)
       --el-component-size = var(--el-component-custom-height) = 36px   （el-ui.scss L13/L15）
```

于是：

| 元素 | 高度 | 视觉结果 |
| --- | --- | --- |
| `ElInput` 根 div | 40px | 外层占位 40px，与按钮等高 |
| 内部 wrapper / input | 36px | 白底边框只有 36px 高，上下各留 2px 空隙 |

**如果要真正 40px 的内盒**，需要覆盖内层变量：

```css
/* 追加在本页 <style scoped> 里 */
:deep(.el-input__wrapper) {
  min-height: 40px;
}
/* 或用 Element Plus 提供的变量 */
:deep(.el-input) {
  --el-input-height: 40px;
}
```

同理，`.el-button--default` 的高度也被 `el-ui.scss` L85–L87 钉在 `var(--el-component-custom-height)` = 36px，本页靠 `.custom-height` 的 `!important` 提到 40px——**按钮是真的 40px，输入框是"外 40 内 36"**，这就是两者并排时那点微妙的不齐。

### 7.1 `@reference` 与 `@apply`：Tailwind 4 的两个编译期概念

| 概念 | 作用 | 若缺失 |
| --- | --- | --- |
| `@reference` | 声明"我在哪里能找到这些工具类/变量的定义"，**仅供解析** | `@apply` 报 `Cannot apply unknown utility class` |
| `@apply` | 把工具类**展开成真实 CSS 声明**写进当前选择器 | 无 |

**为什么不用 `@import 'tailwindcss'`？** 那会把整套 Tailwind 基础样式（preflight）**再输出一遍**。三页各引入一次 → 三份重复 CSS。`@reference` 正是 Tailwind 4 为"组件级复用工具类"设计的解法。

### 7.2 绝对居中四件套：为什么不用 `transform`

```css
position: absolute;   /* 脱离文档流，才能让 inset 生效 */
inset: 0;             /* 四边贴住定位父级（L5 的 .relative.flex-1） */
width: 440px;
height: 650px;        /* 有固定尺寸，inset 的"拉伸"才被 margin 接管 */
margin: auto;         /* 四边等分剩余空间 → 水平垂直居中 */
```

| 属性 | 必须性 | 删掉的后果 |
| --- | --- | --- |
| `absolute` | 必须 | 变成普通流元素，`inset-0` 无效 |
| `inset-0` | 必须 | `margin:auto` 无剩余空间可分配，元素贴左上 |
| 固定宽高 | 必须 | 元素被 4 个 0 拉伸为父级大小，居中退化为"填满" |
| `m-auto` | 必须 | 元素贴在 `inset-0` 的左上角 |

**与 `top:50%;left:50%;transform:translate(-50%,-50%)` 的关键差异**：

```text
transform 方案：居中本身占用了 transform 属性
               → 滑入动画若也用 transform，必须叠加成 translate(-50%,-50%) translateX(30px)
               → 否则动画一开始元素会跳到左上角

margin:auto 方案：不占用 transform
               → 动画可自由使用 translateX(30px) → 0
```

这就是作者选后者最实在的理由：**给动画留出 `transform` 通道**。

| 断点 | 触发条件 | 变化 | 目的 |
| --- | --- | --- | --- |
| `max-md`（≤768px） | `@media (width < 768px)` | `.auth-right-wrap` 关闭动画；`.title` 降为 30px | 移动端省电、避免布局抖动 |
| `max-sm`（≤640px） | `@media (width < 640px)` | 表单盒宽 100%、左右 padding 28px；`.title` 顶部留 40px | 窄屏放下表单；标题避让顶栏 |

### 7.4 动画与 `overflow-hidden` 的配合

`overflow:hidden`（L5）除了裁掉超出内容，还有一个隐性作用：**避免滑入过程中出现水平滚动条**。`translateX(30px)` 在动画起手时会让元素右移 30px，若容器没有裁切，页面可能出现横向滚动。

### 8.6 装饰动画系统（L148–L313）

**基础规则**（L149–L155）：

| 声明 | 作用 | 为什么必须 |
| --- | --- | --- |
| `position: absolute` | 所有装饰元素绝对定位 | 否则会参与文档流、把布局挤乱 |
| `opacity: 0` | **初始透明** | 关键：动画完成后才可见，避免"先闪现再动画" |
| `animation-fill-mode: forwards` | 保留终态 | `from` 里是 `opacity:0`，没有 `forwards` 会闪回透明 |
| `animation-duration: 0.8s` | 统一时长 | 由各 `animate-*` 类只覆盖 `animation-name`，时长复用 |
| `animation-timing-function: cubic-bezier(0.25,0.46,0.45,0.94)` | 缓动 | 与右栏滑入同一个曲线，节奏统一 |

**mixin `fadeAnimation($direction, $rotation)`**（L158–L182）：

| 行 | 逻辑 | 说明 |
| --- | --- | --- |
| L159 | `from { opacity: 0; … }` | 起始透明 |
| L162–L170 | 按 `$direction` 分四种位移 | `up`→`translateY(30px)`；`down`→`translateY(-30px)`；`left`→`translateX(-30px)`；`right`→`translateX(30px)`，均叠加 `rotate($rotation)` |
| L173 | `to { opacity: 1; … }` | — |
| L176–L180 | 归位 | `up/down` 归 `translateY(0)`；其余归 `translateX(0)`；**旋转保留**（`rotate($rotation)` 在终态仍存在） |

> **细节**：`fadeInUp` 的 `from` 是 `translateY(30px)`（在下方），`to` 是 `translateY(0)` → 元素**向上**移动，所以叫"fade in up"。方向名描述的是"运动方向"，不是"起始位置"。

| --- | --- | --- | --- |
| `fadeInUp` | L185–L187 | Y+30 → 0 | 空心圆、小圆 |
| `fadeInDown` | L189–L191 | Y−30 → 0 | 太阳/月亮 |
| `fadeInLeft` | L193–L195 | X−30 → 0 | 旋转方块（被覆盖） |
| `fadeInLeftRotated` | L197–L199 | X−30 → 0，`rotate(-25deg)` | `.square-rotated` |
| `fadeInRight` | L201–L203 | X+30 → 0 | 右下方块（被覆盖） |
| `fadeInRightRotated` | L205–L207 | X+30 → 0，`rotate(45deg)` | `.square-bottom-right` |
| `fadeInLeftRotatedBlue` | L209–L211 | X−30 → 0，`rotate(-10deg)` | 蓝方块 |
| `fadeInLeftRotatedPink` | L213–L215 | X−30 → 0，`rotate(10deg)` | 粉方块 |

**"月牙"是怎么画出来的**：

```text
.circle-top-right（50×50 实心圆，背景 = 主题浅色）
  + box-shadow: 0 0 25px #333 inset   → 内部一圈暗边
  + ::before（50×50 圆，背景 = 左区底色）定位 left:15px
    → 遮住右侧 15px 以外的部分，露出左侧一弯月牙
  + rotate:-48deg → 月牙朝向更像"月亮"
悬停时 ::before 右移到 18px → 月牙变细（像月相变化）
```

这是纯 CSS 画月亮的经典做法：**两个圆做布尔减**。注意 `::before` 的背景色必须**等于根容器背景**，暗色下是 L516 的混黑色——所以 L537 用的是 `$bg-mix-light-9`（暗色下已被重新定义语境）。这也是为什么**一旦有人改了左区背景色但忘了改 `::before`，月亮就会"破功"**。

### 8.11 `hideContent` 为什么没被用

```text
设计意图：登录/注册/忘记密码三页中，可能有一页想"只留 logo、不要插画文案"
实际实现：defineProps 声明了，但模板没有 v-if、脚本没有解构
结果：传与不传完全一样
```

**如果要让它生效**，最小改动是：

```vue
<!-- 模板：给插画/文案/装饰加条件 -->
<div v-if="!hideContent" class="left-img">…</div>
<div v-if="!hideContent" class="text-wrap">…</div>
<div v-if="!hideContent" class="geometric-decorations">…</div>
```

```ts
const props = defineProps<{ hideContent?: boolean }>()
```

对忘记密码页而言，一个合理用法是：**隐藏插画区，让表单居中更"工具化"**——因为重置密码是"任务型"操作，不需要营销文案。第 19.8 节给出这个改造。

## 10. 缺失的表单层：ElForm 机制深潜

> 本页没有 `<ElForm>`，所以这一章讲的是"**如果加上，它会怎么工作**"。这是第 18 章 patch 的理论基础。

### 10.1 本页 vs 注册页：表单层的十项对照

| 能力 | 注册页（有 ElForm） | 本页（无 ElForm） |
| --- | --- | --- |
| 数据模型 | `:model="formData"`（reactive 对象） | 无（散装 `ref`） |
| 规则 | `:rules="rules"`（computed） | 无 |
| 字段注册 | `<ElFormItem prop="username">` | 无 |
| 错误提示位 | `ElFormItem` 内置 `.el-form-item__error` | 无 |
| 失焦校验 | `trigger: 'blur'` | 无 |
| 全量校验 | `formRef.validate()` | 无 |
| 单字段校验 | `validateField('confirmPassword')` | 无 |
| 回车提交 | 确认密码上 `@keyup.enter` | 无 |
| 错误滚动定位 | `scrollToField` | 无 |
| 无障碍 | `label` + `aria-labelledby` | 无 |

### 10.2 `ElForm` 到底提供了什么

```text
<ElForm :model :rules>
  ├─ provide(FormContextKey, { model, rules, registerField, unregisterField, validate, ... })
  └─ 渲染 <form> 元素（默认），监听 submit.prevent 防止刷新

<ElFormItem prop="account">
  ├─ inject(FormContextKey) → 在 mounted 时 registerField({ prop, validate })
  ├─ 计算 itemRules = rules[prop] 与自身 :rules 的合并
  └─ 渲染 label / content / error 三段结构
```

三个关键点：

1. **`prop` 是"字段名"，也是"规则键"**。`prop="account"` 会去 `model.account` 取值、去 `rules.account` 取规则。`prop` 写错 → 规则找不到 → **静默不校验**（最隐蔽的错误）。
2. **规则可以写在 FormItem 上，也可以写在 Form 上**。Form 上的 `rules` 按 `prop` 索引；FormItem 上的 `rules` 只作用于自己。二者合并。
3. **校验器是 `async-validator`**。`required` / `min` / `max` / `type: 'email'` / `pattern` / `validator` 都是它的规则语法。

### 10.3 `validate()` 内部发生了什么

```text
formRef.validate()
  → 取所有已注册且有 prop 的字段
  → 逐个 field.validate('')  （trigger 传空字符串 = 不筛触发器）
       → 组装 descriptor = { [prop]: itemRules }
       → new AsyncValidator(descriptor).validate({ [prop]: value })
       → 成功 → callback() ；失败 → 收集第一个 error.message
  → 全部成功 → resolve(true)
  → 任一失败 → reject({ 字段名: [{ message, field }] })   ← 注意：reject 而非 resolve(false)
  → 若 scrollToField / scrollToError 开启 → 滚动到第一个错误字段
```

**两个必须记住的行为**：

| 行为 | 说明 | 踩坑后果 |
| --- | --- | --- |
| 失败时 `reject` | `await formRef.validate()` 失败会**抛异常** | 不写 `try/catch` 会导致 `loading` 永远不复位、控制台报未捕获 Promise |
| `validate(callback)` 与 `await` 二选一 | 传回调时不再抛异常 | 同时用会拿到 `undefined` |

正确骨架（登录页 L206–L254 就是这个结构）：

```ts
try {
  await formRef.value.validate()   // 失败 → 抛出，跳到 catch
  loading.value = true
  // …请求
} catch (e) {
  // 校验失败 或 请求失败
} finally {
  loading.value = false            // 无论如何复位
}
```

### 10.4 `trigger` 的三种取值

| trigger | 触发时机 | 适用 |
| --- | --- | --- |
| `'blur'` | 失焦 | 输入框（默认选择） |
| `'change'` | 值变化 | 下拉、勾选框、开关 |
| `''`（空） | 只在 `validate()` 时 | 需要"提交时才校验"的字段 |

注册页的用法很典型：`username/password/confirmPassword` 用 `blur`，`agreement` 用 `change`（L191）。

### 10.5 给本页加"最小校验"：14 行

```vue
<ElForm ref="formRef" :model="formData" :rules="rules" @keyup.enter="handleSubmit">
  <ElFormItem prop="account">
    <ElInput v-model="formData.account" :placeholder="$t('forgetPassword.placeholder')" />
  </ElFormItem>
  <ElButton type="primary" :loading="loading" @click="handleSubmit">…</ElButton>
</ElForm>
```

```ts
const formRef = ref<FormInstance>()
const formData = reactive({ account: '' })

const rules = computed<FormRules>(() => ({
  account: [
    { required: true, message: t('forgetPassword.rule.required'), trigger: 'blur' },
    { type: 'email', message: t('forgetPassword.rule.email'), trigger: 'blur' }
  ]
}))
```

**四个容易写错的地方**：

| 错误写法 | 后果 | 正确写法 |
| --- | --- | --- |
| `const rules = { … }`（普通对象） | 切换语言后提示语不变 | `computed(() => ({ … t(…) }))`，注册页 L176 就是这么写的 |
| `prop="username"` 但 `model` 里叫 `account` | 规则静默失效 | `prop` 必须与 `model` 的键一致 |
| 忘了 `try/catch` | `loading` 卡死 | 用 `finally` 复位 |
| `type: 'email'` 但后端要的是用户名 | 用户被"邮箱格式"卡住，而系统只认 `userName` | 先定契约（2.3 节），再选 `type` 或 `pattern` |

### 10.6 账号 / 邮箱 / 手机号：三种校验策略

| 身份类型 | 规则写法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **用户名** | `{ required: true, min: 3, max: 20, pattern: /^[a-zA-Z0-9_-]+$/ }` | 与现有 `userName` 契约一致 | 用户可能记不住用户名（这正是"忘记密码"要解决的问题之一） |
| **邮箱** | `{ type: 'email' }`（async-validator 内置） | 有"发送通道"（能收信） | 系统若没存邮箱，无法匹配用户 |
| **手机号** | `{ pattern: /^1[3-9]\d{9}$/ }` | 国内体验好 | 需要短信通道与成本 |
| **二选一** | 自定义 `validator`：先判是否含 `@`，再分支校验 | 兼容老用户 | 提示语要写清楚"账号或邮箱" |

**一个务实建议**：如果后端只有 `userName`，**不要在前端假裝收集邮箱**。要么把文案改成"请输入账号"，要么真的给用户表加 `email` 字段（第 19.2 节给了迁移建议）。**最差的做法是保持现状：提示填邮箱、实际发给后端一个 userName。**

### 10.7 无障碍：`label` 与错误提示的关联

Element Plus 的 `ElFormItem` 会自动生成 `label` 的 `for` 与 `aria-labelledby`，并把错误文本放在 `.el-form-item__error`（带 `role="alert"` 语义由 Element Plus 内部处理）。这就是为什么"加 `ElForm`"不只是加校验，**同时也补齐了无障碍**——本页现在两者皆无。

### 12.3 匿名白名单：`isStaticRoute` 的正则推演

守卫 `beforeEach.ts` L226–L251：

| 行 | 逻辑 | 说明 |
| --- | --- | --- |
| L226 | `function isStaticRoute(path: string): boolean` | 入参是**目标路径** |
| L227–L228 | `routes.some((route) => …)` | 递归遍历 `staticRoutes` |
| L231–L233 | `if (route.name === 'Exception404') return false` | **404 兜底路由不算匿名可访问**：否则未登录时输入任意错误地址会直接停在 404，永远跳不到登录页 |
| L236 | `const routePath = route.path` | 如 `/auth/forget-password` |
| L237 | `routePath.replace(/:[^/]+/g, '[^/]+').replace(/\*/g, '.*')` | 把 `:id` 换成正则，把 `*` 换成 `.*` |
| L238 | `new RegExp('^' + pattern + '$')` | 全匹配 |
| L240–L242 | `regex.test(targetPath) → true` | 命中即匿名放行 |
| L243–L245 | 否则递归子路由 | — |

**对本页的实际推演**：

```text
route.path = '/auth/forget-password'
→ 不含 ':' 也不含 '*'，replace 后不变
→ pattern = '/auth/forget-password'
→ regex  = /^\/auth\/forget-password$/
→ 访问 '/auth/forget-password' → match.slice 命中 → true → 匿名放行 ✅

边界：'/auth/forget-password/'（末尾多斜杠）
→ 正则要求 $ 结尾 → 不匹配 → 走到"未登录跳登录页" ❌
（实际 vue-router 默认会规范化末尾斜杠，通常感知不到）
```

**一个潜在风险**：`'-'` 在正则里是普通字符，安全；但如果路径里有 `.`（如 `/auth/v1.0/reset`），`.` 会被当通配符，导致 `/auth/v1x0/reset` 也被放行。属于低危但值得知道的行为。

### 12.7 `redirect` 参数为什么在这里会丢

```text
场景：用户未登录访问 /system/user → 守卫跳 /auth/login?redirect=/system/user
     用户发现忘了密码 → 点"忘记密码"
       RouterLink :to="{ name: 'ForgetPassword' }"   ← 没有带 query
     → 地址变成 /auth/forget-password（redirect 丢失）
     用户重置成功后 → 返回登录页（也没有 redirect）
     → 登录成功后 router.push('/')   ← 原本想回的 /system/user 再也回不去
```

**结论**：忘记密码流程**天然会打断 `redirect` 链路**。若想保留，需要：

1. 登录页跳转时带上：`:to="{ name: 'ForgetPassword', query: route.query }"`；
2. 本页"返回"时带回：`router.replace({ name: 'Login', query: route.query })`。

第 18 章的 patch 已按此实现（`const route = useRoute()` 后透传 `query`）。

| 环节 | 代码 | 时机 |

### 16.4 为什么三页的"返回/互链"设计不对称

| 页面 | 底部链接 | 为什么 |

> 24 条，按严重度分级：**高**（影响主流程可用性）、**中**（影响体验/维护）、**低**（一致性/规范）。

    }
    if (value !== formData.newPassword) {
      callback(new Error(t('forgetPassword.rule.passwordMismatch')))
      return
    }
    callback()
  }

  const rules = computed<FormRules>(() => ({
    account: [
      { required: true, message: t('forgetPassword.rule.accountRequired'), trigger: 'blur' },
      { min: 3, max: 100, message: t('forgetPassword.rule.accountLength'), trigger: 'blur' }
    ],
    code: [
      { required: true, message: t('forgetPassword.rule.codeRequired'), trigger: 'blur' },
      {
        pattern: new RegExp(`^\\d{${CODE_LENGTH}}$`),
        message: t('forgetPassword.rule.codeFormat'),
        trigger: 'blur'
      }
    ],
    newPassword: [
      { required: true, message: t('forgetPassword.rule.newPasswordRequired'), trigger: 'blur' },
      {
        min: PASSWORD_MIN_LENGTH,
        message: t('forgetPassword.rule.passwordLength'),
        trigger: 'blur'
      }
    ],
    confirmPassword: [{ required: true, validator: validateConfirmPassword, trigger: 'blur' }]
  }))

  /** 启动重发倒计时 */
  const startCountdown = () => {
    stopCountdown()
    countdown.value = COUNTDOWN_SECONDS
    timer = setInterval(() => {
      countdown.value -= 1
      if (countdown.value <= 0) stopCountdown()
    }, 1000)
  }

  /** 停止并清理定时器（必须清理，否则组件卸载后仍在跑） */
  const stopCountdown = () => {
    if (timer) {
      clearInterval(timer)
      timer = null
    }
    countdown.value = 0
  }

  onUnmounted(stopCountdown)

  /** 发送验证码（步骤 1 的主按钮 / 步骤 2 的重发按钮共用） */
  const handleSendCode = async () => {
    if (countdown.value > 0 || sending.value) return

    // 只校验账号字段；未渲染的字段不会被 validateField 命中
    try {
      await formRef.value?.validateField('account')
    } catch {
      return
    }

    sending.value = true
    try {
      await fetchSendResetCode({ account: formData.account.trim() })
      step.value = 2
      startCountdown()
      ElMessage.success(t('forgetPassword.codeSentTip'))
    } catch (error) {
      // HttpError 已由 HTTP 拦截器统一提示，这里只兜底非预期错误
      if (!(error instanceof HttpError)) {
        console.error('[ForgetPassword] send code failed:', error)
      }
    } finally {
      sending.value = false
    }
  }

  /** 提交：step1 → 发码；step2 → 重置 */
  const handleSubmit = async () => {
    if (!formRef.value || loading.value || sending.value) return

    try {
      await formRef.value.validate()
    } catch {
      return
    }

    if (step.value === 1) {
      await handleSendCode()
      return
    }

    loading.value = true
    try {
      await fetchResetPassword({
        account: formData.account.trim(),
        code: formData.code.trim(),
        newPassword: formData.newPassword
      })
      ElMessage.success(t('forgetPassword.success'))
      stopCountdown()
      router.replace({ name: 'Login', query: route.query })
    } catch (error) {
      if (!(error instanceof HttpError)) {
        console.error('[ForgetPassword] reset failed:', error)
      }
    } finally {
      loading.value = false
    }
  }

  /** 返回：step2 → 回第一步；step1 → 回登录 */
  const handleBack = () => {
    if (step.value === 2) {
      step.value = 1
      formData.code = ''
      formData.newPassword = ''
      formData.confirmPassword = ''
      stopCountdown()
      formRef.value?.clearValidate()
      return
    }
    router.replace({ name: 'Login', query: route.query })
  }
</script>

### 18.8 后端契约（前后端对齐表）

| 接口 | 方法 | 路径 | 入参 | 出参 | 关键错误码 |
| --- | --- | --- | --- | --- | --- |
| 发送验证码 | POST | `/api/auth/password/code` | `{ account }` | `void` | 429（太频繁）、400（参数非法） |
| 重置密码 | POST | `/api/auth/password/reset` | `{ account, code, newPassword }` | `void` | 400（验证码错误/过期）、429（尝试过多） |
| 链接模式重置 | POST | `/api/auth/password/reset-by-token` | `{ token, newPassword }` | `void` | 400（token 无效/过期） |

**响应包装**（项目统一格式，`types/common/response.ts`）：

```json
{ "code": 200, "msg": "success", "data": null }
```

**四条契约约定**（比接口本身更重要）：

| 约定 | 原因 |
| --- | --- |
| ① 账号不存在时**也返回 200**，`msg` 统一为"如果该账号存在，我们已发送" | 防用户枚举（否则攻击者可批量探测账号是否存在） |
| ② 验证码错误与过期的**提示文案一致** | 避免攻击者区分"错码"与"过期"来缩小爆破范围 |
| ③ 验证码错误 **5 次即作废**该账号当前验证码 | 6 位数字只有 100 万种组合，不限次可被离线/在线爆破 |
| ④ 重置成功**吊销该用户全部会话** | 否则攻击者若已窃取 token，改密也无法把他踢下线 |

### 18.9 服务端必须做的 8 件事（前端做不了）

| # | 事项 | 具体做法 |
| --- | --- | --- |
| 1 | 验证码/Token **只存哈希** | `sha256(code + salt)` 入库，防库泄漏后直接可用 |
| 2 | TTL | 验证码 10 分钟、Token 15 分钟 |
| 3 | 一次性 | 校验成功立即删除记录 |
| 4 | 冷却与限额 | 同账号 60s 一次、日 5 次；同 IP 日 20 次 |
| 5 | 绑定 | Token 绑定 `userId` + 签发时的 UA/IP 摘要（可选） |
| 6 | 密码策略 | 服务端独立校验长度/复杂度，**不信任前端** |
| 7 | 会话失效 | 改密后 `refreshToken` 全量作废，并记录审计日志 |
| 8 | 不泄露细节 | 响应时间尽量恒定（防时序侧信道），错误文案统一 |

### 19.3 让表单盒适配更多内容（解决 650px 死高）

```css
/* 在本页 <style scoped> 里覆盖（同优先级下后加载生效） */
.auth-right-wrap {
  height: auto;
  min-height: 650px;
  max-height: calc(100vh - 40px);
  overflow-y: auto;
}
```

**三个要点**：

| 属性 | 为什么 |
| --- | --- |
| `height: auto` + `min-height: 650px` | 内容少时保持原视觉，内容多时自动长高 |
| `max-height: calc(100vh - 40px)` | 防止小屏超出视口 |
| `overflow-y: auto` | 覆盖原 `overflow: hidden`，内容超高可滚动 |

> 注意：`inset-0 + m-auto` 的居中逻辑在 `height:auto` 下**仍然成立**（因为仍有 `min-height` 撑开），但如果内容超过 `max-height`，会出现内部滚动条——这是预期行为。

### 19.4 加密码强度与一致性校验

```ts
/** 简单强度：长度 + 字符种类 */
const passwordStrength = computed(() => {
  const pwd = formData.newPassword
  if (!pwd) return 0
  let score = 0
  if (pwd.length >= 6) score++
  if (pwd.length >= 10) score++
  if (/[a-z]/.test(pwd) && /[A-Z]/.test(pwd)) score++
  if (/\d/.test(pwd)) score++
  if (/[^\w\s]/.test(pwd)) score++
  return Math.min(score, 4) // 0-4
})
```

配套的 UI（在 `newPassword` 的 `ElFormItem` 内、`ElInput` 之后）：

```vue
<div class="flex gap-1 mt-1.5">
  <i
    v-for="i in 4"
    :key="i"
    class="h-1 flex-1 rounded-full transition-colors"
    :class="i <= passwordStrength ? strengthColor : 'bg-g-300'"
  />
</div>
<p class="mt-1 text-xs text-g-500">{{ $t(`forgetPassword.strength.${passwordStrength}`) }}</p>
```

> **提醒**：前端强度提示是"引导"，**后端必须独立校验**，否则可被绕过。

### 19.6 记住"草稿"：误点返回后还能找回

```ts
const DRAFT_KEY = 'forget-password-draft'

// 输入时存草稿（防抖后写入更佳）
watch(
  () => formData.account,
  (val) => {
    if (val) sessionStorage.setItem(DRAFT_KEY, val)
    else sessionStorage.removeItem(DRAFT_KEY)
  }
)

// 进入页面时恢复
onMounted(() => {
  const draft = sessionStorage.getItem(DRAFT_KEY)
  if (draft) formData.account = draft
})

// 提交成功后清除
sessionStorage.removeItem(DRAFT_KEY)
```

**为什么用 `sessionStorage` 而不是 `localStorage`**：草稿的生命周期应止于"这个标签页"，用 `localStorage` 会长期残留，甚至泄漏到共用电脑上。

### 19.10 三种"重置成功"的收尾方式

| 方式 | 实现 | 适用 |
| --- | --- | --- |
| **直接回登录**（本文采用） | `router.replace({ name: 'Login', query })` + `ElMessage.success` | 最常见、最轻 |

### 22.4 结语：这一页教给我们的三件事

**第一，模板的"空"是设计，不是缺陷；但"空得没有提示"是缺陷。**
三页共用一个外壳、把业务逻辑留给使用者，这是模板的正确姿势。问题在于：`async () => {}` 既没有 `TODO` 注释，也没有任何用户反馈——它让"留白"和"坏掉"在界面上无法区分。**留白必须留得可见**：一句 `ElMessage('演示环境，重置接口未接入')` 就够。

**第二，认证页的复杂度不在 UI，在流程与安全。**
62 行就能画出界面，但要真正可用，需要状态机、校验、倒计时、防重复、防枚举、Token 生命周期、会话吊销。本文第 18 章 300 行代码里，**只有约 100 行是 UI**，其余全是流程与边界。这也解释了为什么"忘记密码"在真实项目里往往由专门的后端服务承担。

**第三，读代码要读到"没写的东西"。**
本页最有价值的发现都不是"代码写了什么"，而是"代码没写什么"：没有 `ElForm`、没有 `validate`、没有 `catch`、没有 `onUnmounted`、`loading` 从不置真、`username` 从不被读。**这些空缺拼起来，就是这张页面的真实状态。**
